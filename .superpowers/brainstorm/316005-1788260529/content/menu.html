Why not the scale, given it is the conventional choice

Because it is the settle you just rejected on the board title, only worse. I ran both candidates against the real Base UI menu in the running app, not a mockup:

candidatetransform values observedends attext resampled
fade["none"] — one value, every framenoneno
fade + scalematrix(.96) → .968 → .982 → .989 → .994 → .996 → .998 → .9992 → .9998 → matrix(1) → nonenoneyes, every frame

A menu is entirely text at 15px. Scaling it means every glyph is resampled at a fractional factor for the whole animation, and then the layer is dropped at the end and the antialiasing flips back — the exact mechanism behind the title settle. The 24px title was the mild case. So the same constraint applies: animate opacity, never transform, on anything whose content is text.

Fade only (recommended)

120ms in, 100ms out, opacity alone. Satisfies rule 2 without inventing a direction the menu never travelled from, and leaves the text rasterised identically throughout. Applies to both menu.tsx and dropdown.tsx.

Fade + scale from the anchor

The conventional treatment, and Base UI even supplies --transform-origin for it. Cost: the resampling above, plus a geometric implication — the menu did not grow out of the trigger, it appeared.

What Base UI already gives us

The exit animation needs no bookkeeping at all. I expected to need a keepMounted flag or an exit-state machine. Measured against the real component: Base UI stamps data-closed + data-ending-style and then waits for the CSS transition to finish before unmounting — a 200ms transition kept the node alive for 242ms. Pure CSS on the element that already carries the attributes. Nothing in menu.tsx or dropdown.tsx gains a single line of state.

And keyboard users are handled for us. Base UI stamps data-instant when the menu was opened by keyboard or assistive tech, meaning "animate instantly". Honouring it is free, and it is the correct accessibility behaviour — a keyboard user driving the menu should not wait on a fade.

One asymmetry to record: Select (which Dropdown wraps) exposes data-open/closed/starting-style/ending-style/side/align but no data-instant. So the dropdown cannot get the keyboard suppression the menu gets for free. Worth knowing before someone writes a shared helper that assumes both behave the same.
