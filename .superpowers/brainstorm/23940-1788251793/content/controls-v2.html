2 · The doubled border — three ways out

A · Contiguous

Border turns purple and the 2px ring sits flush against it (offset: 0) — one solid 3px edge, no gap to read as a second border.

B · Ring with air

Border stays quiet; the ring sits 3px clear of it. Unambiguously a ring around a field rather than a thicker edge.

C · Single edge

2px border at all times — only its colour changes on focus. No ring at all, so nothing can double. Purest fit with rule 1.
Click into each. What you saw was a 1px purple border, a 1px gap, then a 2px purple ring — three concentric edges in one colour. C is my recommendation: the border is the only edge that exists, so there is nothing to double, and it satisfies rule 1 literally (colour is the only thing that changes). Its cost is a slightly heavier resting field, which is why the resting border uses #DCE3F2 rather than the card's #E4EBFA.

3 · Live password requirements

Requirements, checked as you type

Always visible on the sign-up form (never on sign-in), so it occupies fixed space and states the rule before you fail it.
At least 8 characters
A letter and a number
Not your email address

The strength meter I proposed — withdrawn

It scored passwords on a scale nobody agreed to. "Strong" is a judgement, and if the backend then rejects it, the app lied.
The contract is explicit about this:
SignupRequestDTO.password = { "type": "string" }
No minLength. No pattern. The backend declares no password policy at all.

So a checklist is the honest form: it presents rules this app enforces, rather than implying a verdict on the password's quality.

Buttons are the one change here that leaves the auth screens. rounded-full lives once, in button-variants.ts, so it is a one-line edit — but it repaints every button in the app and invalidates their visual baselines. It is also a genuine departure from the mock, whose radius token file records that "every button in the mock is a pill (its radius is exactly half its height)". That is fine, it is what a modernization phase is for, but it needs to be app-wide rather than auth-only: a boxy Create Account beside pill buttons on the board would read as an unfinished migration. 6px is my pick — it agrees with the inputs it sits under, where 8px agrees with the cards instead.

5 · Typeface

Judged in context, not as a specimen sheet — each tile is a real column header, task card, and count. Watch the numerals: they carry the counts and the 2/3 captions, and that is where these differ most.

Some webfonts did not load (no network?) — tiles showing the same shapes are falling back.
This one expands the agreed scope. On screen 1 we scoped Phase 5 as "keep the palette, typography and layout the mock defines; modernize the material." A typeface change moves typography out of mock governance, which means the mock can no longer arbitrate it and the spec's scope section has to say so. It is a reasonable call — but combined with boxy buttons it is most of a rebrand, so it is worth naming rather than sliding into.

Cost, concretely: the font is self-hosted woff2 under public/fonts/plus-jakarta-sans/ with a documented reason (Storybook's Vite builder silently drops next/font, which once shipped the wrong typeface to a screenshot review). So a swap means new woff2 files, a rewritten fonts.css, the fontFamily in all eight typography.tokens.json entries, and every visual baseline in the app.
