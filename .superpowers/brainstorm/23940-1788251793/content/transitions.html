Outgoing board falls 3px and fades; incoming rises 3px into place, columns staggered ~30ms apart. Plain CSS keyed on boardId — no view transitions at all.
Verified constraint. react@19.2.8 exports no ViewTransition (nor unstable_ViewTransition), and next@16.3.0's config schema has no viewTransition key — it exists only inside the bundled react-dom-experimental. React's <ViewTransition> route morph would require the React experimental channel plus a Next canary. For a repo with pinned deps, required CI checks and committed visual baselines, that is a foundation change disguised as polish. Hence the split above: the card→modal morph uses document.startViewTransition(), which is plain DOM and works today; the board→board change gets the cheap keyed crossfade instead.
The morph degrades cleanly. document.startViewTransition is feature-detected: where it is unsupported the modal simply opens as it does today. That makes it progressive enhancement rather than a dependency, and means it needs no visual-baseline changes — the start and end states are identical to the current ones, only the 300ms between them differs.
