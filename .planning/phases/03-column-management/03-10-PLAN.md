**`src/features/boards/hooks/use-reorder-columns.ts`** — `useReorderColumns({ columns })` returning
`{ reorderColumns: requestReorder, isPending, columns: derivedColumns, reorderingColumnId }`.

Hold a `ColumnOrderOverride` in local state and derive the rendered array through `model.ts`'s
`applyColumnOrderOverride`, exactly as the rename hook derives names — the override is an order rather
than a field, but the retirement mechanism is the same and stays pure and testable in `model.ts`.

On a requested move: compute the next order with `reorderColumns`, set the override with the previous
order recorded alongside it, then issue exactly ONE mutation with the moved column's own `version` and
`toReorderTargetPosition`'s value. Normalise a rejected promise with the shipped `.catch(...)` idiom
and `retry: false`.

On failure drop the override — which restores the whole board's order, not just the dragged column,
because the move shifted every column between the two indices — and raise a toast from this file's
copy table: generic `Couldn't reorder columns.` / `Try again.`, plus a `CONFLICT` entry carrying
`This board changed somewhere else.` / `Refresh to see the latest.`

Expose the in-flight mutation lock at the width `03-BACKEND-FACTS.md` § R2 justifies. If R2 observed
that shifted columns' versions ARE bumped, the lock must cover every column on the board, since the
client's props are stale for all of them the moment the reorder lands. If R2 observed that they are
not, the lock may be narrowed to the moved column alone. When R2 is inconclusive, take the whole-board
lock: it is the version-safe superset under either answer and costs nothing but a brief disabled
menu.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → Server Action | `reorderColumnAction` is callable over the wire with an arbitrary payload regardless of its compile-time signature (ADR tech/0024). |
| Server Action → deployed backend | One `PATCH` moves a column and implicitly shifts every column between the two indices. |
| optimistic client order → the versions the client still holds | A reorder may invalidate the client's `version` for columns it did not move. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-11 | Spoofing | `reorderColumnAction` | high | mitigate | `verifySession()` is the action's first statement; a missing record returns `UNAUTHENTICATED` before parsing or any upstream call. The action does not rely on the route guard having run. |
| T-03-07 | Elevation of Privilege | IDOR — reordering columns on another user's board | high | mitigate | `userId` comes only from `record.id`, never from the argument. The backend independently refuses cross-account access with `403 ACCESS_DENIED` (`02-BACKEND-FACTS.md` P7), and the shared mapping folds 403 and 404 into one `NOT_FOUND` branch so the response cannot be used to probe which ids exist. |
| T-03-06 | Tampering | forged `targetPosition` | medium | mitigate | `reorderColumnInputSchema` requires an integer with a minimum of zero, mirroring the contract's own bound and proven in plan 03-04. The client only ever computes an in-range index from its own rendered array, and `03-BACKEND-FACTS.md` § R4 records what the backend does with an out-of-range value — a clamp is added here only if the probe observed silent clamping rather than refusal. |
| T-03-04 | Tampering | optimistic-lock bypass by omitting `version` | high | mitigate | `version` is required by `reorderColumnInputSchema` and read from the RSC-supplied column, so a reorder cannot be issued as an unconditional overwrite. |
| T-03-12 | Denial of Service | a request per keystroke or per pointer move | low | mitigate | Exactly one mutation is issued per completed move; intermediate arrow steps stay inside the library. Task 3 Test 4 asserts that three arrow presses still produce one call, and the second prohibition above exists so a later change cannot quietly convert this into a per-keystroke write. |
| T-03-31 | Tampering | a second mutation fired against a version the reorder invalidated | medium | mitigate | While the reorder is in flight and until the refreshed props land, the rename and delete entries are disabled at the width `03-BACKEND-FACTS.md` § R2 justifies — the whole board when shifted columns' versions are bumped or when the probe is inconclusive, which is the version-safe superset. Without this, a rename straight after a reorder can fail with a conflict the user could not have caused and cannot interpret. |
| T-03-32 | Spoofing | a kebab click silently starting a drag | medium | mitigate | Defended twice, as the research prescribes: the drag listeners are attached only to the header handle, of which the kebab is a sibling and never a descendant, and the sensors carry an activation constraint so a stationary press is a click. | T-03-33 | Information Disclosure | reorder failure copy | medium | mitigate | The action returns bare `RESULT_STATUS` discriminants; both toast strings are constants in `use-reorder-columns.ts`. No upstream `detail` string reaches the user. |
| T-03-21 | Tampering | dropped `boardId` producing a URL with a literal placeholder | high | mitigate | Same mechanism as the other two column endpoints. Mitigated by an explicit source assertion on `params.path`, and proven against the real backend by plan 03-11's integration test. |
