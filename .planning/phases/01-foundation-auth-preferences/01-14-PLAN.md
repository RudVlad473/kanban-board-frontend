Deliver THEME-01: a signed-in user toggles light or dark, the choice persists to their account,
and the next page they load is already in the right theme.

<decisions>
**Failure feedback is an inline live-region message, not a toast.** UI-SPEC records the
theme-persistence failure UI as unresolved and recommends reverting the Switch plus a transient
toast, explicitly flagged as unconfirmed. Reverting is implemented as recommended. The toast is
not: no toast primitive exists in D-13's seven-primitive set, and pulling in a toast library here
would introduce a runtime dependency that never passed this phase's package legitimacy audit. An
inline, polite live-region message rendered beside the toggle satisfies the same requirement — the
user learns the save failed — using only what the design system already provides. Recorded here so
the deviation from UI-SPEC's recommendation is visible rather than silent.
</decisions>

  <behavior>
    - A signed-in caller reading the theme gets the value stored for the session's user.
    - A signed-in caller updating the theme to a valid value gets the updated record back and the
      value is stored.
    - Updating to the same value twice leaves the stored record identical after the second call as
      after the first, and both calls succeed.
    - An update with a value outside the two the contract allows returns 400 without calling
      upstream.
    - A caller who supplies a different user id in the query string or body still has their own
      preference updated — the supplied id is ignored entirely.
    - An unauthenticated caller is refused, and is refused by this handler's own check rather than
      by anything upstream of it.
    - An upstream failure returns a non-2xx response to the caller rather than a success.
  </behavior>
  <files>app/api/users/me/theme/route.ts, app/api/users/me/theme/route.test.ts</files>
  <action>
    Write `app/api/users/me/theme/route.ts` exporting `GET` and `PUT`.

    Both begin by calling `verifySession()` from `src/lib/dal.ts` and returning 401 when it yields
    nothing. This is the same defence-in-depth rule plan 01-13 applies to pages: the route guard
    does not run against `/api` paths at all, so this check is not redundant — it is the only one.

    The user id passed to the external contract comes exclusively from the verified session. The
    contract exposes `userId` as a query parameter with no declared auth scheme, so a handler that
    forwarded a caller-supplied id would let any signed-in user rewrite any other user's
    preference. Read nothing about identity from the request's query string, body or headers.

    `PUT` validates the body with a Zod schema constraining the theme to the contract's two allowed
    values before calling upstream, then forwards through `externalApi` and returns the updated
    record. `GET` forwards and returns the record.

    On a successful `PUT`, also write the theme cookie (Task 2's `writeThemeCookie`) so the next
    server render can resolve the scope before hydration.

    Write `app/api/users/me/theme/route.test.ts` covering the seven behaviours against the MSW node
    server. The two easiest to omit and most important to keep are the ignored-supplied-id case and
    the double-update idempotency case.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → theme BFF endpoint | The route guard does not run against API paths, so this endpoint is the only place its own access decision is made |
| caller-supplied user id → upstream contract | The contract takes the target user as a query parameter and declares no auth scheme |
| theme cookie → browser | Deliberately readable, unlike the session cookie |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-06 | Elevation of Privilege | Caller-supplied `userId` letting one signed-in user rewrite another's preference | high | mitigate | The handler derives the user id exclusively from `verifySession()` and reads no identity from the request; a test sends a different id and asserts only the session's own record changed |
| T-01-05 | Elevation of Privilege | Endpoint relying on an upstream guard that never runs for API paths | high | mitigate | Both `GET` and `PUT` call `verifySession()` themselves and return 401 when it yields nothing, asserted directly |
| T-01-03 | Tampering | Cross-site request forgery against the state-changing theme update | medium | mitigate | `SameSite=Lax` prevents the session cookie riding a cross-site request, and the endpoint is `PUT`, so the top-level-navigation exemption does not apply |
| T-01-35 | Information Disclosure | Theme cookie readable from JavaScript | low | accept | It carries a display preference, not a credential; readability is required for the pre-hydration scope resolution, and it is a separate cookie so the session's httpOnly protection is untouched |
| T-01-36 | Repudiation | A save reported as successful when it failed, leaving the user's belief and the stored state divergent | medium | mitigate | The control reverts to the stored value on failure and a live-region message states the save did not happen; the test asserts both, since either alone still misinforms |
</threat_model>
