<decisions>
**The recovery surface lives in `src/components/layout/`, not in `app/`.** CONVENTIONS' placement
rules make `app/` routing-only — it composes, it does not contain markup of its own. The fallback
is domain-agnostic app chrome shown in place of a route's content, which is exactly placement rule
4 (`components/layout/`). Both boundary files stay thin wrappers, which is also what makes them
cheap to add per future route segment.

**Copy for the boundaries is a planner decision, not a sourced one.** UI-SPEC's Copywriting
Contract has no error-boundary row — the phase predates having any error boundary. The copy chosen
below states what happened and what to do next, and deliberately says nothing about why, because
the "why" is the one thing that must not reach the screen.

**The error's `digest` may be shown; its message and stack may not.** Next.js hashes server errors
into an opaque `digest` precisely so a user can quote it without the application leaking its
internals. The thrown error's own text is never rendered — in production it can carry a database
string, an upstream URL, or a secret that ended up in an exception.

**Per ADR tech/0011, the fallback's story gets no visual-regression entry.** Baselines stay scoped
to `components/ui/` primitives; this is a layout component, so it gets a story and axe coverage and
no `visual/*.visual.spec.ts` id.
</decisions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| thrown exception → rendered page | An exception object crossing into the DOM is the classic path for internal detail to reach an untrusted viewer |
| crashed segment → surrounding session chrome | A failure inside one route must not take the authenticated shell down with it |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-41 | Information Disclosure | Boundary rendering the thrown exception's own text or stack (`app/(dashboard)/error.tsx`, `app/global-error.tsx`) | high | mitigate | Neither boundary reads anything off the error but its `digest`; a comment-stripped search over both files asserts no such property access exists, and the render test asserts the constructed error's text is absent from the output |
| T-01-42 | Denial of Service | An uncaught render failure blanking a protected route with no way forward | medium | mitigate | The segment boundary renders a recovery surface with a retry control bound to the framework's own `reset`, asserted by test |
| T-01-43 | Denial of Service | A root-layout failure falling through to the browser's default error page | medium | mitigate | `app/global-error.tsx` renders its own document with its own stylesheet import, so the fallback survives the root layout being gone |
| T-01-44 | Information Disclosure | The opaque `digest` being mistaken for sensitive data | low | accept | `digest` is a framework-computed hash of the error, not its content — displaying it is the documented way to let a user quote an incident without exposing its cause |
</threat_model>
