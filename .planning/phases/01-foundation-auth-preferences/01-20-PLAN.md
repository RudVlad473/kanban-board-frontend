the destination and gain their first direct tests in the same pass.

Output: one route declaration in the established shape, a named builder for the dynamic board path,
every call site reading from it, a CI check that keeps it that way, two real hook tests, and the
placeholder retired.
</objective>

<decisions>
**The keys of `ROUTE` do not mirror their values, and that is a deliberate, recorded deviation from
ADR tech/0012.** The ADR's stated shape has keys identical to their own string values, which works
for `DEVICE_TYPE` and `THEME` because those values are labels. A route's value is a URL path; a key
mirroring it would be path-shaped and unusable. What this plan replicates is the half that carries
the benefit and that `routes.ts` is missing: one `as const` object as the single runtime source, and
a type derived from it with the index-access idiom rather than declared separately. The file's own
doc comment must say this, so the next reader does not "fix" it back.

**The dynamic path builder is a separate export, not a member of the object.** A function stored
inside `ROUTE` would be swept into the derived type by the index access, turning `Route` from a
union of paths into a union of paths and a function. `boardDetail` therefore sits beside the object
and builds its result from `ROUTE.BOARDS`, so the prefix still has exactly one source.

**The old loose constants are removed rather than kept as aliases.** Leaving them would let two
spellings coexist indefinitely and defeat the consolidation; removing them makes the compiler
enumerate every call site, which is exactly the list this plan needs.

**Route policy stays derived, not restated.** `PROTECTED_PREFIXES` and `PUBLIC_PATHS` are built from
`ROUTE` members rather than re-typed as literals, so a path can never appear in the policy in a form
differing by a character from the path the app actually links to.

**The hook tests mock the API module rather than the network.** What is under test here is the
hook's own contract — call once, navigate on success, surface the message and stay put on failure —
not the request. Driving them through a mock server would re-test the transport the browser-mode
component tests already cover, and slowly.
</decisions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| route policy declaration → the two guard layers | Both the optimistic guard and the authoritative layout check must agree on which paths are protected; divergence opens a protected route |
| redirect destination → the browser | A destination derived from anything other than a fixed declaration is an open-redirect surface |
| failed authentication → client-side navigation | A hook that navigates on a rejected sign-in would put an unauthenticated visitor on a protected route's URL |
