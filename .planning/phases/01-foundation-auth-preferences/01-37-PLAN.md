<objective>
Move the server ring and the client ring of `src/lib/` into `src/lib/server/` and `src/lib/client/`,
move the three auth-only pure/logic modules into `features/auth/` under their prefix-free names, and
delete the three now-empty folders and every `src/lib/` orphan. This is round-4 gap closure GC-25
(server and client rings), GC-26 (`model.ts`), and GC-27 (feature-file naming). GC-28's enforcement
policy already landed in plan 01-36; GC-30's documentation is plan 01-38.

Purpose: plan 01-36 moved the pure ring and turned on the three-ring boundaries policy. This plan
moves the two coupled rings the policy exists to keep apart — the server-only, secret-holding
modules (`session.ts`, `dal.ts`, `server-client.ts`, `session-cookie.ts`) into `lib/server/`, and
the browser/React-runtime infra (`query-client.tsx`) into `lib/client/` — so their platform coupling
is finally structural. It also relocates the two auth-only pure modules that had no home outside the
old catch-all — `resolveDisplayName` becomes `features/auth/model.ts`, and the auth Zod schemas
become `features/auth/schemas.ts` — and renames the auth server-function module off its `api/auth-`
prefix to `features/auth/actions.ts`.

Output: `src/lib/server/` and `src/lib/client/` hold the two coupled rings, `features/auth/` gains
`model.ts`, `actions.ts` and `schemas.ts`, three empty folders are removed, and every importer and
the one affected Vitest glob name the new paths.
</objective>

**Reconciliation with the design doc's stale file list — the two clients and the auth wrapper are
gone, not moved.** The design doc (written before plan 01-34 was planned) lists three files that
plan 01-34 Task 2 deletes outright, so post-merge they do not exist and are NOT moved here:
`src/lib/api/bff-client.ts` (design doc: -> `lib/client/`), `src/lib/api/bff-generated-types.ts`
(design doc: -> `lib/core/api-contract/`, also covered by plan 01-36's note), and
`src/features/auth/api/auth-api.ts` (design doc GC-27: -> `features/auth/api.ts`). There is no
`api.ts` rename because there is no `auth-api.ts` to rename. Confirm each of the three is absent
before assuming this. `query-client.tsx` is the only file that moves into `lib/client/`.

**`src/lib/validation/auth-schemas.ts` is moved to `features/auth/schemas.ts` — a forced, in-spirit
addition the design doc's fixed file list omitted.** After plan 01-36 replaced the flat `lib`
boundaries element with three `lib-*` patterns (`src/lib/core/**`, `src/lib/server/**`,
`src/lib/client/**`), any file left directly under `src/lib/` in a non-ring folder matches no element
type; with `boundaries/dependencies` set to `default: "disallow"`, every `feature -> @/lib/validation/...`
import then resolves its `to` element to nothing and becomes a lint error. `auth-schemas.ts` is pure
(Zod) and, post-01-33/34, consumed only by auth (`sign-in-form.tsx`, `sign-up-form.tsx`, the auth
server functions) — exactly GC-26's category ("a pure file only ever consumed by one domain belongs
in that domain"). Moving it to `features/auth/schemas.ts` both satisfies GC-26's rule and leaves
`src/lib/` with no unmatched file. Its `zodErrorToFieldErrors` export and the schemas move together.

**Naming: `schemas.ts`, not `model.ts`.** `resolveDisplayName` is a data-derivation (a model
function) and goes in `model.ts` per GC-26. The Zod validation schemas are a distinct concern and get
their own prefix-free singular file `schemas.ts`, consistent with GC-27's "drop the redundant
feature-name prefix" (was `auth-schemas.ts`). Keeping them separate mirrors how `types.ts` is its own
per-feature file rather than being folded into another.

**The auth-actions Storybook stub, if present.** The design doc notes
`src/test-utils/auth-actions-storybook-stub.ts` exists on the 01-33 worktree branch and should be
renamed to match the renamed module. It is not on master at planning time. If it is present after the
01-33/34 merge, rename it to `actions-storybook-stub.ts` and update its internal comment to reference
`features/auth/actions.ts`; if it is absent, there is nothing to rename — do not create one.
