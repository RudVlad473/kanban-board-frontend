<objective>
Guard the protected routes twice — once optimistically before render, once authoritatively inside
the protected layout — then prove all three auth requirements end to end in a real browser.

Purpose: AUTH-03 is the requirement, but how it is built matters more than that it exists. A
historical Next.js vulnerability class made proxy-level auth checks bypassable, which is why
Next.js's own guidance treats the pre-render check as an optimisation and the Data Access Layer as
the decision. This plan implements both and tests that the second alone suffices.

Output: `proxy.ts`, a shared route declaration, the protected route group with its own session
check, a sign-out control, and Playwright specs covering AUTH-01, AUTH-02 and AUTH-03.
</objective>

    The guard reads the session cookie, verifies it through `verifySessionCookie`, then: redirects
    to `SIGN_IN_PATH` when the path matches a protected prefix and no valid session exists;

    the unauthenticated branch. `verifySessionCookie` already returns nothing for all four, so the
    guard needs no special-casing and must not add any.

    toggle arrives in plan 01-14, and leave a public landing route linking to sign in and sign up.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| unauthenticated request → protected route | The point at which access is granted or refused |
| session cookie value → trust decision | An attacker fully controls the bytes they present here |
| redirect destination → browser navigation | A destination influenced by the request is an attacker-controlled navigation |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-05 | Elevation of Privilege | Proxy-level auth check bypassed, the CVE-2025-29927 class | high | mitigate | The protected layout calls `verifySession()` itself and redirects independently; the acceptance criteria require demonstrating this by disabling the guard and confirming protected content still does not render |
| T-01-04 | Tampering | Open redirect via a request-derived redirect destination | medium | mitigate | Both destinations are constants in `src/lib/routes.ts`; the verify gate rejects any reference to query parameters or the referrer header in the guard |
| T-01-33 | Spoofing | Forged or replayed session cookie accepted | high | mitigate | Verification is delegated to `verifySessionCookie`, which rejects tampered and expired values by returning nothing; end-to-end specs exercise both cases against the running application rather than only in unit tests |
| T-01-34 | Information Disclosure | Protected content painted before the redirect resolves | medium | mitigate | The optimistic check runs pre-render; the end-to-end spec asserts the protected heading text never appears, so a flash would fail the run rather than pass unnoticed |
</threat_model>
