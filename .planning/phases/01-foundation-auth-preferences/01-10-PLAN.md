  memory (with a temp-file mirror for the life of that instance). On Vercel, each serverless
  instance has its own memory and can be recycled at any time, so an account created by signing up
  on the deployed app may not exist after a cold start, and a theme saved for it may reset. A
  seeded demo account exists precisely so sign-in and theme persistence are always demonstrable.
  Surfaced at the plan 01-15 deployment checkpoint. This is a property of having no backend, not a
  defect to code around.

  mechanism for mock startup on Vercel's function runtime — is a community pattern, not confirmed

  <name>Task 1: Resolve the contract's identity gap before the mock is written</name>
  <decision>What do `POST /signup` and `POST /signin` return, such that the BFF can learn which user just authenticated?</decision>
  <context>
    The contract has a hole that blocks THEME-01 outright. `POST /signin` documents a bare `200`
    with no response body at all. `POST /signup` documents a `200` whose body is an untyped bare
    string. But both `GET /users/me/theme` and `PUT /users/me/theme` **require** a `userId` query
    parameter, and `components.securitySchemes` is null — the contract declares no auth mechanism,
    so there is no token from which a server could infer the caller. Nothing in the contract tells
    the BFF who signed in.

    Whatever is chosen here becomes the session payload shape, the MSW handlers' response shape,
    and the input to every Route Handler in plans 01-11 and 01-14. Undoing it later means touching
    all three. Since MSW is the only backend that exists, this choice also defines the behaviour
    the real backend will eventually have to match — so it is worth recording as a contract
    clarification, not just an implementation detail.
  </context>
  <options>
    <option id="bare-id-from-both">
      <name>Both endpoints return the bare user id string</name>
      <pros>Smallest possible extension: the signup response is already documented as a bare string, and a user id is the overwhelmingly likely thing a Spring controller returns there. Signin simply returns the same. Session payload is `{ userId }`.</pros>
      <cons>Sign-in still needs a second round trip to `GET /users/me/theme` before the first render in order to know the user's saved theme, which is one more hop before the page can paint without a flash.</cons>
    </option>
    <option id="user-dto-from-signin">
      <name>Signup returns the bare user id; signin returns the full UserResponseDTO</name>
      <pros>Signin hands back `{ id, email, displayName, theme }` in one call, so the theme cookie can be written at sign-in with no extra round trip and the next server render paints in the right theme immediately. The DTO already exists in the contract, so nothing new is invented — only an undocumented response body is filled in with an existing schema.</pros>
      <cons>A slightly larger assumption about the real backend's eventual signin response than returning a bare id.</cons>
    </option>
    <option id="add-users-me">
      <name>Add a GET /users/me endpoint to the mock</name>
      <pros>Cleanest conceptually — one endpoint that answers "who am I", the way most APIs do it.</pros>
      <cons>Invents an operation the contract does not declare. The real backend would have to be changed to match, and CONVENTIONS.md's mock rule is that handlers mirror the real contract's behaviour, not extend it. Also does not solve the problem on its own, since without a token the mock has nothing to key the lookup on.</cons>
    </option>
  </options>
  <resume-signal>Select: bare-id-from-both, user-dto-from-signin, or add-users-me.</resume-signal>
</task>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → Next.js server | Same-origin only; the external contract is never addressed from the browser |
| Next.js server (BFF) → external API | The only place the external base URL is known and used |
| mock process memory → responses | The mock holds credentials and user records for the life of the instance |
| committed spec → generated code | A drifted spec silently produces types that no longer describe the real contract |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-07 | Information Disclosure | Password values flowing through mock handlers | high | mitigate | No handler logs or echoes a password on any path, asserted by a source check in the verify gate; the store keeps the password field out of every response body, which returns only the contract's `UserResponseDTO` fields |
| T-01-08 | Information Disclosure | Account enumeration through distinguishable sign-in failures | medium | mitigate | Wrong password and unknown email return an identical status and body from the mock, so the UI in plan 01-12 cannot leak the difference even accidentally |
| T-01-09 | Information Disclosure | Mock code leaking into the production client or edge bundle, or intercepting real traffic during a build | medium | mitigate | Startup confined to a Node.js runtime branch reached by dynamic import (Pitfall 5); build output checked for Node-built-in warnings; unhandled requests error rather than escaping to the network |
| T-01-10 | Spoofing | External API base URL hardcoded into source or shipped to the browser | high | mitigate | `server-client.ts` imports `server-only` so a client import fails the build; the module fails fast on a missing environment variable rather than falling back to a literal URL, and the verify gate rejects any URL literal in that file |
| T-01-29 | Tampering | Generated API types drifting from the committed contract | medium | mitigate | A CI step regenerates and fails on any diff, with no error suppression — turning ADR tech/0005's requirement into a mechanical gate |
| T-01-30 | Denial of Service | Mock store lost on a serverless cold start | low | accept | A property of having no backend, not a defect; a seeded demo account keeps sign-in and theme persistence demonstrable on any instance, and the limitation is surfaced at the plan 01-15 deployment checkpoint rather than hidden |
</threat_model>
