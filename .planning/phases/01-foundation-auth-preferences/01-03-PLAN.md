<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| local repository → public GitHub remote | First crossing into public visibility; anything committed is published |
| GitHub Actions runner → npm registry | CI resolves and executes third-party package code on a hosted runner |
| GitHub Actions workflow → repository permissions | A workflow's `GITHUB_TOKEN` scope determines what a compromised step could do |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-SC | Tampering | CI dependency install | high | mitigate | `pnpm install --frozen-lockfile` forces the runner to resolve exactly the committed `pnpm-lock.yaml` graph; a drifted or injected transitive dependency fails the install rather than executing |
| T-01-16 | Tampering | Third-party GitHub Actions (`actions/checkout`, `actions/setup-node`, `pnpm/action-setup`) | medium | accept | All three are first-party GitHub or the pnpm organisation's own action, pinned to major version tags; SHA-pinning every action is L2/L3 rigour beyond this project's configured ASVS L1 bar and is recorded here as a conscious acceptance, not an oversight |
| T-01-10 | Spoofing | Secrets in workflow logs | high | mitigate | The workflow declares no `secrets` and no `env` beyond `NEXT_TELEMETRY_DISABLED`; the Vercel deployment (plan 01-15) uses Vercel's own git integration rather than a token in this workflow |
| T-01-17 | Elevation of Privilege | Workflow write access via `GITHUB_TOKEN` | low | accept | No job in this workflow writes to the repository, publishes a package, or comments on a PR; the default token scope is unused, and narrowing `permissions:` further adds no reachable protection at this scope |
</threat_model>
