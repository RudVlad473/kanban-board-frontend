# Phase 1 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Design source coverage (read this first):** The Figma PDF export
(`kanban-task-management-web-app.pdf`, 73 pages) has exactly **one** page relevant to this
phase's design tokens — **page 1**, the "Design System" page (colors, typography, and
Interactive Elements: Button Primary L/S, Button Secondary, Button Destructive, Text Field
idle/active/error, Dropdown idle/active, Subtask Checkbox idle/hovered/completed — each shown
in a "Light Version" and "Dark Version" section). Pages 2–73 are exclusively kanban
board/task-management screens (Phase 2–4 territory) and contain **no** sign-up, sign-in, or
theme-toggle mockups — this is the public Frontend Mentor "Kanban Task Management" challenge
source file, which never included auth screens. Consequently:
- Color, typography, Button, TextField, Dropdown, and Checkbox tokens below are transcribed
  directly from page 1's text layer (`pdftotext -layout`), cross-checked against the swatch
  RGB/HSL values printed alongside each hex code.
- Sign-up, sign-in, and theme-toggle-switch **screens have no Figma reference** — their layout
  is this document's own composition from the page-1 tokens + primitives, called out explicitly
  wherever it applies rather than implied as Figma-sourced.
- IconButton, Switch, and Modal (3 of the 7 Phase 1 primitives, D-13) also have no explicit
  page-1 mockup — same caveat applies to their exact visual states.
- Radius and shadow token *values* are not printed as text anywhere in the PDF (Style
  Dictionary's `radius.tokens.json`/`shadow.tokens.json` categories are locked by D-01/D-06, but
  their px/blur values must be visually measured from the Figma vector frames, not derived from
  a text extraction). Placeholder defaults below are marked accordingly — Plan 1's
  token-authoring task should confirm exact values before finalizing.

## Spacing Scale

CONTEXT.md D-04 locks a **numeric step scale** (`space-1`...`space-12`, Tailwind's own default
numeric convention) rather than the generic named xs/sm/md/lg scale — reproduced below with the
generic role names mapped alongside for checker/planner cross-reference.

| Token (D-04) | Value | Generic role | Usage |
|--------------|-------|---------------|-------|
| `space-1` | 4px | xs | Icon-to-label gaps, checkbox tick inset |
| `space-2` | 8px | sm | Compact element spacing (checkbox-to-label gap, IconButton padding) |
| `space-4` | 16px | md | Default element spacing — form field vertical gap, Button horizontal padding, TextField internal vertical padding, Dropdown item padding |
| `space-6` | 24px | lg | Section padding — auth card internal padding, form section gaps |
| `space-8` | 32px | xl | Layout gaps — auth card top/bottom margin from viewport edge |
| `space-12` | 48px | 2xl | Major section breaks — space between the auth card and the theme-toggle footer |

Exceptions:
- **12px (`space-3`, TextField internal vertical padding / Dropdown item padding)** is a
  deliberate, justified exception to the standard 4/8/16/24/32/48/64 set. Page 1's Text Field and
  Dropdown component frames show internal vertical padding that measures to 12px, not 8px or
  16px — collapsing it onto either would visibly under- or over-pad those two primitives against
  their Figma reference. Rather than adding `space-3` to the main scale (which would give the
  phase a 4-value-plus-outlier spacing set), it is called out here as a component-specific
  exception, same treatment as the 64px case below. Use Tailwind's `px-3`/`py-3` literal (12px)
  directly on TextField/Dropdown internals; do not generalize `space-3` elsewhere.
- **3xl (64px, page-level spacing)** has no direct token — D-04's declared range stops at
  `space-12` (48px). Compose `space-12` + `space-4` (48+16=64px) where a 64px gap is needed, or
  extend the scale to `space-16` (64px) during Plan 1's token-authoring task if a dedicated token
  is preferred. Flagged as an open exception, not resolved here (D-04 didn't anticipate this
  gap).
- Icon-only touch targets (IconButton, theme-toggle Switch's tap area) use a 44×44px minimum hit
  area regardless of the visual glyph size, per standard WCAG 2.5.5 touch-target guidance — this
  is a researcher-added accessibility floor, not sourced from CONTEXT.md/the PDF.

|------|------|--------|-------------|

semantic token per text style" convention — `font-heading-xl`, `font-heading-l`, `font-heading-s`,
`font-body-l`, `font-body-m` — capped at 4 distinct sizes: 24px, 18px, 13px, 12px):

| DTCG token name | Family | Weight | Size | Line height | Extra |
|------------------|--------|--------|------|-------------|-------|
| `font-heading-xl` | Plus Jakarta Sans | Bold (700) | 24px | 30px | — |
| `font-heading-l` | Plus Jakarta Sans | Bold (700) | 18px | 23px | — |
| `font-heading-s` | Plus Jakarta Sans | Bold (700) | 12px | 15px | letter-spacing 2.4px, uppercase (used for column-style labels) |
| `font-body-l` | Plus Jakarta Sans | Medium (500) | 13px | 23px | Primary body copy, form helper text |
| `font-body-m` | Plus Jakarta Sans | Bold (700) | 12px | 15px | Compact counts/meta text |

`font-heading-m` (Bold, 15px, 19px line-height) exists in page 1's full text-layer transcription
as a 6th named style in the source system, but no Phase 1 surface (auth forms, theme toggle)
requires a 15px heading — including it here would push this phase's declared scale to 5 distinct
sizes, over the 4-size maximum. It is intentionally omitted from Phase 1's contract; a later
phase that needs a 15px heading should re-introduce it there, evaluated against that phase's own
4-size budget rather than inherited unused from this one.

[SOURCED: PDF page 1 text layer, `pdftotext -layout` — "Plus Jakarta Sans Bold 24px 30px Line" /
"...Medium 13px 23px Line" etc., transcribed verbatim per style label.]

**Phase 1 usage mapping:**
- Sign-up/sign-in form field labels ("Email", "Password", "Name") → `font-body-m` (12px Bold)
- Sign-up/sign-in form inputs, helper/error text → `font-body-l` (13px Medium)
- Auth card heading ("Sign Up" / "Sign In") → `font-heading-l` (18px Bold)
- App-level page heading (post-auth, e.g. board title bar consumed by Phase 2) → `font-heading-xl`

## Color

All values transcribed verbatim from page 1's swatch grid [SOURCED: PDF page 1 text layer —
hex + RGB + HSL triplets printed under each swatch]. Semantic role assignment below is the
researcher's mapping of the (textually unlabeled) swatches to usage roles, inferred from the
unambiguous structure of the palette itself (exactly two near-black surfaces exist for dark
mode, exactly two near-white surfaces exist for light mode) and cross-checked against the
"Light Version" / "Dark Version" component groupings shown immediately below the swatches on
the same page. This mapping is standard for this specific, widely-published design system but
was not independently re-verified by visually inspecting the PDF's vector frames this session —
flagged as MEDIUM confidence, HIGH confidence on the raw hex/RGB/HSL values themselves.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) — light mode | `#F4F7FD` (hsl(220,69%,97%)) | App background (light theme) |
| Dominant (60%) — dark mode | `#20212C` (hsl(235,16%,15%)) | App background (dark theme) |
| Secondary (30%) — light mode | `#FFFFFF` | Auth card surface, sidebar, Dropdown/Modal surface (light theme) |
| Secondary (30%) — dark mode | `#2B2C37` (hsl(235,12%,19%)) | Auth card surface, sidebar, Dropdown/Modal surface (dark theme) |
| Accent (10%) | `#635FC7` (hsl(242,48%,58%)) | Primary CTA background (Create Account / Sign In buttons), active Dropdown item indicator, focus ring, Switch "on" track, links |
| Accent hover | `#A8A4FF` (hsl(243,100%,82%)) | Primary CTA hover/active state only |
| Destructive | `#EA5555` (hsl(0,78%,63%)) | Destructive Button variant, TextField error border/text (`color-border-danger`/`color-text-danger` per D-17), inline validation error copy |
| Destructive hover | `#FF9898` (hsl(0,100%,80%)) | Destructive Button hover state only |
| Neutral text/lines — dark | `#3E3F4E` (hsl(236,11%,27%)) | Borders/dividers (dark theme) |
| Neutral text/lines — light | `#E4EBFA` (hsl(221,69%,94%)) | Borders/dividers (light theme) |
| Neutral secondary text | `#828FA3` (hsl(216,15%,57%)) | Placeholder text, disabled text, secondary/muted copy (both themes) |
| Surface — deepest dark | `#000112` (hsl(237,100%,4%)) | Reserved for the deepest-contrast dark-mode element (e.g. sidebar logo/nav item active-indicator background); not otherwise used in Phase 1's auth/theme surfaces |

Accent reserved for: **primary submit buttons on the sign-up and sign-in forms, the active/
selected item indicator inside Dropdown, focus-visible outlines on all interactive primitives,
the Switch component's "on" (checked) track color, and text links (e.g. "Already have an
account? Sign In").** Never used for body text, borders, or non-interactive decoration.

Light/dark values are consumed via the same semantic token names per D-09 (`:root` / `.dark`
scope, or `light-dark()`) — components never branch on theme in code.

**Visual hierarchy / focal point:** The auth card, centered on the dominant-surface background,
is the sole focal point of both the sign-up and sign-in screens — everything else (background,
theme-toggle footer) is deliberately quiet. Within the card, the accent-colored primary CTA
(Create Account / Sign In) is the first and strongest color/contrast draw the eye lands on after
the heading; no other element on the screen competes with it for accent color per the "Accent
reserved for" rule above.

## Copywriting Contract

Field names below are taken verbatim from the OpenAPI contract
(`.planning/local-assets/kanban-board-openapi.json`) so form/error copy matches real
request/response shapes, not placeholders.

| Element | Copy |
|---------|------|
| Primary CTA — Sign Up | **Create Account** (submits `SignupRequestDTO { displayName, email, password }`) |
| Primary CTA — Sign In | **Sign In** (submits `SigninRequestDTO { email, password }`) |
| Sign-up form field labels | Email · Name (maps to `displayName`) · Password |
| Sign-in form field labels | Email · Password |
| Auth cross-link (sign-up card) | "Already have an account? **Sign In**" |
| Auth cross-link (sign-in card) | "Don't have an account? **Create Account**" |
| Empty state heading | Not applicable this phase — Phase 1 has no list/collection UI (the boards list, the first list-shaped surface, begins Phase 2). |
| Empty state body | Not applicable this phase (see above). |
| Field-required error | **"Can't be empty"** — reuses the app's own established TextField error copy verbatim [SOURCED: PDF page 1, Text Field (Error) state, shown under both "Idle"/"Active"/"Error" state groups]. Applies to Email/Name/Password when left blank on submit. |
| Field-format error (email) | "Enter a valid email address." — client-side Zod only; the OpenAPI contract declares no server-side format constraint on `SignupRequestDTO.email`/`SigninRequestDTO.email` (no `format`/`pattern` in the schema), so this is a researcher default, not contract-derived. |
| Field-length error (password) | "Password must be at least 8 characters." — **researcher default.** The contract's `SignupRequestDTO.password` has no declared `minLength` (unlike, e.g., `SaveTaskRequestDTO.title`'s explicit `minLength: 3`/`maxLength: 32`) — the backend enforces nothing itself. 8 characters is a conventional client-side floor pending an explicit product decision; flag for confirmation before Plan 2. |
| Sign-in failure (invalid credentials) | "Invalid email or password." — **assumption**, not contract-derived. `POST /signin`'s OpenAPI response only declares a bare `200`; no documented error-response schema exists (RESEARCH.md Open Question 3). Route Handler is expected to translate a non-2xx upstream response into this copy; exact upstream status/body is unknown until the contract gap is resolved. |
| Sign-up failure (generic/duplicate email) | "We couldn't create your account. If you already have one, try signing in instead, or try again in a moment." — **assumption/fallback, not contract-exact.** `POST /signup`'s only documented response is a bare `200` returning `{ type: string }` with no schema for the email-already-registered case, so this copy cannot commit to a specific "email already in use" message. It still gives the user two concrete next steps (sign in instead / retry) rather than a dead-end "something went wrong," covering both the duplicate-email and unknown-failure triggers until the contract gap (see UI Considerations row below) is resolved. |
| Destructive confirmation | **None in Phase 1 scope.** No delete/destructive action exists in AUTH-01/02/03 or THEME-01. The app's own established destructive-confirmation pattern (`"Are you sure you want to delete the `{name}`...This action cannot be reversed."` + Delete/Cancel buttons, [SOURCED: PDF pages 2+, board/task delete-confirmation frames]) is reserved for Phase 2+ (board/column/task deletion) and should be reused verbatim there — not consumed by this phase. |
| Sign-out | "Sign Out" — not itself destructive (no data loss), no confirmation modal needed. |
| Theme toggle | No text label required — icon-only Switch (sun/moon glyphs via `lucide-react`, see Design System note on icon library). If an accessible label is needed for the Switch's `aria-label`, use "Toggle dark mode". |
| Password visibility toggle | No text label required — icon-only IconButton (eye/eye-off glyphs via `lucide-react`) inside the Password TextField. Same accessible-label pattern as the theme-toggle Switch: use a state-reflecting `aria-label` that toggles between **"Show password"** (when the field is currently masked) and **"Hide password"** (when the field is currently revealed). |

## UI Considerations

> Populated by the ui-phase UI-consideration probe (Step 9.5) and lifted by plan-phase's
> `## UI Considerations` lift rule via the identical rule as SPEC `## Edge Coverage`. Shape-rooted UI *state*
> coverage (empty / loading / error / populated / partial / overflow / zero-one-many / long-text).
> Empty-state and error-state COPY live in `## Copywriting Contract` above — this section covers
> state coverage and REFERENCES those rows rather than restating the copy (de-dup).

Applicable state considerations resolved: 4 covered, 4 backstop, 3 unresolved

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | sign-up-form, sign-in-form | ✅ covered | Unfilled state is the primitive's own default (empty TextField + placeholder text); no additional empty-state design needed beyond the primitives already specified in Design System. |
| loading | sign-up-form, sign-in-form (submit) | 🧪 backstop | Submit button enters a disabled + loading-spinner variant (Button primitive's existing `isDisabled`/loading affordance) while the BFF round-trip is in flight; no dedicated copy, needs a held-out interaction test asserting the button disables on submit. |
| loading | theme-toggle (Switch) | ✅ covered | Per Architecture Patterns (RESEARCH.md), the Switch flips instantly client-side — zero perceived latency, no loading state by design. The `PUT /users/me/theme` persistence call happens after the optimistic UI update, not before. |
| error | sign-up-form, sign-in-form (field-level) | ✅ covered | See Copywriting Contract rows "Field-required error" / "Field-format error" / "Field-length error" — TextField's built-in error/invalid visual state (D-17) renders these inline. |
| error | sign-in-form (server-level: invalid credentials) | 🧪 backstop | See Copywriting Contract "Sign-in failure" row — copy is an assumption pending the missing 401 response-shape confirmation (RESEARCH.md Open Question 3); needs an explicit test once Plan 2's Route Handler is built, not a silent pass. |
| error | sign-up-form (server-level: duplicate email/unknown failure) | ⚠ unresolved | Backend's success/error response shapes for `/signup` are undocumented beyond a bare 200 string (RESEARCH.md Open Question 3) — planner must treat the exact trigger condition and copy as an assumption until the contract gap is resolved. |
| error | theme-toggle (PUT /users/me/theme failure) | ⚠ unresolved | No documented UI for a failed theme-persistence call. Recommended behavior: revert the Switch to its prior state and surface a transient toast ("Couldn't save your theme. Try again.") — not confirmed against any source, planner-level assumption. |
| partial | sign-up-form, sign-in-form | ✅ covered | Per-field inline validation on blur/submit (React Hook Form + Zod, DEFAULTS.md C-005) — a partially-filled form shows errors only on touched/submitted fields, not the whole form at once. |
| long-text | sign-up-form (Name field), sign-in-form (Email field) | 🧪 backstop | Long input values scroll horizontally within the TextField (native input behavior) rather than wrapping/truncating — matches every other TextField instance in the design (no custom truncation shown on page 1's Text Field states); needs a visual-regression story with an intentionally long value to confirm no layout break. |
| overflow | route-guard redirect (AUTH-03) | ⚠ unresolved | No design surface exists for an "already mid-navigation, guard triggers" transitional state (e.g., a flash of protected content before redirect fires). `proxy.ts`'s optimistic check runs pre-render per RESEARCH.md Pattern 2, so this should not be visually observable — dismissed as out-of-scope for this UI-SPEC (a behavioral/architecture concern, not a visual one), but flagged since it touches AUTH-03's UI-adjacent surface. |
| long-text | auth cross-links, error banners | 🧪 backstop | Fixed short copy in this phase (see Copywriting Contract) — no dynamic/user-generated long text renders in Phase 1's auth/theme surfaces, so this category is dismissed by content-shape, not by design decision. |
