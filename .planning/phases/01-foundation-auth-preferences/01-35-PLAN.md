    Plan 01-14 (theme persistence, not yet executed) was written to persist through a Route Handler
    called by a client query mutation. This round deleted every other Route Handler in the project
    and moved auth to server functions. Nothing in GC-18 through GC-24 names the theme, and the
    carve-out record written in Task 1 scopes itself to auth mutations — so 01-14's shape is a
    genuinely open question, not something to settle by assumption while editing its file.
  </decision>
  <context>
    The theme toggle is the one mutation in this phase with optimistic behaviour: 01-14's own
    acceptance criteria require the interface to flip before the request is sent and to revert if the
    save fails. That is precisely the property `tech/0002` cited when it rejected server functions
    for the core domain — the framework's optimistic hook has no automatic rollback on failure. So
    the theme is not simply "another auth-like mutation", and moving it wholesale would cost the
    behaviour 01-14 was written to guarantee.

    Whichever option is chosen, the theme's calls inherit plan 01-32's session bridge automatically:
    they go through the same external client, so they authenticate without 01-14 doing anything. That
    dependency is unconditional and is not what is being decided here.
  </context>
  <options>
    <option id="option-a">
      <name>Leave 01-14 as written — Route Handler plus a client query mutation</name>
      <pros>Smallest change to an already-reviewed plan; the optimistic update and its revert stay exactly as specified; the query layer keeps the cache it will need in Phase 2.</pros>
      <cons>Re-creates the endpoint directory this round just emptied, for a single route; keeps the hand-written request and response shapes on both sides of a boundary that no longer exists anywhere else; leaves this phase shipping two different mutation patterns.</cons>
