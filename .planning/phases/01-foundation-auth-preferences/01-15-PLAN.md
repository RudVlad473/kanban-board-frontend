Put the application on Vercel — Preview and Production — and confirm by hand that the deployed
build actually runs against the mock, which is the one property no test in this phase can prove.

against the MSW-mocked API. RESEARCH.md's Pitfall 3 and assumption A2 both single this out as the
place the phase is most likely to be wrong: every test can pass while the deployed build fails,
because mock startup on a serverless function runtime is a community pattern rather than a
documented guarantee.

human-verified confirmation that the full flow works on the deployed URLs.

    Everything below runs against the deployed URLs from Task 1, not against localhost. The mock
    backend running inside a serverless function is the one property no test in this phase can
    prove, and it is the thing most likely to be wrong.

    1. **Sign-in page renders.** Open the Production URL. Confirm you land on the sign-in page (the
       guard should send an unauthenticated visitor there from any protected path) and that it is
       styled — correct background, a centred card, a purple primary button. An unstyled page means
       the token build did not run in the deployment.
    2. **Route guard.** Append `/boards` to the Production URL and load it directly. Confirm you end
       up on the sign-in page and that no board heading flashes on the way.
    3. **Sign-up against the mock.** Create an account with an email you have not used before.
       Confirm you land on the board list placeholder. If this hangs or returns a server error, the
       mock is not intercepting inside the deployed function — say so rather than retrying; the
       executor recorded the function logs for exactly this case.
    4. **Sign-in with the seeded demo account.** Sign out, then sign in with the demo credentials
       recorded in `01-10-SUMMARY.md`. Confirm you reach the board list.
    5. **Session survives a reload.** Press reload. Confirm you are still signed in.
    6. **Theme.** Toggle the theme. Confirm the whole page changes at once. Reload and confirm the
       page comes back in the chosen theme with no flash of the other one on first paint. Sign out,
       sign back in, and confirm the theme is still your choice.
    7. **Cookie flags.** Open devtools, Application, Cookies. Confirm the session cookie shows
       HttpOnly and Secure checked, and SameSite set to Lax. Confirm no cookie or storage entry
       anywhere contains your password.
    8. **Preview environment.** Repeat steps 1, 3 and 6 briefly against the Preview URL.
    9. **Known limitation to expect, not a defect.** An account you create on the deployed app lives
       in that server instance's memory. After a period of inactivity the instance recycles and that
       account, and any theme saved for it, may be gone — which is why the seeded demo account
       exists. If step 4 works but step 3's newly created account stops working later, that is this
       limitation, recorded in `01-10-PLAN.md`, and not a bug to file.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| repository → Vercel build and runtime | Vercel reads the repository and runs its code with the environment values it holds |
| environment variables → running functions | Secrets exist only in the platform, never in the repository |
| public internet → deployed application | The first time this application is reachable by anyone other than the developer |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-10 | Spoofing | Session secret committed or shared between environments | high | mitigate | Secrets are set per environment through the platform, never in `vercel.json` or any committed file; distinct values for Preview and Production mean a leaked preview secret cannot mint production sessions; the verify gate scans committed files for an assigned value |
| T-01-02 | Information Disclosure | Session cookie served without the secure attribute over a real HTTPS origin | high | mitigate | The cookie is written with the secure attribute; the checkpoint has the human confirm HttpOnly, Secure and SameSite in devtools against the deployed origin, which is the only place the attribute's real effect is observable |
| T-01-09 | Information Disclosure | Mock failing to intercept in the deployed function, letting the application attempt a real outbound call | medium | mitigate | The unhandled-request policy errors rather than escaping to the network; the checkpoint exercises a real sign-up on the deployed URL, and the executor is instructed to report function logs rather than work around a failure by weakening the policy |
| T-01-30 | Denial of Service | Mock state lost on a serverless recycle | low | accept | A property of having no backend; the seeded demo account keeps every flow demonstrable, and the checkpoint tells the verifier what to expect so the limitation is not mistaken for a defect |
| T-01-37 | Information Disclosure | A publicly reachable deployment of an application whose accounts are mock-only | low | accept | No real user data exists and no real backend is connected; every account is in-memory and ephemeral. Revisit before a real backend is attached |
</threat_model>
