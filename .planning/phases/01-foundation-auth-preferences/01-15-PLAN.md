<objective>
Put the application on Vercel — Preview and Production — and confirm by hand that the deployed build
reaches the real backend, which is the one property no test in this phase can prove.

Purpose: ROADMAP Success Criterion 5 asks for a live deployment with a working sign-in page. Every
local and CI check reaches the backend from a machine that already resolves it; a deployed function
reaches it from a different network, with environment values supplied by a platform rather than a
file, and this is the first time that path is exercised. Every test can pass while the deployed build
fails on a missing or wrong environment value, and the application deliberately refuses to start
without an explicitly configured base URL, so that failure is loud rather than silent.

Output: a deployed Preview and Production application, per-environment secrets, updated setup
documentation, and a human-verified confirmation that the full flow works on the deployed URLs.
</objective>

    1. **Sign-in page renders.** Open the Production URL. Confirm you land on the sign-in page (the
       guard should send an unauthenticated visitor there from any protected path) and that it is
       styled — correct background, a centred card, a purple primary button. An unstyled page means
       the token build did not run in the deployment.
    2. **Route guard.** Append `/boards` to the Production URL and load it directly. Confirm you end
       up on the sign-in page and that no board heading flashes on the way.
    3. **Sign-up against the real backend.** Create an account with an email you have not used
       before, and write the address and password down — you need them in step 4 and they are a real
       row in a shared database, not a throwaway. Confirm you land on the board list placeholder. If
       this hangs or returns a server error, the deployed function is not reaching the backend — say
       so rather than retrying; the executor recorded the function logs for exactly this case.
    4. **Sign in with the account you just created.** Sign out, then sign in with the address and
       password from step 3. Confirm you reach the board list.
    5. **Session survives a reload.** Press reload. Confirm you are still signed in.
    6. **Theme, on this account.** Toggle the theme. Confirm the whole page changes at once. Reload
       and confirm the page comes back in the chosen theme with no flash of the other one on first
       paint. Stop here on this account — do not sign out and back in yet; step 6b explains why.
    6b. **Theme across a sign-out, on a fresh account.** The account from step 3 has now used both of
       the two concurrent sessions the backend allows it, because signing out of this application
       does not release the backend's own session (step 9). Sign out, create a *second* account with
       a new address, toggle its theme, then sign out and sign back in as that second account and
       confirm the theme is still your choice. This is ROADMAP Success Criterion 4 and it needs an
       account with an unused session allowance.
    7. **Cookie flags.** Open devtools, Application, Cookies. Confirm the session cookie shows
       HttpOnly and Secure checked, and SameSite set to Lax. Confirm no cookie or storage entry
       anywhere contains your password.
    8. **Preview environment.** Against the Preview URL, briefly repeat step 1, then step 3 with a
       third new address rather than reusing either account from above, then step 6 on that third
       account.
    9. **Known limitation to expect, not a defect.** The backend allows one account two concurrent
       sessions and holds each one for three hours, and this application's sign-out cannot release
       them — the backend's own sign-out route is verified broken and recorded in
       `.planning/phases/01-foundation-auth-preferences/deferred-items.md`. So a third sign-in as the
       same account inside that window is refused with
       exactly the message a wrong password gives. If that happens, use a new address rather than
       filing it. Accounts and their saved themes are durable rows in a shared database — if
       something you created disappears, that is a real defect and worth reporting.
  </how-to-verify>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| repository → Vercel build and runtime | Vercel reads the repository and runs its code with the environment values it holds |
| environment variables → running functions | Secrets exist only in the platform, never in the repository |
| public internet → deployed application | The first time this application is reachable by anyone other than the developer |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-10 | Spoofing | Session secret committed or shared between environments | high | mitigate | Secrets are set per environment through the platform, never in `vercel.json` or any committed file; distinct values for Preview and Production mean a leaked preview secret cannot mint production sessions; the verify gate scans committed files for an assigned value |
| T-01-02 | Information Disclosure | Session cookie served without the secure attribute over a real HTTPS origin | high | mitigate | The cookie is written with the secure attribute; the checkpoint has the human confirm HttpOnly, Secure and SameSite in devtools against the deployed origin, which is the only place the attribute's real effect is observable |
| T-01-09 | Information Disclosure | A deployed environment configured with the wrong backend address, sending credentials somewhere unintended | medium | mitigate | The base URL is set per environment through the platform and never committed; `src/lib/api/server-client.ts` fails fast with no fallback, so a missing value cannot silently resolve to something else; the checkpoint exercises a real sign-up on each deployed URL and the executor reports function logs rather than adding a fallback |
| T-01-30 | Denial of Service | The two-session-per-account ceiling exhausting during verification, because this application's sign-out cannot release a backend session | medium | accept | Accepted as the recorded backend defect it is; the checkpoint script gives each leg its own account and step 9 tells the verifier to expect the refusal and use a new address rather than filing it |
| T-01-37 | Information Disclosure | A publicly reachable deployment writing to the shared non-production database, where anyone who finds the URL can create rows | medium | accept | The environment holds no real user data and is a deliberate non-production target; rows are truncated by the reset step plan 01-31 wired into CI, and the deployment is not advertised. This must be revisited before a production backend is attached — a public Production deployment pointed at a production database is a materially different decision from this one |
</threat_model>
