<objective>
Build the authentication boundary: a signed httpOnly session cookie, a Data Access Layer that is
the authoritative answer to "who is this", and the three BFF Route Handlers that create and
destroy it.

Purpose: ADR tech/0001 puts the entire session concern behind the BFF precisely so the external
contract's ambiguity never leaks into client code. Next.js's own guidance — and the
CVE-2025-29927-class bypass it exists to defend against — requires every Route Handler to
authenticate independently rather than trusting an upstream redirect.

Output: `src/lib/session.ts`, `src/lib/dal.ts`, shared Zod schemas, and the sign-up, sign-in and
sign-out Route Handlers, all tested against the MSW mock from plan 01-10.
</objective>

<task type="checkpoint:decision" gate="blocking">
  <name>Task 1: Session library selection</name>
  <decision>Which library secures the session cookie — `jose` or `iron-session`?</decision>
  <context>
    RESEARCH.md Open Question 4 records this as genuinely undecided. ADR tech/0001 chose the
    storage mechanism (an httpOnly cookie issued by the BFF) but names both libraries only as
    illustrative examples, and CONTEXT.md's decision list has no entry for it. Next.js's own
    authentication guide recommends both by name and explicitly advises against a hand-rolled
    scheme, so the choice is between these two rather than open-ended.

    The undo cost is contained: `src/lib/session.ts` is the only module that would change, and its
    three exported functions are the seam every consumer goes through. That is why this is a
    decision to make once, quickly, rather than a door to agonise over.
  </context>
  <options>
    <option id="jose">
      <name>jose — sign and verify a JWT payload</name>
      <pros>Explicit control over claims and expiry, which matters if the session later needs to carry more than an identifier; the single most-depended-on JWT library in the ecosystem; works in every Next.js runtime.</pros>
      <cons>More boilerplate — sign, verify, encode, decode and expiry handling are yours to write, and each is a place to get something subtly wrong.</cons>
    </option>
    <option id="iron-session">
      <name>iron-session — sealed, encrypted cookie session</name>
      <pros>Seal and unseal in one call each; the payload is encrypted rather than merely signed, so nothing in it is readable even if the cookie is captured; far less code to review.</pros>
      <cons>Less direct control over the token's claim structure; an extra abstraction between this code and the cookie if the session shape later grows unusual requirements.</cons>
    </option>
  </options>
  <resume-signal>Select: jose or iron-session.</resume-signal>
</task>

  <action>
    Install the library selected at Task 1, at the version RESEARCH.md records for it.

    Write `src/lib/session.ts` with `import "server-only"` first, exporting exactly three
    functions:
    - `createSession(payload)` — takes the identity shape resolved by plan 01-10's Task 1
      decision, produces a fresh signed or sealed value, and writes it to the `session` cookie via
      Next.js's cookie API with `httpOnly: true`, `secure: true`, `sameSite: "lax"`, `path: "/"`,
      and an absolute expiry seven days out. It must always mint a new value and never reuse or
      extend an incoming cookie value, so an attacker who plants a session cookie before sign-in
      does not end up holding the authenticated one.
    - `verifySessionCookie(value)` — verifies and returns the payload, or null. Every failure mode
      (absent, malformed, bad signature, expired) returns null rather than throwing, so no caller
      can accidentally treat a rejection as a transient error and proceed.
    - `deleteSession()` — clears the cookie.

    Read the secret from `SESSION_SECRET` with no literal fallback and fail fast at module load if
    it is absent. A default secret is worse than a missing one because it fails silently. Document
    the variable in `.env.example` with the generation command, and never commit a real value.

    `secure: true` unconditionally is correct for Vercel Preview and Production, which are HTTPS.
    For local `http://localhost` development, gate it on the environment rather than weakening it
    globally, and make the gate read the Node environment rather than a custom flag.

    Write `src/lib/dal.ts` with `import "server-only"` first, exporting `verifySession()`: read the
    `session` cookie, verify it, and return the identity or null. Wrap it in React's `cache` so
    repeated calls within a single server render do not re-verify. This is the authoritative check
    RESEARCH.md's Security Domain requires every Route Handler and protected Server Component to
    call for itself — the route guard added in plan 01-13 is an optimistic pre-render check only,
    never the authorisation decision.

    Write `src/lib/session.test.ts` covering the eight behaviours above. The two that matter most
    and are easiest to omit are the fresh-value-on-every-create assertion and the Set-Cookie
    attribute assertion, which is the exact test CONVENTIONS.md's auth section calls for.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → BFF Route Handler | Untrusted request bodies cross here; a request can arrive without ever passing through the form |
| BFF → external API | Credentials are forwarded once, server-side, over the typed client |
| session cookie → browser storage | The only authentication state the browser holds |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-01 | Spoofing | Session fixation — an attacker plants a session cookie before the victim signs in | high | mitigate | `createSession` always mints a new value and never reuses or extends an incoming cookie; asserted by a test comparing two consecutive creations for the same identity |
| T-01-02 | Information Disclosure | Session value readable from JavaScript, giving XSS a credential to steal | high | mitigate | httpOnly, Secure and SameSite on every Set-Cookie, asserted directly against the header — the enforcement CONVENTIONS.md's auth section asks for; nothing is written to `localStorage` or `sessionStorage` |
| T-01-03 | Tampering | Cross-site request forgery against the state-changing sign-in and sign-out endpoints | medium | mitigate | `SameSite=Lax` prevents the cookie from riding cross-site POST requests; all three endpoints are POST, so the top-level-navigation exemption that Lax grants to GET does not apply to them |
| T-01-05 | Elevation of Privilege | Trusting an upstream redirect for authorisation, the CVE-2025-29927 class of bypass | high | mitigate | `verifySession` in the DAL is the authoritative check and is called by each consumer for itself; plan 01-13's route guard is documented and implemented as an optimistic pre-render check only |
| T-01-07 | Information Disclosure | Password appearing in logs, error payloads or responses | high | mitigate | No logging call exists anywhere under `app/api/auth/`, enforced by the verify gate; validation errors carry field names and messages only; tests scan every response body for the submitted password |
| T-01-08 | Information Disclosure | Account enumeration through distinguishable sign-in failures | medium | mitigate | The two failure causes return byte-identical responses, asserted by direct comparison; the mock from plan 01-10 behaves the same way so the difference cannot leak from upstream either |
| T-01-10 | Spoofing | Session secret committed or defaulted | high | mitigate | `SESSION_SECRET` is read with no fallback and fails fast when absent; `.env.local` is git-ignored; the verify gate rejects any fallback expression in the module |
| T-01-12 | Denial of Service | Brute-force credential guessing against the sign-in endpoint | low | transfer | Rate limiting belongs to the API tier that owns the credential store; this frontend has no durable state to count attempts in and no honest way to enforce it. Recorded so the eventual backend inherits the requirement explicitly rather than by omission |
</threat_model>
