<objective>
Close GC-17: override D-16 (as GC-15's own text described it) — TextField's `isLoading` now composes
into the shared `disabled` prop exactly like Button, IconButton, Checkbox and Dropdown, instead of
the `readOnly`-based mechanism 01-16 built and 01-24/GC-15 preserved.

Purpose: a live review of every loading-state primitive found TextField as the sole outlier still
using `readOnly` (deliberately kept focusable) while every sibling primitive already composes
`disabled={isDisabled || isLoading}`. The user's explicit decision: loading should imply disabled
everywhere, including TextField. This has a direct, provable consequence for GC-15's already-merged
visual fix (`opacity-70 bg-bg-app`), which becomes CSS-unreachable the moment `isLoading` implies
native `disabled` — this plan investigates that consequence live rather than assuming it, and
reconciles it rather than silently leaving dead code behind.

Output: TextField's disabled composition unified with the rest of the primitive set, its `isBusy`
cva branch simplified to match, and both auth forms' pending-state tests updated to assert the new
behaviour.
</objective>

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-01-69 | Tampering | A field marked `isLoading` was previously only `readOnly` — still focusable/tabbable, with value-freezing enforced purely at the app level (a controlled input ignoring its own change events), not by the browser. A keyboard-only or assistive-tech interaction path that dispatches input differently than the tested `userEvent.keyboard` flow could theoretically still reach the field | low | mitigate | Native `disabled` (Task 1) removes the field from the tab order and blocks all native input dispatch at the browser level — a stronger, platform-enforced guarantee than the prior app-level convention |
