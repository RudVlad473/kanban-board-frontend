<verified_backend_facts>
Every fact below was observed directly against the live nonprod backend on 2026-08-18 during
planning, with `curl`. They are not inferences from a document — treat them as the ground truth
this plan is written against, and re-observe rather than guess if anything disagrees.

- `POST /api/signup` with a fresh email returns **201 Created**, `Location: /api/users/me`,
  `Set-Cookie: JSESSIONID=<value>; Max-Age=600; Expires=<...>; Path=/; HttpOnly; SameSite=Strict`,
  and a JSON body carrying exactly `id`, `email`, `displayName` and `theme` — the same four fields
  `SessionPayload` already declares. The current code's bare-string assumption is wrong.
- `POST /api/signin` with correct credentials returns **200**, the same session-cookie header, and
  the same four-field body.
- `POST /api/signin` with wrong credentials returns **401**, `Content-Type: application/problem+json`,
  and a body carrying `type`, `title`, `status`, `detail`, `instance` and `code: BAD_CREDENTIALS`.
- `GET /api/users/me/theme?userId=<id>` with no cookie returns **401** with `code: UNAUTHENTICATED`;
  the identical call carrying the session cookie header returns **200** and the four-field body.
- The live spec at `GET /api/docs` **still documents sign-up as a 200 with a `UserResponseDTO`**,
  still declares **no** error responses, and still has **no** `securitySchemes`. Regenerating the
  contract therefore does **not** close the gap GC-19 set out to close; the only material additions
  are the `/admin/reset` path and an environment-specific `servers` entry. This is why Task 2
  hand-authors the problem-response type rather than expecting the generator to produce one.
- The probe accounts created during planning still exist in nonprod. They are cleared by the reset
  step plan 01-31 wires into CI; no action is needed here.
