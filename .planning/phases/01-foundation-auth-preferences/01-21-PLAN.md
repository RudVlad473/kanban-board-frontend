<objective>
Close GC-05 and GC-08: extract the duplicated test scaffolding into `src/test-utils/`, and let a
test reuse a story's declared arrangement instead of restating it.

Purpose: `sign-in-form.test.tsx` and `sign-up-form.test.tsx` each hand-roll a byte-for-byte parallel
mock-worker setup with its own three lifecycle hooks, and each hand-rolls an identical provider wrap
in its render helper. Separately, no test file in this project reuses a story: every test restates
render and provider setup that a sibling stories file already declares, and the staging props those
stories declare are never asserted by anything — a human looking at Storybook is their only check.

Output: two shared helpers with real consumers, the Storybook preview annotations wired into the
browser test project, and both form tests asserting their sibling stories' staged states directly.

Both items are in one plan because they are two halves of the same question — what a component test
should not have to restate — and because they rewrite the same two files, which would make them
un-parallelisable in any case.
</objective>

<decisions>
**Two helpers with two distinct jobs, not one helper doing both.** A behavioural test that drives
the component renders it bare through `renderWithProviders`, because composing a story would wrap it
in the `AuthCard` chrome that those assertions neither need nor should be coupled to. A test that
asserts a staged prop state composes the story that already declares that staging, so the props live
in exactly one place. Both helpers therefore have real consumers, and neither is scaffolding written
for its own sake.

**`composeStories`, never `play` functions — this is a hard constraint, not a preference.** D-25
settled that interaction and keyboard assertions live exclusively in Vitest and never in Storybook,
precisely so the same assertion is not maintained in two tools. `composeStories` reuses only a
story's render setup; every assertion stays in the test file. A `play` function would reopen exactly
what D-25 closed.

**The portable-stories helpers come from the installed framework package, not from a separate testing
package.** Verified against the installed tree at plan time: `@storybook/nextjs-vite` version 10.5.7
exports `composeStories`, `composeStory` and `setProjectAnnotations` directly. The deprecated
`@storybook/test` package is not installed and must not be added.

**No global store decorator is added.** GC-05 is explicit: no client-side store exists to decorate
yet. `renderWithProviders` is written so that the future store provider has exactly one place to go,
and that is the whole of the provision made for it now.
</decisions>

<flagged_assumptions>
- **`parameters.nextjs.appDirectory` is inert in the browser test project.** The Next.js framework
  mocks that parameter relies on are installed by the Storybook Vite plugin, which the `browser`
  project does not load. Composed stories therefore get the story's args and decorators but not a
  real App Router context, so both test files keep their existing module mock of the navigation
  hooks. Removing that mock on the strength of the composed parameter would break the suite.
- **Registering the preview annotations for the browser project also brings the accessibility
  addon's own hook along.** If that surfaces a violation on a composed story, the violation is real
  and gets fixed; disabling the check to make the suite pass is not an acceptable resolution.
</flagged_assumptions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| mock server → the test page | A worker that outlives its file, or whose handlers leak between tests, makes one test's arrangement silently govern another's result |
| shared test infrastructure → application bundle | Test-only helpers must never become reachable from shipped code |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-60 | Tampering | Handler leakage between tests once the worker lifecycle is centralised — a security-relevant test such as the indistinguishable-failure-message case could pass on a neighbour's stub | medium | mitigate | The helper registers the same per-test reset both files use today, and the existing per-test handler tests are re-run unchanged as the proof |
| T-01-61 | Spoofing | A composed story silently substituting a stub for real behaviour, so a test appears to cover the component while exercising story scaffolding | medium | mitigate | Composed stories are used only for staged-state assertions; every behavioural test keeps rendering the bare component, and the division is stated in the plan's Decisions block and asserted by the last acceptance criterion |
| T-01-62 | Tampering | Shared test infrastructure becoming importable by application code | low | mitigate | Both helpers live in `src/test-utils/`, which CONVENTIONS rule 7 reserves for test-only infrastructure, and the boundaries lint rule already governs cross-layer imports |
| T-01-63 | Repudiation | Assertions migrating into Storybook play functions, splitting the record of what is actually verified across two tools | medium | mitigate | No play function is added anywhere, asserted by a repository search over both the auth feature and the primitives |
</threat_model>
