## Critical Anti-Patterns

| Pattern | Description | Severity | Prevention Mechanism |
|---------|-------------|----------|---------------------|
| Stale worktree base on unpushed master | The harness's `isolation="worktree"` forks new worktrees from `origin/HEAD`, not local HEAD. After merging wave 10's worktree locally without pushing, wave 11's executor spawned from the stale `origin/HEAD` and HALTed (exit 42, worktree_branch_check base mismatch) before doing any work. | blocking | Push `master` to `origin/master` immediately after every wave's merge completes, before dispatching the next wave's executor. Run `git rev-parse HEAD` vs `git rev-parse origin/HEAD` (or `gsd-tools query worktree.base-check`) before each dispatch if unsure. |
| Orphaned worktree directories/branches after merge | Both wave 10 and wave 11's merges (whether auto-merged by the harness or merged via `worktree.cleanup-wave`) left a `.claude/worktrees/agent-<id>/` directory and a `worktree-agent-<id>` branch behind on disk even though `git worktree list` no longer showed them registered. | advisory | After confirming a wave's commits landed on master (`git log --oneline -3`), always check `ls .claude/worktrees/` and `git branch -a \| grep agent` and clean up (`rm -rf`, `git branch -D`) as a matter of course, not only when something looks wrong. |
| Harness auto-merge is inconsistent | The Claude Code harness auto-merged wave 10's worktree back to master on its own (a `chore: merge executor worktree` commit appeared without me calling cleanup-wave). Wave 11 did NOT auto-merge — I had to call `worktree.record-agent` + `worktree.cleanup-wave` manually. | advisory | Never assume either behavior. After every executor Agent() call returns, run `git log --oneline -3` first to see whether a merge commit already exists before deciding whether to run the manual merge steps. |

**Do not proceed until the blocking row above is understood — push master to origin right after each wave's merge, before spawning the next worktree.**
