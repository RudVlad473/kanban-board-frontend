<objective>
Close GC-02: make this app's validation match the real backend's rules instead of the researcher
defaults it shipped with.

Purpose: the wave-12 forms validate a password only for a non-zero length of eight, and require a
name the backend does not require and never checks the characters of. The real rules were read
directly from the backend's own Bean Validation annotations and are recorded in
`.planning/HANDOFF.json` — they are not to be re-researched. Today a user can type a password this
app accepts and the backend refuses, and the only feedback they get is the generic
account-creation failure banner, which tells them nothing about what to change.

Output: schemas carrying the real rules, an optional name with a sensible fallback everywhere one
is displayed, both Route Handlers and the mock backend updated to match, the generated BFF contract
regenerated, and the design contract's now-superseded copy row corrected.
</objective>

<decisions>
**The rules come from the backend's source, not from its OpenAPI document.** The committed
contract declares the sign-up fields as bare strings with no constraints at all; the real rules
exist only in the backend's Java annotations, already fetched and recorded in HANDOFF.json. That is
the source of truth for this plan.

**The name is optional because the backend says so.** GC-02 records the user's resolution of this
exact question on 2026-08-16: match the backend contract rather than keeping the field required for
a future display purpose. A required field this app enforces and the server does not is a rule this
app invented.

**One fallback, in one place.** Every surface that needs a display name and might not have one
reads the same helper, rather than each call site inventing its own default. The fallback is the
part of the email before the at-sign, which is recognisably the user's own, with a plain literal as
the last resort. Exact wording was left to the planner by GC-02.

**Complexity rules gate sign-up only, never sign-in.** A returning user's stored password predates
whatever rules are current; refusing to even transmit it would lock them out of their own account
over a client-side opinion. The sign-in schema keeps its non-empty check and nothing more.

**Superseded design-contract copy is corrected, not left standing.** The UI-SPEC row for the
password message is explicitly marked a researcher default pending confirmation. Leaving a
now-known-wrong row in the design contract is how this gap was introduced in the first place.
</decisions>

<flagged_assumptions>
- **The exact set of characters the backend counts as "special" is not recorded.** HANDOFF.json
  states the requirement but not the character class. This plan treats any character that is
  neither a letter nor a digit as special — the conventional reading, and more permissive than a
  narrow punctuation list. If the backend uses a narrower set, a password this app accepts could
  still be refused upstream; the reverse (rejecting a password the backend would accept) is the
  worse failure and this choice avoids it.
- **"Letters" in the name rule is read as any Unicode letter, not as A to Z.** HANDOFF.json says
  letters and spaces without saying ASCII. Rejecting a name containing an accented character would
  be a visible, indefensible bug for a real user; accepting one the backend refuses degrades to the
  existing generic failure message.
</flagged_assumptions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser form → BFF Route Handler | Client-side validation is a courtesy; the Route Handler's own parse is the enforcement |
| BFF Route Handler → external contract | The BFF decides what reaches the backend and what the session claims about the user |
| absent user input → rendered identity | A missing name must become a chosen fallback, never an accidental leak of internal state |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-49 | Spoofing | Weak passwords accepted at account creation because this app enforced only a length floor | high | mitigate | The sign-up schema enforces the backend's full rule set — 8 to 64 characters and four character classes — and the Route Handler parses with the same schema, so a crafted request bypassing the form is rejected identically |
| T-01-50 | Tampering | Client-side-only enforcement, bypassable with a direct request to the BFF endpoint | high | mitigate | `signUpSchema` is the single schema used by both the form resolver and the Route Handler's `safeParse`; the route test asserts a rejected body produced no upstream call |
| T-01-51 | Information Disclosure | A blank or literal-undefined display name rendered in the dashboard chrome, exposing that the field was never set | low | mitigate | `resolveDisplayName` never returns an empty string, and both Route Handlers pass identities through it before a session is created |
| T-01-52 | Tampering | The generated BFF contract left stale, letting the typed client and the server's validation disagree about the request shape | medium | mitigate | `pnpm bff-api:generate` is re-run and the result committed; the task's verify asserts a re-run leaves no diff |
| T-01-53 | Denial of Service | Complexity rules leaking into sign-in and locking out accounts whose stored password predates them | medium | mitigate | `signInSchema` is left untouched and a test asserts it still accepts a short, simple password |
