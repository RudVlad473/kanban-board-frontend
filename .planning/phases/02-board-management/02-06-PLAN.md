  <action>
    Create `scripts/probe-board-backend.mjs`, a standalone Node ESM script (no test framework, not
    referenced by any Vitest or Playwright project). It resolves the backend address from
    `process.env.EXTERNAL_API_BASE_URL` and exits non-zero with an explanatory message if unset —
    no hardcoded fallback, matching ADR tech/0006. It uses global `fetch`, extracts the
    `JSESSIONID` from each sign-in response's `Set-Cookie` array via `response.headers.getSetCookie()`,
    and sends it back as a `Cookie` header on every authenticated call.

    It must perform these seven observations in order and print each result as a labelled block:

    - P1 (A1 / Open Question 1, ordering): create account A, then create three boards in sequence
      with distinguishable names ("Probe Alpha", "Probe Bravo", "Probe Charlie"), then `GET /boards`
      and print the returned array's names in order. Print whether the order is creation order,
      reverse-creation order, alphabetical, or none of those.
    - P2 (A2, id format): print all three board ids verbatim, plus whether sorting them as strings
      reproduces creation order and whether they look like UUIDv4, ULID/UUIDv7, or a numeric string.
    - P3 (A3 / Open Question 2, error shape): `PUT /boards/{id}` with a deliberately stale `version`
      (the current version minus one). Print the status code and the raw response body text.
    - P4 (name validation): `POST /boards` with an empty `name`, then with a 1000-character `name`.
      Print the status code and raw body for each — this determines whether the client Zod schema
      needs a `maxLength` the OpenAPI contract does not declare.
    - P5 (column ordering): `POST /boards/{id}/columns` three times in sequence with names "Todo",
      "Doing", "Done", then `GET /boards/{id}/full` and print each column's `name` and `position`.
      This confirms whether the backend assigns `position` by call order (the assumption behind
      ADR domain/0003's sequential-calls requirement).
    - P6 (column name validation): `POST /boards/{id}/columns` with a two-character name and with a
      thirty-three-character name. Print status and raw body for each, confirming the contract's
      declared 3-32 bounds are actually enforced.
    - P7 (ACCESS CONTROL, ASVS V4): create a second account B, then from B's session attempt
      `GET /boards/{A's boardId}/full` twice — once passing `userId=B` and once passing `userId=A`.
      Print the status code and raw body for both. Also attempt `DELETE /boards/{A's boardId}` from
      B's session with `userId=A` and print the result WITHOUT following through if it succeeds
      (report it loudly instead — a success here is a backend finding this frontend cannot fix, and
      it must be recorded, not hidden).

    Every account the script creates is throwaway and randomised per run, following
    `e2e/fixtures.ts`'s pattern. Do not reuse one account across both roles and do not sign the same
    account in more than twice — the backend caps an account at two concurrent sessions and refuses
    a third with the same 401 a wrong password produces.

    Add a header comment (at most 3 lines, per PC-05) stating the script writes real rows to the
    deployed nonprod backend and must never be added to `pnpm test`, `pnpm test:all` or CI.
  </action>
