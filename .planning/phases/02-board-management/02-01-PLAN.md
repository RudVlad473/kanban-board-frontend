## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-01 | Tampering | `isTheme` guard in `src/lib/core/theme/theme.ts` | medium | mitigate | The relocated guard keeps rejecting any value that is not exactly `THEME.LIGHT`/`THEME.DARK`, so a tampered client-written `theme` cookie still resolves to `null` rather than reaching `document.documentElement`'s class list or the backend. Task 1's unit test asserts the rejection cases explicitly. |
| T-02-02 | Spoofing | `SESSION_COOKIE_NAME` re-export in `src/lib/server/session.ts` | high | mitigate | `COOKIE.SESSION` must resolve to the byte-identical string `session`; a drift would make `proxy.ts`'s guard read a cookie that `session.create` never writes, silently opening every protected route to an unauthenticated visitor. Task 2's acceptance criteria pin the three literal values and re-run `session.test.ts` unchanged. |
| T-02-03 | Information Disclosure | `baseCookieOptions()`'s `secure` flag | high | mitigate | `secure` must stay `process.env.NODE_ENV !== "development"` — a de-duplication that accidentally inverted or hardcoded it would ship the session cookie over plain HTTP. Task 2's test asserts both branches. |
| T-02-04 | Tampering | `src/lib/core/cookies/cookie-registry.ts` reaching a client bundle | low | accept | The registry is deliberately in the pure `lib/core/` ring and carries only cookie *names* and non-secret option flags — the same values already visible in any browser's cookie inspector. No secret is centralised here. |
</threat_model>
