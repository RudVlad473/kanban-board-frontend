<objective>
Deliver BOARD-02: a signed-in user creates a board, optionally naming its initial columns, and it
appears in the sidebar immediately.

Purpose: this is the phase's most intricate flow. There is no bulk-create endpoint
(`SaveBoardRequestDTO` accepts only `name`), so creation is client-orchestrated across N+1
sequential requests with a defined partial-failure outcome (ADR domain/0003, D-03/D-04/D-05). It is
also where the boards query cache first gets written to directly rather than refetched.
Output: two Route Handler methods, the domain's Zod schemas and pure model helpers, the
orchestrating mutation hook, the create-board modal, and an end-to-end proof.
</objective>

<assumption_delta_decision>
**Detected signal:** `optional` — ROADMAP Phase 2 Success Criterion 2, "User can create a new board,
**optionally** naming its initial columns". A required→optional transition on the create-board input.

**Decision: promote.** Board creation's primary representation becomes the multi-child sequence — a
create is always "one board plus N initial columns, where N may be zero" — and the
board-with-no-columns case is demoted to the N=0 branch of that one path, not modelled as a separate
simpler operation alongside it. Concretely: `useCreateBoard`'s `mutationFn` always runs the
board-create-then-column-loop orchestration, and `toCreatableColumnNames` returning an empty array is
an ordinary input to it rather than a short-circuit around it.

**Rationale:** this matches ADR domain/0003's own framing (one parent-create call followed by one
child-create call per named item) and keeps a single code path under test, so the zero-column case
cannot silently diverge from the N-column case. Add-alongside — a separate "simple create" branch
beside the orchestrated one — was considered and rejected: it would double the paths D-04's and
D-05's distinct failure outcomes have to be correct on, for no benefit.

Advisory, non-blocking. Toggleable via `workflow.assumption_delta` in `.planning/config.json`.
</assumption_delta_decision>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `POST /api/boards` and `POST /api/boards/{boardId}/columns` | Untrusted request bodies and path segments; may carry an attacker-chosen `userId`, an oversized name, or a `boardId` belonging to someone else |
| Next.js server → external Kanban backend | Server-derived `userId` and the bridged credential cross here |
| external backend → Route Handler | Created-resource responses are untrusted input; the contract declares every field optional |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-02-42 | Elevation of Privilege | `userId` in both new write handlers | critical | mitigate | `userId` comes from `verifySession()` only. | T-02-44 | Tampering | Unvalidated request bodies reaching the upstream API | high | mitigate | Both handlers Zod-parse the body server-side before forwarding and return 400 without an upstream call on failure (ASVS V5). | T-02-45 | Denial of Service | Oversized board name forwarded upstream | medium | mitigate | The board-name schema mirrors whatever maximum 02-BACKEND-FACTS.md's P4 actually observed; if no maximum was observed, that is recorded rather than a maximum being invented, and the risk is accepted as the backend's own. |
