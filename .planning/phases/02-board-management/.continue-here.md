## Confirmed bugs found during orchestrator's own manual verification (before showing the user)

The orchestrator signed into the running dev server directly (Playwright MCP tools) and drove the checkpoint's own 7-point verification list before presenting anything to the user — this is a standing practice for UI-change checkpoints, not something this plan asked for. That inspection surfaced two real issues the executor's own automated test suite did not catch:

**BUG A — real defect, recommend fixing before sign-off.**
The sidebar's board list does NOT scroll independently of the page, contradicting the plan's own must_have: *"the list scrolls while the brand mark and pinned controls stay put."* Confirmed via `browser_evaluate`:
```
nav.scrollHeight === nav.clientHeight  // both 1078px, at both 700px and 900px viewport heights
getComputedStyle(nav).overflowY === "visible"
```
The whole page grows/scrolls instead of an internal scroll region, so the pinned theme-toggle + Hide-Sidebar controls end up below the viewport fold — reachable only by scrolling the *entire page*, not the panel. Likely fix: the list's scroll container needs `min-h-0` on its flex ancestor (so it's allowed to shrink below its content height) plus `overflow-y-auto` on itself, inside a `nav` that has a real height constraint (e.g. `h-screen` or `h-dvh`) rather than growing to content.

**BUG B — disclosed/foreseeable consequence of Option B, not a coding mistake, but should be explicitly recorded rather than silently accepted.**
At 375px viewport, `document.documentElement.scrollWidth` (426px) exceeds `clientWidth` (360px) — real horizontal page overflow with a visible scrollbar. This is the mechanical result of the fixed-300px sidebar plus content column no longer fitting mobile width, now that the mobile treatment is deferred to plan 02-11. This was NOT explicitly flagged as a consequence when Option B was chosen earlier in the session (only "desktop-shaped for two more waves" was mentioned, not literal overflow). Recommend recording this as an explicitly accepted, temporary limitation in 02-09-SUMMARY.md (resolved when 02-11 lands the real mobile treatment), not fixing it here — a real fix means building part of the mobile-overlay work this plan deliberately deferred.

**Minor, dev-only — NOT a real code bug, no action needed for shipping.**
The Next.js dev-tools indicator badge renders at bottom-left and intercepts real mouse clicks on both "Show Sidebar" (collapsed) and "Hide Sidebar" (scrolled into view) at that exact screen position. A real Playwright click times out (`element intercepts pointer events`); a JS-dispatched click on the same element (`btn.click()` via `browser_evaluate`) succeeds instantly — confirming the button's own handler is correct and this is purely a dev-tools-overlay collision that won't exist in a production build. Just a heads-up for local manual testing so it isn't mistaken for a real bug.

Screenshots of BUG A and BUG B were sent to the user via `SendUserFile` this session but were NOT committed to the repo (they were scratch files in the repo root: `02-09-desktop-short-viewport.png`, `02-09-mobile-375.png`, `02-09-desktop-expanded.png`, `02-09-desktop-collapsed.png`, `02-09-dark-mode.png`, `02-09-mobile-375.png` — check if they're still present and clean up if so, or regenerate if useful).
