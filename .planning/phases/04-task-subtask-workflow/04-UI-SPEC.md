# Phase 4 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Sources:**

1. `docs/kanban-task-management-web-app.pdf` (Frontend Mentor "Kanban Task Management Web App"
   design export, 73 pages, gitignored local-only — canonical visual system). Pages opened and
   **measured** this session: **p1** (Design System — the typography table, see the new token
   below), **p2** (empty board — the disabled `+ Add New Task`), **p4** (populated board with task
   cards, light), **p5** (View Task detail with the subtask checklist and `Current Status`, light),
   **p6** (`Add New Task`), **p7** (`Edit Task`), **p8/p9/p10** (board modals, for the shipped-copy
   parallels), **p11** (`Delete this task?` confirmation), **p15** (View Task detail, dark).
2. `src/styles/tokens.css` — the already-implemented, tested, visual-regression-baselined DTCG →
   Style Dictionary → Tailwind v4 token pipeline (plan 01-04).
3. `src/components/ui/*` and `src/features/boards/components/*` — the shipped primitives and the
   Phase 2/3 board components this phase composes against, including the **inert task card** at
   `sortable-column.tsx:88-108` that this phase makes interactive.
4. `docs/api/kanban-board-openapi.json` — the fixed backend contract (`SaveTaskRequestDTO`,
   `UpdateTaskRequestDTO`, `MoveTaskRequestDTO`, `SaveSubtaskRequestDTO`,
   `UpdateSubtaskRequestDTO`, `TaskResponseDTO`, `SubtaskResponseDTO`).

   design to this document; those are answered below as **S-01..S-09**.

**Precedence (inherited verbatim from 02-UI-SPEC.md and 03-UI-SPEC.md):** CONTEXT.md decisions
govern product/UX mechanics; the PDF governs the visual system (color, type scale, spacing,
component anatomy); `tokens.css` wins over the PDF's raw swatches wherever Phase 1's token

spacing/typography/color system — it declares the already-locked tokens as this phase's contract
and names the **one new type token** and **one new primitive** this phase is authorized to add.

## Conflicts Surfaced

These are places where the mock, an earlier UI-SPEC, the shipped code, or the backend contract
genuinely disagree. Each is resolved below, but the disagreement is recorded rather than silently
followed — per this phase's brief.

| ID | Conflict | Resolution |
|----|----------|------------|
| **C-01** | **Measurement calibration.** `tokens/radius.tokens.json` (and `CLAUDE.md`, quoting it) records "render at 600 DPI and divide by 6.25 for CSS px". 03-UI-SPEC.md instead calibrated on the column pitch, which is 1 PDF pt = 1 CSS px (÷8.333 at 600 DPI). The two differ by exactly 1.3333×. **This spec used the pt calibration and confirmed it independently:** the task-card title measures 15.1 CSS px, and PDF p1's own typography table states `Heading (M) … 15px / 19px Line`. ## Spec Decisions (this document's own calls, under CONTEXT.md's delegation)

| ID | Decision | Authorized by |
|----|----------|---------------|
| **S-01** | The `Edit Task` modal's `Save Changes` button commits **title + description only** — one call on one entity. Every subtask row in that modal saves per item, immediately. A `Subtask changes save as you make them.` hint sits under the `Subtasks` label so the split is legible instead of a trap. | D-06 ("the UI-SPEC must record it as U-01 recorded the first") |
| **S-02** | **The `Edit Task` modal has no `Status` control.** Moving a task lives in exactly two places: drag, and the detail view's `Current Status` dropdown. The mock puts a third live move control inside a modal whose primary button says `Save Changes`; with per-item saves that reads as "the move is queued", which it is not. `Add New Task` **keeps** its `Status` field — `addTaskByColumnId` is column-scoped, so the destination must be chosen at create time. | D-06 + D-10 (D-10 names only the detail view) |
| **S-03** | **Subtask add, rename and delete live in the `Edit Task` modal; completion toggle lives in the detail view.** This is exactly the mock's own split (p5 shows checkboxes, p6/p7 show editable rows with an `×`) and it keeps the detail view's rows a single unambiguous click target. Rename is **inline on the row** — the row *is* a `TextField` in that modal — committing on blur or `Enter`, not behind its own control. | CONTEXT "Claude's Discretion": *whether subtask rename is inline on the row or its own control* |
| **S-04** | **The task card's drag handle is a 44×44 `IconButton variant="ghost"` carrying `GripVertical`, pinned to the card's right edge and vertically centred** — a sibling of the card's open-detail button, never nested inside it. It is always rendered, never hover-only. Anatomy mirrors `ColumnHeader`'s handle-plus-sibling-`IconButton` shape exactly. Cost, stated: the card's text column narrows from 248px to 212px. | D-13 ("the handle's placement and affordance are a design decision that document must make") |
| **S-05** | **Deleting a subtask is the bare `×` on its `Edit Task` row — no confirm, optimistic, rollback toast.** Deleting a *task* keeps the confirm modal, mirroring `DeleteColumnConfirm` exactly. | D-09 |
| **S-06** | **Task creation has one entry point: the `+ Add New Task` button in the dashboard header**, disabled when the open board has zero columns. No per-column "add a task" affordance — the mock has none, and the modal's `Status` field already reaches every column. | Mock p2/p4; follows 03-UI-SPEC.md's refusal to ship a dead per-column control |
| **S-07** | **Inter-card gap is 20px, not the shipped 16px.** `sortable-column.tsx:89` currently renders `gap-4`; the mock measures 20.2px between card edges, twice, at 300 DPI. Corrected to `gap-5`. | Measurement; same class of correction 03-UI-SPEC made for the dot-to-caption gap |
| **S-08** | **Drop indication reuses Phase 3's treatment**: a 4px accent bar in the gap at the insertion point, drawn in the gutter rather than left to a shifted preview, with `motion-reduce:` discipline. For tasks the bar is **horizontal** (full card width, in the 20px inter-card gap) rather than vertical. | CONTEXT "Claude's Discretion": *drop-indicator and drag-preview visuals — follow the existing column-drag treatment* |
| **S-09** | **The detail modal ships no visible close control**, matching the mock and matching every shipped modal in this codebase (`Modal.Close` exists but no shipped modal renders it). Dismissal is `Esc` + backdrop, with focus returning to the originating card. | Mock p5; shipped `AddBoardModal`/`EditBoardModal` precedent |

### Font-size ceiling: 4 distinct sizes → 5 (cross-phase scale change, signed off 2026-08-28)

**This is a project-wide scale change, not a quiet one-phase addition.** It is recorded here so the
ceiling is a decision on the record rather than unstated drift, and so a later reader does not treat
the fifth size as an accident to be cleaned up.

Before this phase `tokens/typography.tokens.json` held **five tokens across four distinct sizes**
(24 / 18 / 13 / 12). Adding `heading-m` makes it **six tokens across five distinct sizes**. The
ceiling for this phase and every phase after it is **5 distinct font sizes — 24, 18, 15, 13, 12**.
A sixth distinct size would need its own recorded decision in the shape of this one.

**Authority: the mock's own design-system sheet, not this phase's convenience.** PDF page 1's
`02 Typography` block — rendered at 110 DPI and read directly during this session — defines **six**
type roles across **five** distinct sizes:

| Role         | Family            | Weight | Size | Line height | Extra         | Ported by Phase 1? |
|--------------|-------------------|--------|------|-------------|---------------|--------------------|
| Heading (XL) | Plus Jakarta Sans | Bold   | 24px | 30px        | —             | yes — `heading-xl` |
| Heading (L)  | Plus Jakarta Sans | Bold   | 18px | 23px        | —             | yes — `heading-l`  |
| Heading (M)  | Plus Jakarta Sans | Bold   | 15px | 19px        | —             | **no — the gap this phase closes** |
| Heading (S)  | Plus Jakarta Sans | Bold   | 12px | 15px        | 2.4px kerning | yes — `heading-s`  |
| Body (L)     | Plus Jakarta Sans | Medium | 13px | 23px        | —             | yes — `body-l`     |
| Body (M)     | Plus Jakarta Sans | Bold   | 12px | 15px        | —             | yes — `body-m`     |

Five distinct sizes **by design**. The project's four-size scale was therefore never a deliberate
ceiling — it is an artifact of Phase 1 porting five of the design system's six roles, because
nothing in Phases 1–3 rendered a task card and `Heading (M)` had no consumer to justify it.

**Considered and rejected: merging `heading-s` into `body-m` to stay at four distinct sizes.** The
two are byte-identical on family, weight, size and line height (Plus Jakarta Sans / 700 / 12px /
15px) and differ only in `letterSpacing: 2.4px` and `textTransform: uppercase`, so collapsing them
would hold the count at four even with `heading-m` added. **Rejected**, for two reasons: the mock
defines them as two distinct roles whose whole difference *is* the kerning and case treatment, so
merging them would contradict the design source of truth purely to satisfy a count; and `heading-s`
is already shipped and visual-regression-baselined on every column header, so the merge would force
a Phase 1 token change plus a re-baseline to buy nothing. Do not merge them.

**Sign-off.** The choice was put to the user during `/gsd-ui-phase 4` on **2026-08-28**, with the
six-role table above as the evidence, and the user chose **“Raise ceiling to 5 sizes.”** Verbatim
scope of that sign-off:

- Add `heading-m` (15px / 700 / 19px) as specified below.
- Record the ceiling move from 4 to 5 as an explicit **cross-phase** scale change, justified by the
  mock's own six-role design system — not as a quiet one-phase addition.
- Phases 01 / 02 / 03 keep their current output. **Nothing is retro-edited.**
- The shipped 12px card-title defect (**C-02**) is fixed by this.

**Falsifiable, re-runnable:** `pdftoppm -f 1 -l 1 -r 110 -png docs/kanban-task-management-web-app.pdf`
and read the `02 Typography` block. If it lists fewer than six roles, or gives `Heading (M)` a size
other than 15px at a 19px line, this decision is wrong and the ceiling returns to four.

### The one new type token this phase adds

`heading-m` — `{ fontFamily: "Plus Jakarta Sans", fontWeight: "700", fontSize: "15px",
lineHeight: "19px" }`, added to `tokens/typography.tokens.json` and asserted in both themes by
`tokens/style-dictionary.build.test.ts` alongside the existing five.

**Evidence (falsifiable, re-runnable):** PDF p1's typography table states verbatim
`Plus Jakarta Sans / Bold / 15px / 19px Line / Heading (M)`. Independently, rendering p4 at 300 DPI
(`pdftoppm -f 4 -l 4 -r 300 -x 1300 -y 480 -W 1400 -H 1200`) puts the first card's title cap-band at
y 302–348, a 46px cap height → 11.05 CSS px → 15.1px at Plus Jakarta Sans's ~0.73 cap ratio. Phase 1
generated five of the design system's six type tokens and omitted this one, because nothing in
Phases 1–3 rendered a task card for real. See **C-02** — the currently-shipped card title is 12px,
which is a defect this phase fixes, not a deliberate choice to preserve.

Weight is applied via the `[font-weight:var(--font-weight-{token})]` arbitrary-property syntax
project-wide (documented Tailwind v4 namespace-collision workaround, `button-variants.ts` comment) —
new components this phase adds must follow the same pattern, never a bare `font-bold`/`font-medium`
utility.

**Caption composition is fixed:** when the task has at least one subtask the card renders exactly
`toSubtaskSummary(task.subtasks)` → `"{N} of {M} subtasks"`, the already-shipped pure function at
`features/boards/model.ts:20`; at zero subtasks the caption is not rendered at all (Copywriting
Contract, "Card caption"). The
mock's own caption reads `substasks` — a typo in the source design that the shipped function already
corrects. Do not "restore" it.

### Completed-subtask treatment (derived, not a new token)

A completed subtask's label is `line-through` at **55% of `--color-text-primary`**
(`text-text-primary/55 line-through`). Falsifiable: `#000112` at 55% over the row's `#F4F7FD` fill
composites to `#6e707c` (4.58:1). `#FFFFFF` at 55% over the dark row's
`#20212C` composites to `#9b9ba0` (5.77:1) — dark passed at 50% too (`#8F9095`, p15's own
sample, 5.03:1), and moves only so one opacity rule covers both themes. Do not substitute
`text-text-muted` — it is a different value in each theme and misses both.
**50% was the mock-sampled value (`#7A7C87`, p5 samples `#797B87`) but fails WCAG AA at 3.87:1; 55% is the lowest whole percent that clears 4.5:1, so do not "restore" it to match the mock.**

## Interaction Notes (non-template, phase-specific)

### Task card anatomy and semantics (S-04, D-13)

The shipped inert `<li>` (`sortable-column.tsx:91-107`) becomes a two-child flex row:

```
<li class="flex items-center rounded-lg bg-bg-surface shadow-sm pl-4 pr-2 py-6">
  <button type="button" class="min-w-0 flex-1 text-left">   ← opens the detail view
    <span class="font-heading-m …">{Task Title}</span>      ← NEW heading-m, wraps
    <span class="font-body-m … text-text-muted">{N} of {M} subtasks</span>
  </button>
  <IconButton                                                ← the drag handle, a SIBLING
    variant="ghost" size="md"
    icon={<GripVertical />}
    label="Reorder {Task Title}" />
</li>
```

The card list's own `gap-4` becomes **`gap-5`** (S-07).

**The handle must not open the detail view, and the card must not initiate a drag.** This is D-13's
whole point: with `Space` and `Enter` both accepted as dnd-kit lift keys, a card that is
simultaneously an `Enter`-activated button and a drag target makes `Enter` ambiguous. The handle
therefore carries the activator ref and the listeners; the content button carries neither, and
stops pointer-event propagation so a click on it never reaches the sensor. A drag sensor activation
constraint (pointer-distance or press-delay) is still required, exactly as `ColumnHeader`'s kebab
needed one. **"A plain click on the card opens the detail view rather than starting a drag" and "a
plain click on the handle does not open the detail view" should both be explicit acceptance
criteria.**

### Task move (D-10, D-11)

- **Pointer:** press and drag the handle. `cursor-grab` at rest, `cursor-grabbing` while held.
  Dropping in a different column moves the task; dropping at a different index in the same column
  reorders it (D-11).
- **Keyboard:** focus the handle → `Space` lifts → `↑`/`↓` move within the column, `←`/`→` move
  across columns → `Space` drops → `Esc` cancels and returns the card to its original column and
  index. While lifted the handle carries `aria-roledescription="draggable task"` and
  `aria-pressed="true"`; every transition is announced through a polite `aria-live` region using
  the Copywriting Contract's announcement strings.
- **`Current Status` dropdown:** a **real write** (D-10), not a display of the current column. It
  is a second entry point into the same mutation and must produce the same optimistic apply, the
  same rollback and the same conflict handling — one hook, two callers, never two implementations.
- **Wire mapping:** one `PATCH /tasks/{taskId}/move` per *completed* move, carrying
  `{ targetColumnId, version, targetPosition }` (`targetPosition` 0-based, optional per the
  contract, always sent per D-11). Intermediate arrow-key steps are local only — a request per
  keystroke would burn versions and 409 against itself.
- **Ordering site:** tasks are ordered once, at the read, in `fetch-board-full.ts`, exactly as
  columns already are. No component sorts a task list.

### The detail view (TASK-02)

Vertical rhythm, measured on p5 at 300 DPI and expressed in declared tokens:

```
Modal.Content (shipped p-4 / md:p-6, w-[min(90vw,28rem)])
  ├─ row: <Modal.Title heading-l, wraps, pr-6>  … <IconButton kebab, 44px, shrink-0>
  ├─ 24px  (--space-6)
  ├─ description, body-l, text-text-muted        ← omitted entirely when empty
  ├─ 24px
  ├─ "Subtasks (N of M)", body-m, text-text-muted
  ├─ 16px  (--space-4)
  ├─ checklist: rows at min-h-10, px-4, py-2, gap-4, bg-bg-app, rounded-sm, 8px between rows
  ├─ 24px
  ├─ "Current Status", body-m, text-text-muted
  ├─ 8px   (--space-2)
  └─ <Dropdown> (shipped primitive; options are the board's columns, in board order)
```

The mock's own modal is 480px wide with 32px padding; this phase reuses the **shipped**
`Modal.Content` (448px, `md:p-6`) unchanged rather than re-deriving a Phase 1 primitive.
No visible close control (S-09): `Esc`, backdrop, and focus returns to the originating card.

Each checklist row is a `Checkbox` `size="sm"` (16px — measured 16.1px on p5) plus its label, with
the whole row acting as the label's click target through the shipped `Field.Label`/`peer` wiring —
**not** a `<div onClick>` wrapping a checkbox.

### The `Add New Task` and `Edit Task` modals

Both use the same field rhythm, measured on p6 at 300 DPI: **24px between field groups, 8px from
label to control**, `Modal.Footer` submit at 24px below the last control, every control 40px tall
(`h-10`) except the description (`min-h-28`, 112px).

`Add New Task` — Title, Description, Subtasks (draft rows + `+ Add New Subtask`), Status,
`Create Task`. Its subtask rows are **local drafts** until submit; creation posts the task and then
each non-blank subtask sequentially, keeping whatever succeeded (D-07).

`Edit Task` — Title, Description, Subtasks (live rows + `+ Add New Subtask`), `Save Changes`. **No
Status field** (S-02). Its subtask rows are **live entities**: an existing row commits a rename on
blur or `Enter` when its value changed and is non-empty; a newly added row stays a draft until it
first commits, then becomes live. `Save Changes` covers title + description only, and the autosave
hint says so.

Two visually identical row sets with two different save semantics is the real hazard S-01 creates.
The hint copy is the mitigation, and "editing a subtask title in Edit Task persists without
pressing Save Changes" should be an explicit acceptance criterion.

### Divergence from the mock, recorded (S-01, S-02)

PDF p7's `Edit Task` batches title, description, N versioned subtasks and a status change behind
one `Save Changes`. **This phase does not build that.** This is the second deliberate divergence in
the same direction as 03-UI-SPEC.md's **U-01** (which declined the same batching for a board's
columns), for the identical reason: each child carries its own `version`, so one button is N
independently-failing calls. The mock's *visual anatomy* for that panel is honoured in full — same
field order, same labels, same row-with-`×` shape, same full-width secondary `+ Add New Subtask`,
same primary submit. What is not carried over is the batching mechanic and the Status control.

### Toast reuse

No new toast anatomy. Task and subtask failures reuse the `Toast` established in Phase 2
(`bg-bg-surface` / `shadow-lg` / `rounded-lg` with a `--color-bg-danger` accent), and Base UI's
`Toast.Viewport` already renders its own `aria-live="polite"` region. **The keyboard-move live
announcements are a separate region from the toast viewport** — they are frequent, transient
position reports, and routing them through the toast stack would bury real errors. Carried forward
verbatim from 03-UI-SPEC.md.
