## Critical Anti-Patterns

| Pattern | Description | Severity | Prevention Mechanism |
|---------|-------------|----------|----------------------|
| Trusting a pipeline's exit code | `CI=1 playwright test … \| tail -20` returned exit 0 while the run was failing; the surviving output read "107 passed" of 316. The masked failures were only found by a positive control that corrupted one baseline and failed four tests. | blocking | Redirect to a file (`> log 2>&1`) and let the command you care about be the last thing in the script. Never append a diagnostic `echo` after it. |
| Waiting on a background run with no bound | Backgrounded commands have no timeout — a foreground one that exceeds its limit is *moved* to the background, not killed. A ~4-minute suite hung 29 minutes and was noticed only because the user asked. | blocking | State the expected duration when launching. Compare the log's mtime against `date`; no new output after ~3× expected means hung. `pgrep` showing the process alive proves nothing. |
| A detector whose silence is read as absence | Four this session: `lastIndexOf('<button')` landed on a neighbouring element and twice reported `disabled` on the wrong tag; `/disabled/` matched Tailwind's `disabled:opacity-50`; `elementFromPoint` returned null for an off-viewport column; a grep missed a backtick and reported two present rules as MISSING. One nearly caused a working fix to be reverted. | blocking | Before concluding something is absent, run the detector against a state where it MUST be present. Prefer rendering the value into the DOM (`data-probe`) over pattern-matching serialized HTML. |
| A "completed (exit code 0)" notification for a process you killed | Fired twice within the hour, reporting the killed run's exit and reading exactly like success. | advisory | Correlate the notification's task-id with what you killed; prefer the exit status the script recorded into its own log. |
| Adjusting a fail-first test instead of re-diagnosing | An e2e hydration spec passed against unfixed code because the e2e project runs `next build` and React's hydration warnings exist ONLY in the development bundle (0 occurrences in production). The spec could never fail and was deleted. | advisory | When a fail-first test passes without the fix, the diagnosis is wrong. Check the mechanism exists at that layer at all. |
| Sweeping a token family without measuring it | A first comment sweep deleted all 335 `T-NN-NN` and 20 requirement ids on the assumption they were ambiguous like `D-NN`. They are not: `T-02-51` carries its phase, and requirement ids are defined once in ROADMAP.md. It would have erased the only record of which criterion each e2e spec proves. | advisory | Measure ambiguity per family before a sweep. `D-01` is defined in nine phase docs; requirement ids in one. |
