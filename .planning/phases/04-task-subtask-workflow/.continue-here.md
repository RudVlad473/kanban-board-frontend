# BLOCKING CONSTRAINTS — Read Before Anything Else

> These are not suggestions. Each was discovered through actual failure this session.

- [ ] CONSTRAINT: **One working tree, one agent.** Three agents were dispatched concurrently
      because their *file sets* did not overlap. They still shared one git index and one
      pre-commit hook, so each hook run swept the others' half-finished work and two agents
      committed with `--no-verify` to get their own files in. Two `comments:check` failures
      reached the branch that way. Structural mitigation: give each concurrent agent its own
      `git worktree`, or dispatch strictly one at a time. Never accept `--no-verify`.
- [ ] CONSTRAINT: **A single green suite run is not evidence.** Two agents reported green and
      were wrong — one called failures "pre-existing" that were introduced by its own batch,
      another reported "three clean full runs" on a suite that failed 3 of 3 for the
      orchestrator. Structural mitigation: run `pnpm test` at least three consecutive times
      and report every exit code. A standalone file run does NOT substitute — the drag
      failures are load-dependent and vanish outside a full run.

**Do not proceed until both boxes are checked.**

## Critical Anti-Patterns

| Pattern | Description | Severity | Prevention Mechanism |
|---------|-------------|----------|---------------------|
| Concurrent agents in one checkout | File-disjoint agents still share the git index and pre-commit hook; they resolve the contention by bypassing the hook | blocking | One worktree per agent, or strict serialisation. `--no-verify` is never the answer |
| Single-run green | Load-dependent failures pass when a suite is run once or a file is run alone | blocking | Three consecutive full `pnpm test` runs; report all exit codes |
| Trusting a reviewer's findings | A Gemini 3.1 Pro review returned 4 findings; 2 were false, and the "critical" one would have replaced a working `next/cache` export in 3 Server Actions | advisory | Check every finding against `tsc`, the suite, or the running app before changing code |
| Stale LSP diagnostics | Diagnostics reported missing exports and type errors twice; `tsc --noEmit` exited 0 both times | advisory | Believe the compiler, not the editor, especially right after a rename or refactor |

<blockers>

- **RESOLVED 2026-09-01 (`252c5b3`) — the suite is green and the suspected regression was not one.**
  The `sortable-column.test.tsx` reorder-rollback failure was a **test-side race**, not a defect in
  the `useOptimistic` path `81568db` introduced. `useReorderColumns` raises the toast *inside* the
  transition's async body, but `useOptimistic` drops the optimistic order only when the transition
  **completes** — one render later. The test polled for the toast and then read the column order
  synchronously, so under full-suite load it sampled the still-reordered board.

  The proof is in the repo: `board-view.test.tsx:1423` exercises the same production path with
  `await expect.poll(getRenderedColumnNames)` and has never flaked. The hand-rolled predecessor
  called `setOverride(null)` *before* the toast, which is why the pre-refactor sample never showed
  it. Both rollback cases (ERROR and CONFLICT) now poll.

  Evidence: six consecutive full `pnpm test` runs green — 3 pre-fix (exit 0/0/0) and 3 post-fix
  (exit 0/0/0), 1659/1659 each; `tsc --noEmit`, `pnpm lint` and `pnpm comments:check` clean; and a
  negative control expecting the *reordered* order fails by timeout in both device variants, so the
  poll observes the rollback rather than trivially passing.

- **What `6f33011` DID fix:** the two `BoardView (MOBILE)` drag specs it targeted did not recur in
  any of the six runs, having previously failed 3 of 3. Confirmed.
