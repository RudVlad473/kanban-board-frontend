<objective>
Build the quality-verification layer this repo's test tiers leave a hole in, and make its two
generic instruments PASSIVE: an accessibility scan and a layout-shift score that run at the end of
every test in any spec importing this module, checked against a committed baseline, with nobody
having to remember to call them.

Purpose: the `visual` project screenshots Storybook primitives at rest (ADR tech/0008), the `e2e`
project asserts settled end states, and the `browser` Vitest project cannot reproduce a mechanism
that only exists in a real compositor. Three of this phase's own defects lived in that gap and were
each found by ad-hoc video review or a hand-written one-off observer. Opt-in tooling would have
caught none of them, because nobody knew to opt in — which is why two of the five instruments are
built here as `auto` fixtures instead.

`e2e/quality-baseline.ts` and its unit test (the comparator), `scripts/record-quality-baseline.mjs`

`e2e/quality-fixtures.e2e.spec.ts` (the wiring proof), and one new devDependency.

23 shipped specs are untouched here — 04-24 turns the gate on for them, once this plan has proved
the mechanism on a scope small enough to iterate on.

<decisions_this_plan_makes>
Six scope questions the planning was asked to answer rather than leave ambiguous. Each is
implemented below and recorded permanently by plan 04-25's ADR.

**D-A — the self-test spec is PERMANENT, not a `zz-` probe.** `e2e/quality-fixtures.e2e.spec.ts`
joins the `e2e` project for good. A fixture layer with no standing test is the exact failure this
harness exists to catch: an in-page `MutationObserver`, a `PerformanceObserver` entry type, or an
axe API that silently stops installing makes every spec that uses it pass. The repo already treats
instrument vacuity as first-class — `boards-switch.e2e.spec.ts` carries explicit "a silently
uninstalled observer must fail here, not pass everything" guards — and this spec IS those guards for
the shared layer. The `zz-` convention (`docs/review-brief.md`) still applies to one-off probes
built ON this harness, including plan 04-25's react-scan probe.

**D-B — NO new `VERIFY_STEPS` entry and NO new `ci.yml` step.** Because of D-A the spec matches the
`e2e` project's glob, so `pnpm verify`'s existing `pnpm exec playwright test --project e2e` step and
`ci.yml`'s `e2e` job already run it. `scripts/check-ci-gate-coverage.mjs` compares ci.yml `run:`
commands against `VERIFY_STEPS[].ciCommand` and nothing else, so a new `package.json` script that
never appears in ci.yml (`e2e:baseline`) needs no entry either. Adding one would land as an
`uncovered-step` or `stale-exception` violation. Asserted below: `VERIFY_STEPS` stays at 20 and
`pnpm gates:check` exits 0 unchanged.

The COST that decision accepts is restated by 04-24, not here: this plan adds four tests to the
suite, 04-24 adds per-test work to seventy-three. 04-24 measures it and puts the number in front of
a human.

**D-C — three different layout questions, three different owners.** ADR tech/0008 and tech/0011 own
the STATIC appearance of Storybook design-system components at rest — two PNGs compared, no notion
of shift at all. This plan's PASSIVE gate owns cumulative layout shift accumulated over the whole
lifetime of the real app document a test ends on, which is where a skeleton-to-content or font-swap
regression lives and which nothing in this repo currently measures. The opt-in `layoutShiftTracker`
owns shift attributable to ONE chosen interaction, read between a `start()` and a `getScore()`.
They do not overlap and none replaces another. Restated because the first version of this plan
collapsed the last two and concluded, wrongly, that page-load shift was already covered.

**D-D — `react-scan` is deferred to plan 04-25 and stays opt-in.** Unlike the five fixtures it needs
a network fetch from a CDN at fixture-setup time. Putting that in a spec that D-A makes a standing
pre-push and CI gate would add an unpkg.com dependency to every push. 04-25 adds it as an opt-in
fixture proved by a throwaway probe, never exercised by the standing spec.

**D-E — the baseline-noise decision: a committed baseline, gated on EQUALITY, recorded once.**

Turning a route-level accessibility scan on across a codebase nobody has ever scanned that way will
surface findings. Three options were considered:

| Option | Rejected/chosen because |
|---|---|
| Fail hard on any violation from day one | Turns every unrelated future push red for pre-existing debt this phase is not scoped to fix. Rejected. |
| Report-only (a console warning or a report attachment), flip to hard later | This is an instrument that passes silently and asks a human to read a log — precisely the two things this repo's own discipline and the request behind this revision both reject ("a system that works by itself and doesn't require much manual work from a human"). A deferred flip is a deferred flip forever. Rejected. |
| **Committed baseline, gate on the difference** | **Chosen.** Pre-existing findings are recorded, not fixed; anything NEW is a hard red. |

Two properties make the chosen option honest rather than a rebranded allowlist:

1. **The gate is EQUALITY, not subset.** The observed rule-id set must equal the baselined set. A
   rule that stopped firing fails too, with "re-record" named. That is a red build on an
   improvement, deliberately — it is a one-command fix, it produces a reviewable diff on a committed
   file, and it is the only thing that stops a fixed violation from staying baselined and letting the
   same regression back in silently later. This repo already lives with exactly this trade for
   `toHaveScreenshot` under ADR tech/0008.
2. **A missing entry is a hard failure, never a skip.** Adding an e2e test therefore costs one
   `pnpm e2e:baseline` run. An unbaselined test that quietly gates on nothing would be the hole the
   whole mechanism exists to close.

What would make D-E false: if re-recording became frequent enough to be noise rather than a signal —
say more than once a week outside deliberate a11y work — the equality gate is the first thing to
reconsider, in favour of gating new rules hard and reporting disappeared ones.

Explicitly NOT in scope here: fixing anything the baseline surfaces. 04-24 files the inventory as a
pending todo and changes no file under `src/` or `app/`.

**D-F — `flickerTracker` and `optimisticRoute` stay opt-in, and this is a property of the
instruments, not a shortcut.** Both are defined relative to an interaction a human has to choose:

- `flickerTracker` needs a `start()` at a specific moment (a full navigation replaces `document.body`
  and drops the observer), a `selector` naming the element whose thrashing matters, and a
  `maxMutations` budget that only means anything against a named interaction. A whole-test mutation
  count over `main` would be dominated by the sign-in and the two or three navigations every spec in
  this suite performs, and would carry no signal at any threshold.
- `optimisticRoute` must be installed before a specific write and released or elapsed before the test
  ends. Applying a blanket delay passively would slow every write in the suite and re-open, on
  seventy-three tests at once, the write-hold hazard that turned a locally-green suite red on CI on
  2026-09-05.

`axe` and `layoutShiftTracker` are automatable precisely because neither needs a chosen interaction:
"scan whatever is on screen at the end" and "how much did this document shift in total" are both
well-defined with no argument. That is the whole discriminator, and it is why two of five are passive
and three are not.
</decisions_this_plan_makes>
