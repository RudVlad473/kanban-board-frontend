## Summary

This phase's core deliverable — migrating component tests from `composeStories().run()` to direct
`render()` of composed stories, and retiring the `next/headers` mock in favor of real Playwright
e2e coverage — is executed consistently across all 17+ test files reviewed. The pattern (shallow
assertions through composed stories, deep interaction assertions through direct renders with
inherited decorators) is applied uniformly, the `next/link`/`next/navigation` shim carve-out is
correctly scoped and commented per file, and `session.test.ts`'s mock-free JWT rejection coverage
(expired, tampered-payload, malformed, credential-less, absent) is thorough with no weakened
assertion versus what the ADR/ledger claims it replaces.

The mid-phase production-bug fix (ADR tech/0026, `app/api/session/force-sign-out/route.ts`) closes
the redirect-loop bug it targets and correctly prevents an open redirect (the `redirect` query
param is validated against the closed `ROUTE` enum). However, the route handler itself has no
mechanism to verify a request actually originated from `server-client.ts`'s internal 401-triggered
redirect, as the ADR's own stated goal ("no way to reach this route without the originating 401
condition being genuine") implies it should — this is a real gap, detailed below. A related dead-code
finding follows from the same investigation: the destination-passing mechanism the ADR describes is
never actually exercised by the one production caller.

A test-coverage gap was also found in `board-list.test.tsx`: a spy is wired up for the retry
button's `router.refresh()` call but never asserted against, leaving that interaction untested.

## Warnings

### WR-01: `force-sign-out` Route Handler has no guard against being invoked directly, enabling a forced-logout CSRF

**File:** `app/api/session/force-sign-out/route.ts:19-26`
**Issue:** The handler is a plain, unauthenticated `GET` that unconditionally calls
`session.destroy()` before evaluating anything about the caller. Nothing restricts it to being
reached only via `server-client.ts`'s internal `redirect(ROUTE.FORCE_SIGN_OUT)` — any origin can
send a browser here directly (e.g. `<a href="https://app/api/session/force-sign-out">` or a
top-level `window.location` navigation from a third-party page). Because the session cookie is
`SameSite=Lax` (confirmed in `e2e/cookie-policy.e2e.spec.ts`'s COOKIE-03 assertion), Lax still
attaches the cookie on a top-level cross-site GET navigation, so this is a genuine, working
logout-CSRF: a third-party page can force a signed-in visitor's session to be destroyed with no
interaction beyond a click or an auto-navigating redirect. Separately, using `GET` — which HTTP
defines as a safe/idempotent method — to perform a destructive state change (cookie deletion) is
itself the root cause: browsers, prefetchers, and link-preview crawlers treat `GET` as
side-effect-free and may issue it speculatively. This directly contradicts the review focus this
phase's own ADR states as a design goal: "no way to reach this route without the originating 401
condition being genuine" is not actually enforced anywhere in the code — only asserted in the ADR
prose.

Impact is bounded (session destruction only — no data exposure, no privilege escalation, no
cross-account leak), which is why this is filed as a Warning rather than a Blocker, but it is a
real, reachable defect worth closing before this exception to the Route-Handler ban is trusted as
"narrow and justified."

**Fix:** Require some proof the request came from the internal flow — e.g., a short-lived,
signed one-time token minted by `server-client.ts` immediately before the `redirect()` call and
verified here before `session.destroy()` runs, or at minimum an `Origin`/`Sec-Fetch-Site` check
rejecting cross-site navigations:

```ts
export const GET = async (request: NextRequest): Promise<NextResponse> => {
    const secFetchSite = request.headers.get("sec-fetch-site");
    if (secFetchSite !== "same-origin" && secFetchSite !== "none") {
        return NextResponse.redirect(new URL(ROUTE.SIGN_IN, request.url));
    }

    await session.destroy();
    // ...
};
```

### WR-02: The `redirect` query-param / `isKnownRoute` allowlist is dead code — no caller ever supplies it

**File:** `app/api/session/force-sign-out/route.ts:11-23`, `src/lib/server/server-client.ts:98`
**Issue:** `docs/adr/tech/0026` states the Route Handler is called "passing the intended post-clear
destination," and the route handler carries a full allowlist mechanism (`isKnownRoute`) to safely
consume that destination. But the only production call site,
`redirect(ROUTE.FORCE_SIGN_OUT)` in `server-client.ts:98`, passes no query string at all — a plain
bare path with no `?redirect=...`. A repo-wide grep confirms `FORCE_SIGN_OUT` has exactly these two
occurrences (its own `ROUTE` declaration and this one bare `redirect()` call). `requestedDestination`
is therefore always `null` in every real invocation, and `isKnownRoute` always falls through to the
`ROUTE.SIGN_IN` default — functionally correct today, but the allowlist logic is currently
unreachable by any real caller, and the ADR's own description of the mechanism doesn't match the
shipped code.
**Fix:** Either wire the intended destination through from `server-client.ts` (e.g.
`redirect(\`${ROUTE.FORCE_SIGN_OUT}?redirect=${ROUTE.SIGN_IN}\`)`) to match what the ADR describes,
or simplify `route.ts` to drop the query-param/allowlist mechanism entirely and update the ADR text
to match the simpler, currently-shipped behavior (always redirect to `ROUTE.SIGN_IN`). Leaving the
mismatch as-is means the allowlist code has no real test coverage exercising its non-default branch.

### WR-03: `board-list.test.tsx`'s `mockRefresh` spy is wired but never asserted — the retry button's real behavior is untested

**File:** `src/features/boards/components/board-list.test.tsx:22-25,59-66`
**Issue:** `mockRefresh` is created via `vi.hoisted(() => vi.fn())` and injected into the
`next/navigation` shim specifically so `router.refresh()` calls can be observed
(`board-list.tsx:38` calls `router.refresh()` from the "Try again." button's `onClick`). But the
only test touching the `LoadFailed` story (`"renders the authored load-failure copy and a retry
control"`) only asserts the copy and the button's presence — it never clicks the button, and
`mockRefresh` is never referenced in any `expect(...)` call anywhere in the file. The one piece of
real interactive behavior this component owns (retrying a failed board load) has zero behavioral
coverage; only its static rendered state is verified.
**Fix:** Add a deep-interaction test that clicks the retry button and asserts `mockRefresh` was
called, mirroring the pattern used elsewhere in this same phase (e.g. `sidebar.test.tsx`'s deep
tests):

```ts
it("calls router.refresh() when Try again is clicked", async () => {
    // Arrange
    await render(<LoadFailed />);

    // Act
    await screen.getByRole("button", { name: "Try again." }).click();

    // Assert
    expect(mockRefresh).toHaveBeenCalledOnce();
});
```

## Info

### IN-01: Inconsistent naming when a locally-rendered result shadows the top-level `screen` import

**File:** `src/components/ui/button/button.test.tsx` (and the same pattern in `checkbox.test.tsx`,
`dropdown.test.tsx`, `icon-button.test.tsx`, `switch.test.tsx`, `text-field.test.tsx`,
`menu.test.tsx`, `toast.test.tsx`, `error-fallback.test.tsx`)
**Issue:** Most deep-interaction tests declare `const screen = await render(...)`, deliberately
shadowing the module-level `import { screen } from "@testing-library/react"` used by the shallow
tests in the same file, so both styles can share the same `.getByRole(...)` call shape. This is a
consistent, deliberate project pattern (not a bug on its own), but `sidebar.test.tsx` instead names
its render result `rendered`, and a handful of tests within the same files as the shadowing pattern
(e.g. `dropdown.test.tsx`'s `"marks the currently selected item..."` test) call the outer `screen`
directly after an unnamed `render(...)`. The two conventions coexisting increases the chance that a
future edit inside one of these files queries the wrong tree (the globally-mounted one vs. the
locally-rendered one) without a type error surfacing it, since both are named identically and both
expose the same `getByRole`-shaped API.
**Fix:** Pick one convention project-wide — either always shadow as `screen` (drop
`sidebar.test.tsx`'s `rendered` naming to match), or always name the local render result something
distinct (`rendered`/`view`) and stop shadowing the import. Not blocking; a review-time nit, since
every instance found during this review was internally correct.
