The plan isn't inventing a port target from memory.
- **ADR numbering collision-checked.** `docs/adr/tech/0019` through `0024` are confirmed absent in the repo today (highest existing is `0018-no-mock-server.md`), so plan 02.1-05's proposed numbering is safe.
- **The security control is threaded consistently, not just stated once.** "`userId` always session-derived, never client-supplied" and "`verifySession()` called at every entry point, not inherited from an outer check" appear in `route.ts`'s own comment (matches CVE-2025-29927 note in `layout.tsx:11-16`, both verified real) and are re-asserted in Plan 00's `load-boards.ts` spec, Plan 04's threat register, and Plan 12's comment-sweep instructions (which explicitly forbid deleting the rationale). This is real defense-in-depth being carried forward, not cargo-culted.

## Concerns

- **MEDIUM — Plan 02.1-01 Task 1 asserts `[...parsed.data].reverse()` is equivalent to the existing `newestFirst()` ordering without the plan (or my review) actually reading `newestFirst`'s implementation in `src/features/boards/hooks/use-boards.ts` / `model.ts`.** If `newestFirst` sorts by a timestamp or id rather than doing a literal array reversal, the RSC replacement silently changes board list order for real users. `.reverse()` is only correct if the upstream API's insertion order is stable and `newestFirst` is in fact just a reversal. This should be verified against the real function body before the plan is executed, not assumed from the name.
- **LOW/MEDIUM — Plan metadata inconsistency: `02.1-02-PLAN.md`'s frontmatter declares `depends_on: []`, but ROADMAP.md explicitly states "Wave 2 *(blocked on 02.1-01)*" and the plan's own content (mock-ban rule referencing 02.1-01's tracer, comment checker scanning `src/components/ui/text-field/text-field.tsx` which exists pre-phase) has no hard dependency on 02.1-01's code, yet the wave number implies one.** If any tooling schedules by `depends_on` rather than by wave number, 02.1-02 could run concurrently with or before 02.1-01. Low practical risk (02.1-02's changes are additive/advisory-only and don't touch board code), but the metadata should match the roadmap's stated ordering.
- **LOW — Plan 02.1-05's own `<objective>` text says "This plan runs in wave 2, immediately after the tracer," but its frontmatter says `wave: 3` and `depends_on: ["02.1-01", "02.1-02"]`.** This is a self-contradiction within one plan document — the ROADMAP.md wave list (which I read) also places it in Wave 3, so the frontmatter is correct and the prose is stale. Low impact since wave-based execution presumably uses the frontmatter, but it's the kind of drift that misleads a future reader trying to understand why later plans (e.g. 02.1-12, which cites ADR tech/0019 as already existing) are safe to assume the ADR landed first.
- **LOW — Citation precision in `read_first` blocks is occasionally off by a few lines** (e.g., Plan 03/04 cite `routes.ts` lines "25-31" for `boardDetail`, but the function itself is only at line 31, with 25-30 being its preceding comment; `vitest.setup.ts`'s Storybook-reasoning block is described elsewhere as "24 lines" but the whole file is 49 lines with the relevant comment at L27-42, i.e., ~16 lines not 24). None of these change what the executor needs to do, since the *content* being referenced is correctly identified, but a few `grep`-based acceptance criteria in these plans assume specific line ranges that don't quite match, which could cause a false-negative on an otherwise-correct diff.
- **MEDIUM — Plan 02.1-01 Task 1 is a very large single "tracer" task** (creates 2 files, deletes 7 files/folders including their tests, rewrites 2 components, edits `vitest.config.ts`, and requires a real-backend Playwright pass) with `estimate.confidence: low`. Bundling deletion of the whole old client-fetch stack with construction of the new RSC stack in one non-checkpointed task raises the chance that a stray import (e.g., a Storybook story or a test-utils stub still importing `use-boards`) is missed until a later plan's CI run fails for an unrelated reason. The plan's acceptance criteria (`git ls-files` greps) mitigate this reasonably well, but there's no intermediate verification point inside the task itself.

## Suggestions

- Before executing 02.1-01 Task 1, have the executor `Read` `src/features/boards/hooks/use-boards.ts`'s `newestFirst` (and `model.ts` if the sort logic lives there) and confirm `.reverse()` is behaviorally equivalent, or replace it with the actual sort key if it isn't just insertion-order reversal.
- Correct `02.1-02-PLAN.md`'s `depends_on` to `["02.1-01"]` to match the roadmap's stated wave-2 blocking relationship, even though the risk is currently low.
- Fix `02.1-05-PLAN.md`'s objective prose ("runs in wave 2") to say wave 3, matching its own frontmatter and the roadmap.
- Where `read_first` line ranges are used as grep targets in acceptance criteria, prefer content-based greps (function/symbol names) over exact line numbers, since line numbers drift as earlier plans in the same wave edit the same file.

## Risk Assessment

**LOW-MEDIUM.** The plan set is well-researched and consistently grounded in verified repository state — the core architectural shift (RSC/Server Actions, one cookie client, zod at the boundary, composed-story testing, curl seeding, blocking CI gates) is coherent, sequenced correctly, and the security controls that matter (session-derived `userId`, defense-in-depth `verifySession()`, no leaked upstream error text) are threaded through every relevant plan rather than stated once and forgotten. The concerns found are two documentation/metadata inconsistencies (unlikely to cause execution failures if wave numbers are what actually gates scheduling) and one real but narrow behavioral-equivalence assumption (`.reverse()` vs `newestFirst()`) that should be checked before Plan 00 executes, since it's the tracer every other plan depends on.
