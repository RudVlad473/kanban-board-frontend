## Issues Encountered

- **Environment resource contention (not a plan defect).** Running the full, un-scoped `pnpm test` / `pnpm build` / `pnpm lint` concurrently with other in-flight work in this sandboxed Windows worktree repeatedly triggered V8 "JavaScript heap out of memory" crashes — including in commands with no relationship to this plan's changes (`node scripts/build-tokens.mjs`, a trivial style-dictionary script, crashed at ~10MB heap usage). `tasklist` showed 40+ orphaned `node.exe`/`chrome-headless-shell.exe` processes from earlier crashed runs holding several GB of RAM, consistent with concurrent wave-6 sibling worktree agents also running heavy Vitest Browser Mode / Storybook suites. Re-running the same commands sequentially, with `--no-file-parallelism` where applicable, always completed cleanly once contention eased: `pnpm exec tsc --noEmit` (exit 0), `pnpm exec eslint .` (0 errors), `pnpm exec prettier --check .` (only 2 pre-existing, untouched files flagged), `pnpm build` with temporary `SESSION_SECRET`/`EXTERNAL_API_BASE_URL` (exit 0, matching `01-32-SUMMARY.md`'s documented precedent for this pre-existing env-var gap), and `pnpm test --no-file-parallelism` (56/56 test files, 569/569 tests, exit 0). Comment-only edits cannot cause a heap OOM; this is infra contention, not a regression.

This exact constraint is already documented in plans 02.1-01, 02.1-04, and 02.1-10's summaries as a known sandbox limitation, not something this plan can resolve. `--list` confirms the 5 AUTH-03 tests still resolve cleanly (no import/syntax breakage). The change to the guard files is comment-only, so the guard's actual redirect behavior is unaffected; the literal live-backend run is deferred to CI/a human environment with the token, per this phase's established pattern.
