# Phase 02.1 Plan 06: Server Action Real-Backend Test Rewrite Summary

**Rewrote sign-up/sign-in/sign-out/update-theme Server Action tests to exercise the real deployed
nonprod backend, removing 23 module mocks of this project's own code and leaving only two
documented next/headers and next/navigation framework shims.**

## Performance

- **Duration:** ~40 min
- **Started:** 2026-08-21T12:45:00Z (approx)
- **Completed:** 2026-08-21T13:23:00Z
- **Tasks:** 3
- **Files modified:** 8 (4 created, 4 deleted)

## Accomplishments

- `sign-up.integration.test.ts` proves a well-formed sign-up against the real backend: a JWT (not
  plaintext) session cookie, the real theme-cookie write, schema-rejection with no upstream call,
  the backend's own duplicate-account mapping, and the board-list redirect — via the real
  (unmocked) `externalApi`, `session`, and `themeCookie`.
- `sign-in.integration.test.ts` proves the same shape for sign-in: session cookie on real
  credentials, theme cookie read back from the account's own stored preference,
  `PROBLEM_CODE.BAD_CREDENTIALS` on a wrong password with no session cookie written, and
  schema-rejection with no upstream call.
- `sign-out.integration.test.ts` proves sign-out clears both the session and theme cookies and
  redirects to sign-in, whether a real session was staged first or none exists at all — matching
  `sign-out.ts`'s own behavior of never calling upstream.
- `update-theme.integration.test.ts` proves theme persistence by reading the value back from the
  real backend (`externalApi.GET`) instead of asserting a mock call, proves the
  no-session/invalid-value branches leave the stored theme unchanged, and adds a two-real-account
  test proving `updateThemeAction`'s `userId` is always session-derived, never caller-suppliable
  (T-02.1-20's Spoofing control — unprovable while `verifySession` was mocked).
- All four rewritten files are collected by the Vitest `node` project's existing
  `src/**/*.integration.test.ts` glob with no `vitest.config.ts` change needed (confirmed by
  running each file directly under `--project node`).
- The four superseded `*.unit.test.ts` files (23 total `vi.mock`/`vi.spyOn` calls across them) are
  deleted.

## Decisions Made

- **`no-restricted-properties`, not the plan's literal `no-restricted-syntax`, for shim-mock
  disable directives.** 02.1-02 wired D-04/D-19's mock ban as `no-restricted-properties`
  (`eslint.config.mjs` section 8d-2) because a second `no-restricted-syntax` block would have
  silently clobbered section 8d's existing selectors for every `.ts`/`.tsx` file (that exact
  bug is documented in 02.1-02-SUMMARY.md's own Deviations). `no-restricted-syntax`'s actual
  selectors (`TSImportType`, 2+-param functions, raw `<a>`) never match a `vi.mock(...)` call
  expression, so following the plan's literal text would have left every one of these 7 shim
  mocks carrying an unused, silently-stripped-on-commit directive — reproducing 02.1-01's
  already-documented "directive stripped by lint-staged" gap, and directly violating this same
  plan's own `<verification>` requirement (`grep -c "Unused eslint-disable directive"` prints
  `0`). Verified after committing: `pnpm lint` (full repo) shows 0 unused-directive warnings, and
  the directives survived the pre-commit `eslint --fix` pass intact (confirmed via `git show` on
  the committed files).
- **Raw literal upstream paths instead of `EXTERNAL_PATH.SIGN_UP`/`EXTERNAL_PATH.USER_THEME`.**
  The plan's read_first/action text references these as existing "post-02.1-04," but 02.1-04 is a
  parallel sibling plan in this wave (not a listed `depends_on`), so its `EXTERNAL_PATH` additions
  are not present in this isolated worktree. Used `"/signup"`, `"/signin"`, `"/users/me/theme"` —
  the exact literals `sign-up.ts`/`sign-in.ts`/`update-theme.ts`/`server-client.integration.test.ts`
  already use today.
- **No `createSessionRecord` factory usage across any of the 4 files.** Every test that needs a
  session stages one from a real, freshly signed-up account via `session.create(...)`, because
  every assertion in these files proves an outcome by reading a real value back from the backend
  (a theme, a `PROBLEM_CODE`, a redirect after a real upstream 401) — a synthetic factory-built
  session with a fabricated `jsessionId` cannot be read back meaningfully. The plan's `must_haves`
  key_link for `createSessionRecord` applies where a session must be staged with no real backend
  correlation needed; no test in this plan's final shape has that shape.

## TDD Gate Compliance

All 3 tasks carry `tdd="true"` in the plan frontmatter, but no task in this plan modifies the
Server Action implementation under test (`sign-up.ts`/`sign-in.ts`/`sign-out.ts`/
`update-theme.ts` are unchanged) — the work is a test-suite rewrite against already-correct,
already-shipped production code, not new feature development. There is no RED phase (a test that
fails because a behavior doesn't exist yet) or GREEN phase (implementation added to make it pass)
to separate into distinct commits: the "behavior" each test proves already exists and already
works. Each task is therefore a single `test(...)` commit rather than a RED/GREEN/REFACTOR
sequence. This mirrors how a pure test-only change is classified per this plan's own commit-type
table (`test` — "Test-only changes").
