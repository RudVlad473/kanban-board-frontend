<objective>
Rewrite the four Server Action test files so they exercise real actions against the real deployed
backend instead of mocking `externalApi`, `verifySession` and `themeCookie`.

Purpose: these four files carry 23 of the repository's module mocks — every one of them a
business-logic double D-04 bans outright. They currently prove that the action calls a mock with
certain arguments, not that the action works. ADR tech/0018 already established that this project
runs no fake HTTP layer; D-04 closes the same gap one level up, at module doubles.

Output: four `*.integration.test.ts` files in the Vitest `node` project, each creating its own
randomised throwaway account against the real backend, with the only surviving mocks being the two
documented framework shims.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → Server Action | A Server Action is invokable over the wire with an arbitrary payload regardless of what TypeScript claims about its caller |
| test suite → shared nonprod backend | Every test in this plan creates real, permanent accounts on a backend shared with CI and other developers |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02.1-19 | Tampering | Server Action payload validation | high | mitigate | Each rewritten file keeps a test that sends a schema-violating payload and asserts the action rejects it *and* performs no upstream write — with the mocks gone, that assertion now exercises the real `.safeParse()` guard rather than a stubbed one. |
| T-02.1-20 | Spoofing | session-derived `userId` in `updateThemeAction` | high | mitigate | Task 3's two-account test proves account B's data is untouched when account A's session is active. This control was unprovable while `verifySession` was mocked. |
| T-02.1-21 | Information Disclosure | test-created accounts on shared nonprod | medium | accept | Every test mints a randomised throwaway email with a non-production password; the accounts hold no real data and CI's post-suite `/admin/reset` step plus `e2e/global-setup.ts`'s precondition clear them. Accepted — this is the standing trade-off ADR tech/0018 already made. |
| T-02.1-22 | Denial of Service | two-concurrent-sessions-per-account cap | medium | mitigate | Each test creates its own account and performs at most one sign-in through the action under test; the plan states the budget rule explicitly per task because exceeding it surfaces as an indistinguishable 401, not as a clear failure. |
| T-02.1-SC | Tampering | npm/pip/cargo installs | high | mitigate | No packages installed by this plan. |
</threat_model>
