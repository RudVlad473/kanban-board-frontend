## Decisions Made

- **0020's Enforcement documents the actual shipped mechanism, not the plan's literal wording.**
  The plan's Task 2 action text says "Enforcement: the no-restricted-syntax selectors in
  eslint.config.mjs," but `02.1-02-SUMMARY.md` records that a second `no-restricted-syntax` block
  was tried first and reverted — ESLint flat config replaces (not merges) a rule's config per
  matching file, so it would have silently dropped this project's pre-existing raw-`<a>`/
  positional-arg/`TSImportType` selectors for every `.ts`/`.tsx` file. The actual shipped rule is
  `no-restricted-properties` (`eslint.config.mjs` section 8d-2). `0020`'s Enforcement line names
  `no-restricted-properties` correctly; the ADR's carve-out text also cites the pre-existing,
  unrelated `no-restricted-syntax` rule (the one already gating `sidebar.test.tsx`'s `next/link`
  raw-`<a>` shim comment) to satisfy the D-19 shim-directive requirement, which is accurate and
  distinct from the mock-ban mechanism. This follows this plan's own `read_first` instruction: "so
  the ADR documents shipped code rather than intent."
- **`vitest.config.ts`/`package.json` confirmed the "node" Vitest project name and
  `src/**/*.integration.test.ts` glob** before writing the new CONVENTIONS.md test-location row,
  rather than trusting the plan text's literal row wording unverified.

### Accepted, Not Auto-fixed

**1. ADR tech/0024's Enforcement has no automated command — a genuine gap against the plan's
`must_haves` key_link.**
- **Found during:** Task 3, drafting `0024-boundary-schema-validation.md`.
- **Issue:** The plan's frontmatter `must_haves.key_links` states "Every new ADR's Enforcement
  statement names a real command ... rather than 'code review'." `0024` (D-12, zod boundary
  validation) has no automated check anywhere in this codebase for "always `.safeParse()`, never
  `.parse()`" — no script, no ESLint rule. `eslint.config.mjs` was grepped for `safeParse`/`.parse(`
  and found nothing.
- **Why not auto-fixed:** Building a new enforcement mechanism (an ESLint rule or script banning
  direct `.parse()` calls) would require touching `eslint.config.mjs` or adding a file under
  `scripts/` — both outside this plan's declared `files_modified` (ADRs + `CONVENTIONS.md` only)
  and outside its `<objective>` (documentation, not new tooling). Task 3's own action text for
  `0024` also specifies no `Enforcement:` bullet, unlike `0023`'s explicit "Mechanism:" instruction
  — this asymmetry in the plan's own text suggests `0024`'s enforcement was intentionally left as
  code review, with the `must_haves` key_link's three named examples (`handlers:check`,
  `comments:check`, the `no-restricted-syntax` rule) covering `0019`/`0023`/`0020` specifically,
  not all six ADRs uniformly.
- **Current state:** `0024`'s Enforcement line reads "code review — no automated check currently
  confirms every DTO consumer calls `.safeParse()` rather than casting directly; a direct cast ...
  is a review-blocking gap." Honest and accurate to what exists.
- **Follow-up:** A future plan (or `02.1-15`'s retrofit sweep) could add an ESLint
  `no-restricted-syntax`/custom rule banning `.parse(` on a zod schema object, mirroring the
  `no-restricted-properties` pattern `02.1-02` already used for `vi.mock`/`vi.spyOn` — not scoped
  to this documentation-only plan.
