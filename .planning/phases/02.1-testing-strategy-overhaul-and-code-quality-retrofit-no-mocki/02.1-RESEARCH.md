## Summary

This phase has two intertwined but separately-verifiable halves. The **data-fetching architecture
half** (D-01/D-02/D-03) is well-supported by an **official Next.js documentation page that did not
exist when ADR tech/0002 was written** — `docs/01-app/02-guides/client-side-data-fetching/
tanstack-query.mdx` — which shows the exact combination this phase needs: RSC-rendered reads passed
as props, a Client Component `useMutation` wrapping a Server Action as `mutationFn` for optimistic
`onMutate`/`onError`, and the Server Action itself calling Next.js's cache-invalidation primitives
to force fresh data on the next render. Next.js 16 (this project's pinned version) also introduces
`refresh()` from `next/cache` — a Server-Action-only primitive purpose-built for "update a sibling
UI element after a mutation," which is a better fit than `revalidatePath` for this app's persistent
`Sidebar`, because **`(dashboard)/layout.tsx` does not re-render on ordinary navigation** (official,
confirmed Next.js behavior) — a fact this repo's actual composition (`DashboardLayout` → `<Sidebar
/>`) makes directly load-bearing, not theoretical.

The **testing-policy half** (D-04/D-07/D-08/D-09) turns out to be *less* net-new work than
CONTEXT.md's framing suggests, once the actual code is read. `vitest.setup.ts` **already wires
Storybook's portable-stories mechanism** (`setProjectAnnotations`, explicitly commented "the
portable-stories wiring GC-08 calls for") into the "browser" Vitest project — nobody has used it
yet (`composeStories` appears nowhere outside `node_modules`), but D-08's plumbing is done, only the
`.test.tsx` files themselves are missing. Similarly, `use-boards.unit.test.ts` **already** uses RTL's
`renderHook` in the jsdom "unit" project — D-09 is structurally satisfied for that one hook; its
only violation is the `vi.mock` on `boards-api` (a D-04 problem, not a D-09 problem), which will
resolve itself once the hook has a real Route Handler-free path to call against the seeded backend.

**Primary recommendation:** Build the RSC read path as a straight port of the already-proven
`useThemePreference` shape (RSC passes an `initial*` prop → Client Component seeds local `useState`
→ `useMutation({ mutationFn: serverAction })` does manual optimistic apply + manual rollback in
`onError`/`onSuccess`) rather than the heavier `HydrationBoundary`/`dehydrate` TanStack Query SSR
pattern — this repo has already built and shipped the lighter pattern once, it fits a
single-consumer list exactly like `theme`, and it avoids introducing a second SSR-hydration
mechanism into a codebase that has never needed one.

A reader can trace the primary use case end to end: `DashboardLayout` fetches and validates once

### Pattern 1: RSC read + Client Component optimistic write (recommended primary pattern)

**What:** A persistent Server Component (`DashboardLayout`) fetches once per request-that-actually-
hits-it, validates with zod, and passes plain props to a Client Component. The Client Component
seeds its own `useState` from those props and layers a `useMutation`-wrapped Server Action on top
for optimistic apply/rollback — exactly `useThemePreference`'s already-shipped shape, scaled from a
single value to a list.

**When to use:** Any RSC-fed list/detail data that a sibling Client Component needs to mutate
optimistically. This is the shape for board create/rename/delete from the Sidebar.

**Example — read side (`[VERIFIED: app/(dashboard)/layout.tsx:17-33]` is the exact file/lines this
pattern extends; code below is new code following that file's proven shape, not yet written):**
```typescript
// app/(dashboard)/layout.tsx — extends the existing async Server Component
const DashboardLayout = async ({ children }: PropsWithChildren) => {
    const identity = await verifySession();
    if (!identity) redirect(ROUTE.SIGN_IN);

    const { data, error } = await externalApi.GET(EXTERNAL_PATH.BOARDS, {
        params: { query: { userId: identity.id } },
    });
    const parsed = error === undefined ? BoardSchema.array().safeParse(data) : null;
    const boards = parsed?.success ? parsed.data : [];

    return (
        <div className="flex min-h-full bg-bg-app">
            <Sidebar boards={boards} />
            {/* ... */}
        </div>
    );
};
```

**Example — write side, modeled on `[VERIFIED: src/features/theme/hooks/use-theme-preference.ts:50-94]`
(the actual, already-shipped local-state + `useMutation`-as-Server-Action-wrapper pattern):**
```typescript
// src/features/boards/hooks/use-board-list.ts (new) — same shape as useThemePreference
export const useBoardList = ({ initialBoards }: { initialBoards: Board[] }) => {
    const [boards, setBoards] = useState<Board[]>(initialBoards);
    const mutation = useMutation({ mutationFn: createBoardAction, retry: false });

    const addBoard = (name: string) => {
        const optimistic = { id: crypto.randomUUID(), name, version: 0 };
        setBoards((prev) => [optimistic, ...prev]);
        mutation.mutate(name, {
            onError: () => setBoards((prev) => prev.filter((b) => b.id !== optimistic.id)),
            // onSuccess: reconcile optimistic.id -> real id once the action returns it
        });
    };

    return { boards, addBoard };
};
```

**Example — Server Action calling `refresh()` (`[CITED: Next.js docs/01-app/03-api-reference/
04-functions/refresh.mdx — Context7]`, Next.js 16-specific, Server-Action-only):**
```typescript
"use server";
import { refresh } from "next/cache";

export const createBoardAction = async (name: string): Promise<Board | { status: "error" }> => {
    const record = await verifySession();
    if (!record) return { status: "error" };

    const parsed = createBoardSchema.safeParse({ name });
    if (!parsed.success) return { status: "error" };

    const { data, error } = await externalApi.POST(EXTERNAL_PATH.BOARDS, {
        params: { query: { userId: record.id } },
        body: { name: parsed.data.name },
    });
    if (error !== undefined) return { status: "error" };

    const board = BoardSchema.safeParse(data);
    if (!board.success) return { status: "error" };

    refresh(); // re-runs (dashboard)/layout.tsx's RSC fetch for this client — layouts don't
               // otherwise re-render on navigation, so this is load-bearing, not decorative
    return board.data;
};
```

### Pattern 2: Storybook portable stories in a `.test.tsx` file (D-08)

**What:** Import a component's own `.stories.tsx` file, compose it with `composeStories`, then
drive it through Testing Library queries inside a plain `test()`/`expect()` body.

**Critical, repo-specific deviation from generic Storybook docs:** import `composeStories` from
`@storybook/react`, **not** `@storybook/nextjs-vite`. `[VERIFIED: vitest.setup.ts:27-42]` — this
project's own "browser" Vitest project setup file documents exactly why: `@storybook/nextjs-vite`'s
main entry eagerly imports real Next.js internals (`sb-original/image-context`, `next/dist/client/
components/navigation.js`, which reads `process.env` at module-evaluation time) that only resolve
under the Vite plugin the *separate* "storybook" Vitest project loads — the "browser" project
(where component `.test.tsx` files already live per CONVENTIONS.md's test-location table) does not
load that plugin by design. Using `@storybook/nextjs-vite` here would break the same way that led to
the 01-33 Storybook stub files.

**Portable-stories wiring is already present** — `setProjectAnnotations([a11yAddonAnnotations,
previewAnnotations])` in `vitest.setup.ts:49` already applies this project's decorators/parameters
(provider tree, theme class toggle, viewport globals, a11y config) to every `composeStories` call in
the "browser" project. No `vitest.config.ts` change is needed for D-08 — only new `.test.tsx` files.

### Pattern 3: zod schema-first boundary validation (D-12)

**What:** Define the zod schema as the single source of truth; derive the TypeScript type from it
via `z.infer`; validate with `.safeParse()` (never `.parse()`, which throws — every call site in
this codebase that touches an unverified upstream response already treats a bad shape as a
recoverable `{status:"error"}`/`502`, not an uncaught exception, per `session.ts`'s `isSessionPayload`
and `update-theme.ts`'s existing zod usage).

**Repo precedent already exists — this is an extension, not a new pattern.** `[VERIFIED:
src/features/theme/actions/update-theme.ts:18,37]`:
```typescript
const themeSchema = z.enum([THEME.LIGHT, THEME.DARK]);
// ...
const parsed = themeSchema.safeParse(theme);
if (!parsed.success) { return { status: "error" }; }
```

**Extended to the `BoardResponseDTO` shape.** `[VERIFIED: src/lib/core/api-contract/
generated-types.ts:283-288]` — the generated type this schema must accept, quoted verbatim:
```typescript
BoardResponseDTO: {
    id?: string;
    name?: string;
    /** Format: int64 */
```

### Pattern 4: curl-based E2E seeding with a cookie jar (D-07)

**What:** Replace `e2e/fixtures.ts`'s `createFixtureAccount`/`createFixtureBoard` TypeScript
Playwright-`APIRequestContext` calls with a shell script issuing raw `curl` requests against the
same backend endpoints, carrying the sign-up response's session cookie forward via a cookie-jar
file.

**Constraint this must preserve** — `[VERIFIED: e2e/fixtures.ts:51-66]`, quoted: "the backend caps a
single account at two concurrent sessions... Fixtures that seed data (`createFixtureBoard`) use this
sign-up session's own credential rather than signing in a second time." The curl replacement must
carry the *same* session forward (via cookie jar), not sign in a second time.

**Mechanics** — `[VERIFIED: curl.se manpage via WebFetch]`:
- `-c cookies.txt` (writes cookies from a response to a jar file) and `-b cookies.txt` (reads a jar
  file for a subsequent request) can be combined (`-b file -c file`) to read-then-rewrite across a
  chain of calls — the same session-reuse shape `fixtures.ts` already implements in TypeScript.
- This repo's actual cookie needs bridging as a raw header (`[VERIFIED: src/lib/server/cookies/
  upstream-cookie.ts:34]`, quoted: `` toHeader: (jsessionId: string): string => `${COOKIE.UPSTREAM_SESSION}=${jsessionId}` ``)
  — the backend's `Set-Cookie: JSESSIONID=...` needs to become a `Cookie: JSESSIONID=...` header on
  the next request. A jar file (Netscape cookie format) round-trips this correctly with plain
  `-b`/`-c`; extracting the raw value via `-D headers.txt` + `grep`/`sed` is an equally valid
  fallback if finer control over the exact header is needed (mirrors `extractJsessionId`'s manual
  parsing in `fixtures.ts:40-49`, which explicitly avoids Playwright's `headers()` collapsing
  behavior — a curl jar file does not have that collapsing problem, since it stores each cookie as
  a distinct jar entry).

**Where it lives — recommendation (resolves CONTEXT.md's open discretion point):** a standalone
script at `e2e/seed.sh` (or `scripts/e2e-seed.sh`, mirroring `scripts/check-routes.mjs`'s existing
top-level `scripts/` convention for repo tooling), invoked from Playwright test bodies via
`execSync`/`spawnSync` per-test (mirrors today's per-test `createFixtureAccount` call — each test
still needs its own randomized account), rather than folded into the existing `e2e/global-setup.ts`
(`[VERIFIED: e2e/global-setup.ts:18-44]` — that file runs exactly once for the whole suite and its
only job is the `/admin/reset` precondition; per-test account/board seeding is a fundamentally
different lifecycle and mixing them would make the reset precondition harder to reason about in
isolation).

**Example shape** (pattern only — `[ASSUMED, LOW confidence]`, no single authoritative source for
this exact script shape; general curl/jq/bash mechanics are well-established, the specific script
structure is this session's synthesis, not sourced):
```bash
#!/usr/bin/env bash
set -euo pipefail

jar=$(mktemp)
trap 'rm -f "$jar"' EXIT

email="e2e-$(uuidgen)@example.com"
signup_response=$(curl -sS -c "$jar" -X POST "$EXTERNAL_API_BASE_URL/signup" \
    -H "Content-Type: application/json" \
    -d "{\"email\":\"$email\",\"password\":\"$FIXTURE_PASSWORD\",\"displayName\":\"E2E Fixture\"}")

account_id=$(echo "$signup_response" | jq -r '.id')

curl -sS -b "$jar" -X POST "$EXTERNAL_API_BASE_URL/boards?userId=$account_id" \
    -H "Content-Type: application/json" \
    -d "{\"name\":\"$1\"}"
```

### Anti-Patterns to Avoid
- **Calling `refresh()`/`revalidatePath`/`updateTag` from anywhere other than a Server Action** —
  `[CITED: Next.js refresh.mdx — Context7]` confirms `refresh()` throws when called from a Route
  Handler; `updateTag` is explicitly Server-Action-only too.
- **Wrapping a Server Action in `useMutation` and expecting `queryClient.setQueryData` to update a
  component that never called `useQuery`** — per D-02, boards reads never go through `useQuery`, so
  cache-manipulation-based optimism (the official Next.js doc's `activityCache` example) has nothing
  to update; use local `useState` instead (Pattern 1), or explicitly opt into the
  `HydrationBoundary` SSR pattern if a future feature genuinely needs multiple independent
  `useQuery` subscribers.
- **Assuming a mutation triggered deeper in the tree (e.g., a modal on `/boards/[boardId]`) will
  automatically refresh `Sidebar`'s board list** — it will not, because `(dashboard)/layout.tsx`
  does not re-render on ordinary navigation (`[CITED: Next.js layouts-and-pages.mdx — Context7]`);
  every board-mutating Server Action must itself call `refresh()`.
- **Using `@storybook/nextjs-vite`'s `composeStories` export in a `.test.tsx` file** — breaks the
  "browser" Vitest project per `vitest.setup.ts`'s own documented reasoning (Pattern 2 above).

| E2E session cookie bridging in curl (D-07) | A hand-rolled `Set-Cookie` header parser reimplementing `extractJsessionId` | curl's built-in cookie jar (`-c`/`-b`) | `[VERIFIED: curl.se manpage]` — the jar file format already handles the "multiple `Set-Cookie` headers, extract the right one" problem `fixtures.ts:40-49`'s `extractJsessionId` exists specifically to work around in Playwright's own API; curl's native jar avoids reimplementing that parsing |

## Common Pitfalls

### Pitfall 1: Assuming Sidebar auto-refreshes after a board mutation
**What goes wrong:** A board is created/renamed/deleted from a modal elsewhere in the tree; the
Sidebar's board list (rendered by the persistent `(dashboard)/layout.tsx`) doesn't show the change
until a hard reload.
**Why it happens:** `[CITED: Next.js layouts-and-pages.mdx — Context7]` — "A layout is UI that is
shared between multiple pages. On navigation, layouts preserve state, remain interactive, and do not
rerender." `DashboardLayout` is exactly such a layout, and `<Sidebar />` is composed inside it —
`[VERIFIED: app/(dashboard)/layout.tsx:17,33]`.
**How to avoid:** Every board-mutating Server Action must call `refresh()` (Next.js 16) itself —
never rely on the invoking navigation to do it.
**Warning signs:** A newly-created board doesn't appear in the sidebar until the page is manually
reloaded, even though the create call itself succeeded (network tab shows 201/200).

### Pitfall 2: The 14 files using `vi.mock`/`vi.spyOn` (D-04/D-16 scope)
**What goes wrong:** Undercounting or missing files during the retroactive rewrite.
**Confirmed count and file list** — `[VERIFIED: grep -rln "vi.mock\|vi.spyOn" --include=*.ts
--include=*.tsx src app e2e]`, exactly 14 files, matching CONTEXT.md's stated count exactly:

**Why it happens:** ADR tech/0018 already removed the mock *HTTP* layer; these 14 files mock

**How to avoid:** `app/api/boards/route.test.ts` disappears entirely (the Route Handler it tests is
deleted, D-01). The other 13 need real-backend-driven rewrites or (for pure-browser-API mocks like
`next/navigation`'s `usePathname` in `sidebar.test.tsx`) a decision on whether framework-shim mocks

mock, and the line may not be obvious to a future contributor.

### Pitfall 3: `useBoards.unit.test.ts` doesn't need a Vitest-project move (D-09 nuance)
**What goes wrong:** Assuming D-09 ("hooks tested with RTL, not Browser Mode") requires moving
`useBoards`'s test into a different Vitest project.
**Why it happens:** CONTEXT.md's phrasing ("given hooks currently run in Vitest Browser Mode")
reads as if `useBoards` is currently tested in Browser Mode.
**Actual state, verified this session:** `[VERIFIED: src/features/boards/hooks/
use-boards.unit.test.ts:1-9]` — this file already imports `renderHook`/`waitFor` from
`@testing-library/react` and already runs in the "unit" (jsdom) Vitest project (its `.unit.test.ts`
suffix routes it there per `vitest.config.ts`'s `include` glob). Its *only* D-04 violation is
`vi.mock("@/features/boards/api/boards-api", ...)` — the fix is replacing the mocked `boardsApi`
call with a real network call against the seeded backend (or, once `useBoards()`/`boardsApi` are
deleted per D-01/D-02/D-03, this file is deleted along with them and its assertions move to
whatever hook replaces it, e.g. `useBoardList` from Pattern 1).
**How to avoid:** Don't scope planning work to "move this file to a new project" — scope it to
"remove the module mock" and, separately, "this file's subject (`useBoards`) may not exist after
D-02's rewrite at all."

### Pitfall 4: `refresh()` vs `revalidatePath`/`updateTag` — using the cache-invalidation primitive
this app doesn't need
**What goes wrong:** Reaching for `revalidatePath`/`updateTag` (heavily featured in Next.js's older
docs and ADR tech/0002's own Sources list) out of habit, when this app has no cached data to
invalidate.
**Why it happens:** `[CITED: Next.js version-15 upgrade guide + patch-fetch.ts internals —
Context7]` — Next.js 15+ made `fetch` uncached by default at runtime; this project's own
`next.config.ts` (`[VERIFIED: next.config.ts:1-13]`, only sets `agentRules: false`) enables no
`cacheComponents`/`use cache` feature anywhere, and `externalApi`'s calls never set
`cache: 'force-cache'` — so there is no fetch cache entry for `revalidatePath`/`updateTag` to
invalidate in the first place. What actually needs to happen is a **re-render of the current
client's already-rendered RSC tree**, which is exactly `refresh()`'s job.
**How to avoid:** Default to `refresh()` for this phase's mutations; reach for `updateTag`/
`revalidatePath` only if a later phase deliberately opts a fetch into caching (`'use cache'` +
`cacheLife`), which nothing in this phase's scope does.

## Open Questions

1. **Does D-10's "single generic, typed cookie client" include `upstream-cookie.ts`, or only
   `theme-cookie.ts` + `session.ts`'s inline cookie calls?**
   - What we know: `theme-cookie.ts` and `session.ts` both call `next/headers`'s `cookies()`
     directly and share `baseCookieOptions()` — a clean generic fit. `upstream-cookie.ts` instead
     parses a raw `fetch` `Response`'s `Set-Cookie` header (`[VERIFIED:
     src/lib/server/cookies/upstream-cookie.ts:1-35]`) — a structurally different operation with no
     `cookies()` call at all.
   - What's unclear: CONTEXT.md's D-10 text says "replaces the ad hoc `themeCookie`/`upstreamCookie`
     modules" — implying both — but the two have genuinely different responsibilities (own-app
     cookie I/O vs. upstream-response cookie extraction).
   - Recommendation: the planner should design one generic client for `theme-cookie.ts`+`session.ts`'s
     shared `cookies()`-based read/write/clear shape, and treat `upstream-cookie.ts` as a
     deliberately separate, smaller module — or explicitly confirm with the user that a single
     interface spanning both is wanted despite the shape mismatch.

2. **Does D-04's no-mocking policy cover framework-shim mocks (`next/link`, `next/navigation`) or
   only business-logic mocks?**
   - What we know: `sidebar.test.tsx`'s own comment justifies its `next/link` mock as working around
     a Vitest Browser Mode environment gap (`process is not defined`), not as faking business logic.
   - What's unclear: D-04's text ("No mocking... anywhere outside Storybook") reads as absolute.
   - Recommendation: confirm with the user whether framework-environment shims are in-scope for
     D-16's retrofit, since removing them (if even possible — the underlying `process is not
     defined` gap may not have a non-mock workaround in Vitest Browser Mode) is a materially
     different, possibly infeasible, task versus leaving them as documented exceptions.

3. **Should `checkAuthorRoles`-style route-guard behavior (currently exercised only via
   `app/api/boards/route.test.ts`, which is deleted under D-01) get a replacement test at all, or
   does deleting the Route Handler retire that coverage entirely into the new RSC's own test?**
   - What we know: `route.test.ts` is one of the 14 `vi.mock` files and tests the now-banned
     Route Handler.
   - What's unclear: whether `(dashboard)/layout.tsx`'s unauthenticated-redirect behavior already
     has coverage elsewhere (it likely does, given AUTH-03 is a Phase 1 requirement) that would make
     `route.test.ts`'s coverage fully redundant once deleted, or whether the 401→502-on-guard-bypass
     assertion specific to `route.ts:16-19` needs a new home.
   - Recommendation: the planner should grep for existing `(dashboard)/layout.tsx` test coverage
     before assuming `route.test.ts`'s deletion is coverage-neutral.

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|------------------------|
| Trusting a client-supplied `userId` instead of the session record | Spoofing | `[VERIFIED: app/api/boards/route.ts:11-14]`'s own comment already documents this exact control for the code being replaced — the OpenAPI contract declares `userId` a client-suppliable query parameter, but every call site reads it from `verifySession()`'s own record instead; the new RSC/Server Action call sites must preserve this, not regress it while porting |
| Server Action invoked directly over the wire with an arbitrary payload, bypassing TypeScript's compile-time argument shape | Tampering | `[VERIFIED: src/features/theme/actions/update-theme.ts:32-40]`'s own comment: "Validated after the session check, before calling upstream — a Server Action is invokable over the wire with an arbitrary request body regardless of what TypeScript claims about its caller, so this is real runtime defense, not a formality." Every new board Server Action (create/rename/delete) needs the identical session-check-then-schema-validate ordering |
| A proxy-bypass-class vulnerability reaching a data-fetching RSC that assumes an earlier guard already ran | Elevation of Privilege | Repeat `verifySession()` at every server entry point (RSC data-fetch, every Server Action) — never rely on `(dashboard)/layout.tsx`'s own check alone, since a future refactor could introduce a new RSC/Server Action outside that layout's subtree |
