# Quick Task 260908-g61: Eradicate `useOpenBoardId` Summary

**The board delete now moves the URL with `window.history.replaceState`, which Next 16 syncs into
`usePathname()` in the same commit and with no RSC request — so the lag the `useOpenBoardId`
compensator existed to paper over is gone, and the hook is deleted rather than replaced.**

## Task 1 — the spike: PREMISE CONFIRMED

Probe: `e2e/zz-replacestate-delete.e2e.spec.ts` (throwaway, deleted in Task 1's last step). It
seeded one account and two boards through `e2e/seed.ts`'s own helpers, opened the doomed board,
installed an in-page 4ms sampler recording `{Date.now(), h1 text, doomed column present,
location.pathname}`, and clicked confirm. A bespoke sampler was used deliberately: `flickerTracker`
counts `MutationRecord`s and cannot report *what the header said* at each instant, which is the
entire measurement.

Four runs, all recorded BEFORE the rollback:

| Run | Command |
|-----|---------|
| Half A / dev | `QUALITY_RECORD_MODE=record E2E_PORT=3000 pnpm exec playwright test --project=e2e e2e/zz-replacestate-delete.e2e.spec.ts` |
| Half B / dev | same command, with the Step 3 edit in the working tree |
| Half B / production | `QUALITY_RECORD_MODE=record pnpm exec playwright test --project=e2e e2e/zz-replacestate-delete.e2e.spec.ts` (no `E2E_PORT` → `pnpm build && next start -p 4173`) |
| Half A / production | same command, Step 3 edit reverted — the counterfactual the plan did not ask for, added so "closed, not moved" is measured rather than inferred |

### The six answers

**Q1 — Synchrony.** Direct, non-polling reads taken the instant the sidebar row disappeared.

| Run | header text | doomed column visible | address bar |
|-----|-------------|----------------------|-------------|
| Half A dev (@220ms) | destination | false | **deleted board** |
| Half A prod (@104ms) | destination | false | **deleted board** |
| Half B dev (@119ms) | destination | false | destination |
| Half B prod (@101ms) | destination | false | destination |

With `router.replace`, the compensator hook fixed the header and the body but could not fix the
address bar — the third reader stayed stale. With `replaceState` all three agree at the sync point,
on both dev and a production build.

**Q2 — Does the server catch up, and is any request issued?** `page.on("request")`, filtering on
the `rsc` header.

- Half A dev: `POST /boards/<survivor>` (next-action) @178ms, **`GET /boards/<survivor>?_rsc` @180ms**, `POST` @402ms.
- Half A prod: two `next-action` POSTs, no RSC GET (the Router Cache served the navigation).
- Half B dev: `POST /boards/<survivor>` @100ms, `POST` @341ms. **Zero RSC requests.**
- Half B prod: `POST /boards/<survivor>` @70ms, `POST` @139ms. **Zero RSC requests.**

The mechanism that answers "does the server catch up": `onMutate` runs `replaceState` *before*
`mutationFn` issues the action, so the Server Action POST is addressed to `/boards/<survivor>` —
`proxy.ts` stamps `x-kanban-pathname` with the destination and the action's own `refresh()` renders
the destination board. The client URL and the server header cannot diverge, because the URL moves
first.

**Q3 — Which pathname does `refresh()` carry?** The destination, in every run. After settle: URL,
header and content all on the destination; `anyRscRequestNamingDeletedBoard: false`; the T-02-54
membership `redirect()` never fired against the deleted id; `pageErrors: []`. Half B dev and prod
both recorded `consoleErrors: []`. (Half A's very first dev run logged an unrelated pre-existing
hydration-mismatch warning on `AddTaskButton`'s `disabled` attribute; it did not recur and is not
this task's.)

**Q4 — Hard reload.** Fetched the post-delete URL's raw HTML through the page's own cookie jar:
`serverHtmlNamesSurvivor: true`, `serverHtmlNamesDoomedColumn: false` in all four runs, and the
reloaded page's `<h1>` read the survivor. The destination genuinely server-renders.

**Q5 — Back.** `page.goBack()` after the delete landed on the survivor, never the deleted board's
address, in all four runs (`landsOnDeletedBoard: false`). T-02-70 holds.

**Q6 — The window, re-measured.** Spans are relative to the confirm click.

| Run | header title wrong | deleted content painted | address wrong |
|-----|--------------------|-------------------------|---------------|
| Half A dev | 0–77ms | 0–77ms | **0–594ms** |
| Half A prod | 0–59ms | 0–59ms | **0–247ms** |
| Half B dev | 0–37ms | 0–37ms | 0–37ms |
| Half B prod | 0–40ms | 0–40ms | 0–40ms |

**The window is CLOSED, not shortened.** The residual ~40ms is present identically in both halves
and is not a disagreement between two sources of truth — it is the interval before React's first
commit, during which nothing has re-rendered at all. From the first commit onward, Half B has zero
samples where any of the three signals disagrees. What Half B removes is the 247ms (production)
interval in which the address bar alone still named the just-deleted board.

**Verdict: PREMISE CONFIRMED. Shape (a)** — `history.replaceState` alone, relying on the action's
own `refresh()`. Q2/Q3/Q4 show the server reaching the destination with no help; neither a
follow-up `router.replace` (b) nor a `router.refresh()` (c) was needed, so neither was added.

## Handoff to quick task `260908-g63` (the ADR amendment)

**Both findings from `use-open-board-id.ts`'s deleted doc comment survive this change and belong in
`docs/adr/tech/0030`. They are recorded here verbatim enough to quote, and this task deliberately
does not write the ADR.**

1. **The measured stranding window.** The deleted comment said "~700-800ms"; the accurate figure is
   `260907-q83-SUMMARY.md:139`'s raw measurement — **151ms–819ms after the confirm click**, during
   which the header `<h1>` read blank *and* the just-deleted board's own column heading was still
   painted, simultaneously, from one cause. Carry those numbers, not the comment's.
2. **Why a `status: "pending"` filter was insufficient.** The delete's own network round trip
   usually settles well before the separately-held RSC navigation does, so a pending-only filter
   closed the window for a moment and then reopened it the instant the mutation succeeded (measured
   live against a production build, 260907-q83). The shipped filter was `status !== "error"`,
   retired naturally once the URL itself caught up.

Add from this task: the compensator was needed because `router.replace` writes its `replaceState`
from a `useInsertionEffect` on the *next* router state, so the address bar lagged the rest of the UI
by a measured 247ms on a production build (594ms on dev). Removing that lag removed the need for a
second source of truth entirely.

## Where the plan was wrong or incomplete

1. **A brand-new e2e spec cannot pass the passive `qualityGates` teardown.** The plan's Task 1 has
   the probe running four times but never mentions that `e2e/quality-fixtures.ts` fails any spec
   with no `e2e/quality-baseline.json` entry (`No baseline entry for "…". Record one with pnpm
   e2e:baseline`). The first run "failed" on that alone, after the measurement had printed. The
   escape is `QUALITY_RECORD_MODE=record`, which appends to the gitignored
   `.quality-observations.jsonl` and skips the comparison — it does **not** touch the baseline,
   which `pnpm e2e:baseline` alone merges. Every later probe run used it. A future probe-spec plan
   should name this up front.
2. **`git checkout HEAD -- src/` does not undo a file deletion.** Used for a counterfactual, it
   silently restored `use-open-board-id.ts` to both disk and index — i.e. it would have resurrected
   the very file this task deletes. Caught by checking `git status --short` after each restore.
   `git checkout <ref> -- <path>` only writes paths present in `<ref>`; the deletion has to be
   re-applied by hand.
3. **`git add` aborts the whole invocation on one bad pathspec.** Passing the already-staged deleted
   file alongside the six modified ones failed with `fatal: pathspec … did not match any files` and
   staged *nothing*, so the first commit contained only the deletion. Amended. Worth knowing for any
   plan that stages a `git rm`'d path by name.
4. **Task 2's `<verify>` runs the e2e gate against a dev server (`E2E_PORT=3000`), but the quality
   baseline and its timing budgets are recorded against a production build.** That mismatch produced
   two failures that are not regressions (see above) and cost a real investigation to rule out. The
   e2e verify step for a spec carrying `qualityGates` should run production-first.
5. **The plan's Step 2 describes Half A as "the number Task 2 must beat".** It is worth stating that
   Half A is not the pre-q83 broken state — it is the current shipped state *with* the compensator,
   so its header/content window is already closed and only its address-bar lag is beatable. A reader
   expecting an ~800ms baseline would think the probe had failed.
6. **`e2e/boards-delete.e2e.spec.ts` was definite scope, not conditional.** Its `files_modified`
   entry is marked CONDITIONAL; the header comment it names was unambiguously falsified by the
   change and had to be rewritten.
