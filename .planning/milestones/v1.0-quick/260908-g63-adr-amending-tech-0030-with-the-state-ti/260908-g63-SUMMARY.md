**The material correction — the fifth slot is not what the plan or the brief said it was.** Both
state that `onSettled` in `use-create-subtask.ts`, `use-delete-subtask.ts`, `use-rename-subtask.ts`
and `use-toggle-subtask.ts` retires "an id from the in-flight set `use-unconfirmed-ids.ts` reads".
It does not. Each of the four declares its own `useState<ReadonlySet<string>>`
(`use-toggle-subtask.ts:72`, `use-rename-subtask.ts:61`, `use-create-subtask.ts:64`,
`use-delete-subtask.ts:55`) and `onSettled` deletes from *that* (`:184`, `:163`, `:157`, `:128`),
feeding a predicate the hook returns itself (`isSubtaskPending`, `isCreatingSubtask`). Three of the
four declare no `mutationKey` at all, so `useMutationState` cannot see them by construction.

`useUnconfirmedIds` filters `{ mutationKey, status: "pending" }` and retires with no callback — which
is precisely **why 12 of the 16 hooks need no `onSettled`**. That turns the fifth slot from a footnote
into a stated condition: a hook needs it when it exposes a pending predicate from state it owns.

## The owner's correction, and the commit that applied it

The draft's revert rule asserted **"No shipped hook restores a snapshot."** The owner rejected that
as trading one false universal for another, and was right. Verified before rewording: the four
deletes DO restore prior state — `use-delete-task.ts:117`, `use-delete-subtask.ts:110` and
`use-delete-column.ts:109` all read `{ ...current, columns: context.undo(current) }`, and
`use-delete-board.ts:122` reads `restore(current ?? [])`.

The accurate discriminator, now in the ADR (`3fe08b3`) and in both doc edits, is **what the `onError`
write is a function OF**: a snapshot restore assigns a value captured in `onMutate` and ignores the
live entry; the shipped shape applies an undo closure TO `current`, so a sibling that landed in
between survives the rollback. `use-create-board.ts` is the one that performs no restore at all, for
the reason its own `:135-136` comment gives.
