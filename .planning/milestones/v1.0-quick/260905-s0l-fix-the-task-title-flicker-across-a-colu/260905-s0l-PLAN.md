<objective>
Reordering a task inside one column makes every card in that column change title twice within
about three frames. The cause is not the optimistic write and not dnd-kit: TanStack's
`notifyManager` flushes observer notifications on a `setTimeout(0)` macrotask, so the browser
paints dnd-kit's own drop render — DOM still in the PRE-move order, every sort transform already
cleared — before the optimistic reorder from `useMoveTask.onMutate` reaches the `useQuery`
observer.

Purpose: make the frame the drop paints already be the reordered one, using the library's own
documented knob rather than any bookkeeping about the mutation.
Output: a one-statement change in `query-client.tsx`, a decision record so a later reader cannot
quietly revert it, and a test that is falsified against the unfixed code first.
</objective>

1. **The two renders, measured 2026-09-05** (headless Playwright on the dev server, a `rAF`
   sampler recording every `<li>` card's title, bounding top and inline transform/transition;
   card "Alpha" dragged from index 0 to index 2 in a four-card column):
   - During the drag, `verticalListSortingStrategy` shifts siblings with inline
     `translate3d(0, ±112px, 0)` and `transition: transform 200ms`. DOM order is still the
     ORIGINAL order; only the visual order has changed.
   - On drop, dnd-kit clears every transform and transition synchronously inside its own
     `unstable_batchedUpdates`. **That render paints.** At t=800ms the DOM read Alpha@165,
     Bravo@277, Charlie@389, no transforms — the original order, every slot showing its pre-move
     title.
   - At t=842ms — about two frames later — the optimistic reorder landed: Bravo@165, Charlie@277,
     Alpha@389. Every card in the column therefore changes title twice inside ~3 frames.
   - Cross-column moves do not show it, because the destination column's cards carried no sort
     transforms to clear.
2. **The gap is the notify scheduler, not an await.** Verified in
   `node_modules/.pnpm/@tanstack+query-core@5.101.4/.../notifyManager.js`: the default scheduler is
   `systemSetTimeoutZero`, so a `setQueryData` inside `onMutate` reaches `useQuery` observers on a
   later MACROTASK. The `await cancelQueries` chain in `Mutation.execute` is microtasks and is not
   the frame boundary.
3. **The fix was measured, then reverted.** `notifyManager.setScheduler(queueMicrotask)` at module
   scope took the same drag from the last drag frame straight to the final order, with no
   intermediate old-order frame. `notifyManager` is re-exported from `@tanstack/react-query`
   (`build/modern/index.d.ts` line 52) and its type carries
   `readonly setScheduler: (fn: ScheduleFunction) => void`. Import from `@tanstack/react-query`,
   never from `query-core` directly.

   `app/layout.tsx`, so the module executes on the server too; `queueMicrotask` has been a Node
