<hard_constraints>

These bind every task.

1. **Never dispatch a check script through `pnpm run`.** The spike measured every one of the 10 fast
   checks costing 575-990ms MORE via `pnpm run <alias>` than via `node scripts/<x>.mjs` — a
   double-pnpm-boot tax paid once per script, ~6-8s across the tier for identical work. The runner
   spawns `process.execPath` against the `.mjs` path directly. This applies ONLY to the fast tier;
   see constraint 2 for why the heavyweight steps do the opposite.

2. **The heavyweight steps keep CI's exact command string.** `pnpm format:check`, `pnpm exec next
   typegen`, `pnpm build`, `pnpm lint`, `pnpm test`, `pnpm api:generate`, `pnpm exec playwright test
   --project e2e` are invoked exactly as `ci.yml` spells them. Two reasons, both load-bearing: the
   ~700ms pnpm boot is under 1% of steps that cost 3.7-158 seconds, and the drift guard compares
   these literals to `ci.yml`'s `run:` lines, so a "faster" rewrite to `node_modules/.bin/next build`
   would break the comparison AND silently skip the `prebuild` -> `tokens:build` hook.

3. **Never print secret material.** The e2e preflight checks that `NONPROD_RESET_TOKEN` is DEFINED,
   never what it equals. Do not log it, do not include it in an error message, do not copy it into
   another env var. Reading `.env.local` from inside a committed `.mjs` file is the established
   pattern (`e2e/test-env.ts` does exactly this); a Bash command whose own text names that path is
   refused by the permission layer, so keep the path inside the script.

4. **Do not put visual regression in the default tier.** No `CI=1`, no `pnpm build-storybook`, no
   `--project visual` anywhere in `verify.mjs`. The spike measured 348s for coverage orthogonal to
   behavior, already gated by CI's own `visual` job before merge. It goes in the guard's exception
   list with its reason, not in the runner.

5. **Do not reimplement `e2e/global-setup.ts`'s refusal.** It already throws a named error for an
   absent token and for a failed reset probe. The runner front-loads only the token-PRESENCE check
   (so the refusal costs 5ms instead of 4 minutes) and adds a caveat line on e2e failure. It does
   not probe the network itself and does not duplicate the message.

6. **Do not touch `NEXT_TELEMETRY_DISABLED`, runner images, or action pins.** That is a separate
   filed todo (`2026-09-03-pin-ci-runtime-layer-runner-image-actions-node.md`).

7. **Comment style.** `pnpm comments:check` gates `scripts/**/*.mjs` at 3 prose lines per comment
   run, and two adjacent `/* */` blocks count as one run. Follow `~/.claude/CODE_COMMENTS.md`. In
   code comments cite paths a reader can open (`.planning/quick/spike-pnpm-startup-and-pre-push-gates.md`,
   `docs/adr/tech/0008`), never `D-NN`, `QT-E3Z-NN` or any other planning token.

8. **Falsify every guard in both directions.** A guard that has only ever been seen passing is
   untested. Each falsification uses a fabricated value and is reverted immediately; never leave a
   probe edit in the tree.

</hard_constraints>

<locked_decisions>

Settled by the spike and the todo. Implement, do not revisit.

- **D1 — two tiers.** Default tier on pre-push; visual regression stays CI-only. An 11-12 minute
  gate makes `--no-verify` the reflex, at which point the hook protects nothing.
- **D2 — e2e is in the default tier.** Decided by the user 2026-09-03, after correcting a stale
  claim: since `5f325f8` resets are targeted per user id, so a local e2e run does not wipe the
  shared nonprod backend. Its ~60s rides behind ~240s of other gates.
- **D3 — order is ascending measured cost**, with two hard ordering constraints (typegen before
  lint; build before e2e) and one deliberate exception: **e2e runs LAST despite being cheaper than
  `test`.** It is the only step whose failure may be environmental rather than the code's fault, and
  putting it last means such a failure arrives with every other gate already proven green, which is
  what makes "is this my bug or the backend?" answerable instead of a guess.
- **D4 — the guard parses every job, not only `quality` and `e2e`.** The spike's wording names those
  two, but a guard that ignores unknown jobs is defeated by adding a job instead of a step. Every
  job must be either scanned or named in the exception list with a reason.

</locked_decisions>
