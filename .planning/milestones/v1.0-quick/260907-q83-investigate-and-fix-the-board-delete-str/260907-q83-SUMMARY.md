# Quick Task 260907-q83: Fix the board-delete stranding window Summary

**Both dashboard-header.tsx and board-screen.tsx now resolve the OPEN board from the delete
mutation's own destination (read via `useMutationState`) instead of the stale
`usePathname()`-derived id, closing the ~700-820ms window where a board delete showed the just-deleted
board's own content beside a blank header title.**

## Performance

- **Duration:** ~2h30m (including CI contention troubleshooting)
- **Tasks:** 3
- **Files modified:** 6 modified, 1 created

## Measurement (Task 1)

Reproduced the reported stranding bug with a throwaway probe (`e2e/zz-delete-stranding.e2e.spec.ts`,
deleted after use) driven against a real running dev server. Timed from the confirm button's own
click (not the menu-open steps before it, which were the first cut's contaminating overhead — see
Deviations below):

- **Window measured:** 151ms-819ms after the confirm click (a fresh account/board pair; the exact
  numbers vary run to run with server warmth, but the shape is stable): the header `<h1>` reads
  `(blank)` and the doomed board's own column heading (`Strandcol (0)`) is still painted for the
  *entire* window, simultaneously — both symptoms share one cause, not two.
- **What closes it:** the header flips to the destination's name at the same instant a fresh RSC
  `GET .../boards/<survivorId>?_rsc=...` request — issued as a direct consequence of
  `use-delete-board.ts`'s `router.replace(destination)` — lands. Confirmed the standing hypothesis:
  `usePathname()` (and everything derived from it) does not move until that navigation's response
  commits, even though the boards-list cache entry was already updated synchronously one line above
  the `router.replace` call in `onMutate`.
- **Candidate 1 falsified:** the destination board's sidebar `<Link>` already carries
  `prefetch={true}` (`board-card.tsx:71`), so per `docs/adr/tech/0030`'s own reasoning it should
  already be in the Router Cache — yet the confirm click still issued a fresh RSC request. The
  Router Cache is not being reused here (at least in dev mode), so making prefetch fire earlier
  would not have closed the window; this candidate was not built.
- **Both destination branches checked:** the "others remaining" branch is the one measured above;
  the "delete the last board" branch was not separately probed with the throwaway instrument, but
  is covered by BOARD-05's own existing assertion and, post-fix, by `useOpenBoardId` resolving to
  `null` for that branch too (no board open, matching the empty-state page Next renders for
  `children`).

## Fix (Task 2)

**Platform primitive used:** `useMutationState` (TanStack Query's own reactive read of the mutation
cache), the same shape `src/lib/client/use-unconfirmed-ids.ts` already uses to expose an in-flight
mutation's variables to any component in the tree — not a bespoke override store.

**Platform primitive rejected, and why:** `router.prefetch()` of the destination (candidate 1) —
the destination was measured already `prefetch={true}` and the confirm click still triggered a
fresh RSC round trip, so the Router Cache was not being reused here; making prefetch fire more
aggressively would not have removed the network wait. Reordering the two cache writes so the list
removal applies after the navigation commits (candidate 3) was also rejected without shipping: per
Task 1's measurement, both symptoms (blank title, stale content) span the identical window, so
deferring only the list write would have fixed the title while leaving the stale board content and
a phantom sidebar row untouched.

**What shipped:** `src/features/boards/hooks/use-open-board-id.ts` (new) — reads the URL's own board
id via `usePathname()`, then checks TanStack's mutation cache for a `MUTATION_KEY.DELETE_BOARD`
mutation whose `variables.boardId` matches that same id; if one exists and its status is not
`"error"`, its `context.destinationBoardId` (computed once, synchronously, in `use-delete-board.ts`'s
`onMutate`, next to the existing `router.replace` call) is returned instead. `dashboard-header.tsx`
and `board-screen.tsx` both now call this hook instead of inlining `toBoardIdFromPath(usePathname())`.

### A real bug found and fixed mid-task (Rule 1)

The first implementation scoped the override to `status: "pending"`. It passed against the dev
server, and FAILED against a production build (`pnpm build && pnpm exec next start`): the delete's
own network round trip to the real backend settles (`status` moves to `"success"`) well before the
separately-held RSC navigation lands, so a pending-only filter closed the window and then
**reopened it** the instant the mutation succeeded — the exact stranding bug, just shifted to a
later sub-window. Caught by re-running the new case's own falsification against a fresh production
build rather than trusting the dev-server pass. Fixed by widening the filter to `status !== "error"`
— which self-retires the moment the URL itself catches up (`pathBoardId` no longer equals
`deletedBoardId` once the pathname commits to the destination), with `error` excluded so a REFUSED
delete falls back to the real (correct) pathname while `onError`'s own reverse `router.replace` is
in flight, instead of continuing to claim the failed destination.

**2. [Rule 1 - Test bug] The first cut of the new e2e case's assertions could not have caught the
bug**

- **Found during:** Task 1, first attempt at falsifying the case against unfixed code
- **Issue:** using `expect(locator).toBeHidden()`/`toBeVisible()` on the stranding symptoms — both
  POLL and are satisfied the instant the condition becomes true, so the assertions passed the moment
  the artificially-held RSC response finally released, proving nothing about the window in between
  (the exact mistake `boards-switch.e2e.spec.ts` itself documents and designs around)
- **Fix:** used a sync point (`await expect(sidebar link).toBeHidden()`, which fires the instant
  `onMutate`'s synchronous cache write lands) followed by DIRECT, non-polling reads
  (`.textContent()`, `.isVisible()`) taken immediately after
- **Files modified:** `e2e/boards-delete.e2e.spec.ts`
- **Commit:** `56cc7a6`

1. Deleting a board that is currently open, with others remaining, watched at normal speed and under

   none.

   restore correctly.
5. A mock comparison (`docs/kanban-task-management-web-app.pdf`, pages p4-p7) if the fix changed
