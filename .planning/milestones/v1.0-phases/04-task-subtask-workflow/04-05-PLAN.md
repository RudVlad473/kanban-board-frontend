<objective>
Add the three design-system pieces this phase's surfaces need before any of them can be built: the
`heading-m` type token the task card's title requires, the `Textarea` primitive the Description field
requires, and the `Checkbox` change the completed-subtask treatment requires. All three are
`src/components/ui/` and `tokens/` work with visual baselines attached, deliberately separated from

the box rather than the label, so the specified completed-row colour is unreachable from a consumer.

completed label.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user input → `Textarea` control | Free-form multi-line text that later reaches a Server Action body |
| design tokens → every themed surface | A token change is global; a wrong value silently reaches every consumer |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-19 | Tampering | `Textarea` value reaching a Server Action | medium | mitigate | The primitive performs no validation and claims none; the real defence is `.safeParse` at the action boundary per ADR tech/0024, asserted in the action plans, so no consumer can mistake the control for a guard |
| T-04-20 | Spoofing | unlabelled form control | low | mitigate | `label` is a required prop, so an unlabelled control cannot be constructed; a missing-label regression fails type-checking, not only the axe pass |
| T-04-21 | Tampering | existing Checkbox consumers | medium | mitigate | The treatment stays behind the already-shipped opt-in prop, and an unchanged-default test plus an add-only visual diff gate the regression |
| T-04-SC | Tampering | package-manager installs | low | accept | This plan installs nothing; the primitive is built from the already-installed `@base-ui/react`. `04-RESEARCH.md` § Package Legitimacy Audit records zero packages added by this phase |
</threat_model>
