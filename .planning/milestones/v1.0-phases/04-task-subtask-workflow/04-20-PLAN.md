than applying optimistically.

server has destroyed the subtasks.

what actually happens.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → delete-task action | An irreversible server-side cascade triggered from a client control |
| confirmation copy → user consent | The only place the user learns what the cascade actually destroys |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-01 | Tampering | `deleteTaskAction` payload | high | mitigate | `.safeParse` after the session check, covering all three id segments |
| T-04-02 | Elevation of Privilege | user id in the upstream query | high | mitigate | Read only from the verified session record, asserted by grep |
| T-04-40 | Repudiation | consent narrower than the effect | high | mitigate | The confirmation body names the task AND its subtasks and states the action cannot be reversed; a browser case asserts all three elements of that string |
| T-04-41 | Denial of Service | reflexive confirmation | medium | mitigate | Initial focus is on the non-destructive action, and both dismissal guards are held while the delete is in flight so a second confirm cannot be issued |
| T-04-42 | Information Disclosure | probing which task ids exist | medium | mitigate | A second delete maps to the shared not-found branch, which deliberately covers both forbidden and missing so a caller cannot distinguish them |
