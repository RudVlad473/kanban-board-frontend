# Phase 3 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Sources:**

1. `docs/kanban-task-management-web-app.pdf` (Frontend Mentor "Kanban Task Management Web App"
   design export, 73 pages, gitignored local-only — canonical visual system). Pages consulted this
   session via `pdftoppm -scale-to-x 1100`: **p2** (empty board + `+ Add New Column` CTA, light),
   **p3** (populated board with the `+ New Column` ghost column, light), **p8/p18** (Add New Board
   modal, light/dark), **p9** (Edit Board modal with its `Board Columns` section), **p13**
   (populated board, dark).
2. `src/styles/tokens.css` — the already-implemented, tested, visual-regression-baselined DTCG →
   Style Dictionary → Tailwind v4 token pipeline (plan 01-04).
3. `src/components/ui/*` and `src/features/boards/components/*` — the shipped primitives and Phase 2
   board components this phase composes against.
4. `docs/api/kanban-board-openapi.json` — the fixed backend contract (`ColumnResponseDTO`,
   `SaveColumnRequestDTO`, `UpdateColumnRequestDTO`, `ReorderColumnRequestDTO`).
5. **User decisions, 2026-08-26** (recorded below as **U-01..U-05**) — this phase has no
   CONTEXT.md, so the five open product questions were resolved directly with the user in this
   session and are treated with the same authority a CONTEXT.md `## Decisions` entry would carry.

**Precedence (inherited verbatim from 02-UI-SPEC.md):** user decisions govern product/UX
mechanics; the PDF governs the visual system (color, type scale, spacing, component anatomy);
`tokens.css` wins over the PDF's raw swatches wherever Phase 1's token generation deliberately
adjusted a value. This UI-SPEC does **not** re-derive the spacing/typography/color system — it
declares the already-locked tokens as this phase's contract and names the **five new tokens** this
phase is authorized to add (three column-dot accents, two ghost-column gradient stops).

**User decisions locked this session:**

| ID | Decision |
|----|----------|
| **U-01** | Column add/rename/delete uses **per-column affordances**, not the PDF's batched `Board Columns` section inside Edit Board. The `+ New Column` ghost column opens an Add-Column modal; each column header carries a kebab menu with `Rename Column` / `Delete Column`. Rationale: every column carries its own `version` for optimistic concurrency, so one `Save Changes` across N columns is really N independent POST/PUT/DELETE calls that can partially fail — the exact D-04 partial-failure problem Phase 2 already hit. Also gives reorder somewhere to live, and follows D-07's precedent of relocating the PDF's header-kebab actions onto the row they act on. |
| **U-02** | Reorder drag handle is the **whole column header**, no separate grip glyph — plus a **mandatory** keyboard path (focus header → `Space` lift → `←`/`→` move → `Space` drop → `Esc` cancel) with an `aria-live` announcement. Drag-only would make COLUMN-03 keyboard-inaccessible. |
| **U-03** | Column headers render the PDF's **colored dot**, assigned deterministically from the column's own **id** across three new tokens (the backend `ColumnResponseDTO` has no color field). Keyed by id, **not** by position — see the note under Color, below. |
| **U-04** | Column delete is confirmed through a modal **mirroring `DeleteBoardConfirm` exactly** — `"Delete this column?"` / `"Delete Column"` (destructive) / `"Keep Column"` (secondary, holds initial focus). |
| **U-05** | Rename and reorder apply **optimistically with rollback + error toast** (D-15's pattern); delete **waits for the server** (D-09's pattern, since the cascade is irreversible per ADR domain/0002). |

## Spacing Scale

Declared values — this project's own already-implemented 4px-base scale (`src/styles/tokens.css`,
`--space-*`), reused verbatim (must be multiples of 4):

| Token | Value | Usage this phase |
|-------|-------|------------------|
| `--space-1` | 4px | Menu popup inset (`Menu.Content` `p-1`) |
| `--space-2` | 8px | Caption-to-kebab gap in the column header row; Add/Rename modal field-to-error gap |
| `--space-4` | 16px | Modal padding (mobile); `Menu.Item` horizontal padding (already `px-4`); dot-to-caption gap in the column header row |
| `--space-6` | 24px | Modal padding (tablet+); the board canvas's own `p-6`; the inter-column gutter (`gap-6`, already shipped in `board-view.tsx:30`); column-header bottom padding (`pb-6`, already shipped) |
| `--space-8` | 32px | Layout gaps between major regions |
| `--space-12` | 48px | Major section breaks |
| `--space-16` | 64px | Page-level spacing |

This phase's new components (`AddColumnModal`, `RenameColumnModal`, `DeleteColumnConfirm`,
`ColumnHeader`, `AddColumnPlaceholder`) are built exclusively from the seven tiers above.

**The dot-to-caption gap is 16px because the mock overruled this spec.** This table originally
assigned it `--space-1` (4px), and `ColumnHeader` shipped that way in plan 03-06. Measured against
PDF p3 on 2026-08-27 the mock's gap is ~15px — a 62px gap beside a 62px dot at 300 DPI, calibrated
by the column pitch (304.1px = 280px column + 24px gutter). `--space-4` (16px) is the nearest tier,
so the code and this row were both corrected in plan 03-08. Do not "restore" 4px: it was a spec
error, not a deliberate deviation. Second time the mock has overruled a UI-SPEC reading this
milestone — see 02-UI-SPEC.md's pinned-footer `+ Create New Board`.

**`--space-3` (12px) remains barred for new work.** It exists in `tokens.css` and is load-bearing
inside `TextField`'s and `Dropdown`'s already-baselined internals, and `Menu.Item`'s `py-3` — all
components this phase **reuses as-is**, not rebuilds. Carried forward verbatim from 02-UI-SPEC.md:
introduce no *new* 12px usage, and do not read its presence in those files as license to reach for
12px elsewhere.

Exceptions:

- **44×44px minimum touch target** on every icon-only control — the column-header kebab is
  `IconButton` `variant="ghost"` `size="md"` (`size-11` = 44px, already implemented). This sets the
  column header row's min-height to 44px, which is taller than the 15px caption alone and is
  **deliberate**: it is also the drag-handle grab area (U-02).
- **Column width: 280px** (`w-70`), already shipped in `board-view.tsx:41` and confirmed by
  measurement against PDF p3 (280pt at a 1440pt-wide page). The `+ New Column` ghost column is the
  **same 280px**, measured identically — it must not be narrower.
- **Ghost-column height** matches the tallest column's full scroll height, not the viewport (PDF p3:
  the placeholder runs from the top of the column region to the bottom of the longest column).

## Typography

This project's already-implemented 5-token type scale (`src/styles/tokens.css`) mapped onto the
template's semantic roles. No new type token this phase:

| Role | Token | Size | Weight | Line Height | Usage this phase |
|------|-------|------|--------|-------------|------------------|
| Display | `heading-xl` | 24px | 700 | 30px | The `+ New Column` ghost-column label (PDF p3 — the one place 24px appears outside the board title) |
| Heading | `heading-l` | 18px | 700 | 23px | Modal titles — `Add New Column`, `Rename Column`, `Delete this column?` (`Modal.Title`, already wired to this token) |
| Label (caption) | `heading-s` | 12px | 700 | 15px, +2.4px tracking | The ALL-CAPS column header caption `TODO (4)` — already shipped in `board-view.tsx:46`, unchanged |
| Label | `body-m` | 12px | 700 | 15px | Field label `Column Name`; button text (`Button`/`IconButton` already carry it) |
| Body | `body-l` | 13px | 500 | 23px | `Menu.Item` text (`Rename Column` / `Delete Column`, already `body-l` at `menu.tsx:90`); delete-confirmation body copy; `TextField` input values and error text |

Weight is applied via the `[font-weight:var(--font-weight-{token})]` arbitrary-property syntax
project-wide (documented Tailwind v4 namespace-collision workaround, `button-variants.ts` comment) —
new components this phase adds must follow the same pattern, never a bare `font-bold`/`font-medium`
utility.

**Caption composition is fixed:** the column header renders exactly
`toColumnCaption({ name, taskCount })` → `"{NAME} ({N})"`, uppercased via the `uppercase` utility
(not by transforming the stored name). The name truncates; the `({N})` count never does — see UI
Considerations → long-text.

| Role | Token(s) | Light | Dark | Usage |
|------|----------|-------|------|-------|
| Dominant (60%) | `--color-bg-app` | `#F4F7FD` | `#20212C` | Board canvas behind the columns; the sticky column-header backdrop |
| Secondary (30%) | `--color-bg-surface` | `#FFFFFF` | `#2B2C37` | Modal panels (Add/Rename/Delete Column), `Menu` popup surface, task-card surfaces |
| Accent (10%) | `--color-bg-primary` / `--color-bg-primary-hover` | `#635FC7` / `#5854BE` | `#635FC7` / `#5854BE` | See reserved-for list below |
| Destructive | `--color-bg-danger` / `--color-bg-danger-hover`, `--color-text-danger` | `#C93F3C` / `#B23632` | `#C93F3C` / `#B23632` | Destructive actions only — see reserved-for list below |

### New tokens this phase adds (five)

These are the only new color values this phase is authorized to introduce. All five were sampled
this session by decoding `pdftoppm` renders of PDF **p3** (light) and **p13** (dark) at 1100px
width — falsifiable by re-running the same render and re-sampling the same coordinates.

| Token | Light | Dark | Evidence |
|-------|-------|------|----------|
| `--color-accent-column-1` | `#49C4E5` | `#49C4E5` | p3/p13 @ (24,98) — identical in both themes |
| `--color-accent-column-2` | `#8471F2` | `#8471F2` | p3/p13 @ (253,98) — identical in both themes |
| `--color-accent-column-3` | `#67E2AE` | `#67E2AE` | p3/p13 @ (487,98) — identical in both themes |
| `--color-bg-column-add-from` | `#E9EFFA` | `#23242F` | Ghost-column gradient top stop; p3 @ (822,130) = `#E9EFFA`, p13 @ (822,130) = `#22232E` ≈ `grey-700` at 25% over `bg-app` |
| `--color-bg-column-add-to` | `#EEF3FC` | `#21222D` | Ghost-column gradient bottom stop; p3 @ (822,740) = `#EEF2FB`, p13 @ (822,740) = `#21222D` (exact) |

**The gradient stops are declared as pre-composited flat hex, not as alpha.** The PDF's source
gradient is `#E9EFFA → rgba(233,239,250,0.5)` (light) and `rgba(43,44,55,0.25) → rgba(43,44,55,0.125)`
(dark), but Style Dictionary's existing config emits flat hex colors and every other token in
`tokens.css` is flat hex. Compositing the alpha against the known `--color-bg-app` canvas at
authoring time keeps the pipeline uniform and keeps the value directly assertable in a test. The
placeholder therefore renders as
`bg-[linear-gradient(180deg,var(--color-bg-column-add-from)_0%,var(--color-bg-column-add-to)_100%)]`
and must **not** be layered over anything other than `--color-bg-app`.

**The three dot colors are purely decorative and must be `aria-hidden="true"`.** No information is
carried by hue alone — the column's identity is its adjacent text caption — so these three values
are exempt from a text-contrast requirement, and the checker should read them as decoration, not as
a fourth/fifth/sixth semantic color. They are assigned by hashing the column's **id** into
the three tokens (U-03), a pure function that belongs in `features/boards/model.ts` per
CONVENTIONS.md's `model.ts` rule, so the mapping is assertable without rendering.

**Keyed by id, not by position — this was corrected on 2026-08-27 and must not be reverted.** The
original reading of U-03 was `position % 3`, and it shipped that way. The backend renumbers
positions contiguously on delete (03-BACKEND-FACTS R2/R3), so a position-keyed hue repaints every
column after the deleted one: deleting the first of four columns was measured live recolouring all
three survivors at once. A hue that changes in response to an edit elsewhere reads as a bug to a
user who has learned "Done is the green one". An id is immutable for the column's lifetime. The
visible cost is that the three accents are no longer guaranteed to appear in order, or at all, on a
board with few columns — accepted deliberately, because the dot carries no meaning the caption does
not already carry.

### Accent reserved for (explicit list — never "all interactive elements")

Carried forward from 02-UI-SPEC.md items 1-5 (sidebar selected row, `+ Create New Board`, primary

### Destructive reserved for

Carried forward from 02-UI-SPEC.md items 1-3, **plus this phase's two additions**:

   already applies `text-text-danger` at `menu.tsx:91`).
5. The `Delete this column?` confirmation modal — title text color and the `Delete Column` button's
   fill (`Button variant="destructive"`, already implemented).

Column-mutation error toasts reuse the existing `Toast` error treatment established in Phase 2
(D-04/D-09/D-15) with no new color.

**Deviations already baked into `tokens.css` (do not re-derive):** the PDF's raw destructive red
(`#EA5555`/`#FF9898`) and its light-mode-only accent hover (`#A8A4FF`) were contrast-adjusted during
Phase 1 to `#C93F3C`/`#B23632` and a single `#5854BE` hover shared by both themes. Likewise the
PDF's muted grey `#828FA3` is `--color-text-muted` in dark but `#66707F` in light. New components

PDF's `#828FA3`.

The header is **not** draggable and offers **no** keyboard lift (`draggable` off, sensor disabled, no `aria-roledescription`) — a lone column has nowhere to go, and an affordance that visibly does nothing is the dead-control failure this codebase already refuses at `board-view.tsx:14-18`. |
| long-text | Column name in the Add / Rename modals | ✅ covered | The existing `columnNameSchema` (`schemas.ts:114`) already mirrors the backend's 3-32 bound, and `TextField`'s established truncation convention applies to the input value. |
| long-text | Delete-confirm body with a 32-char column name | ✅ covered | Prose, so it wraps rather than truncating — `Modal.Description` with `break-words`, the exact treatment `delete-board-confirm.tsx:49` already uses for the same reason. |

## Interaction Notes (non-template, phase-specific)

### Column header anatomy and semantics

The header becomes three elements in one 44px-min-height flex row, replacing today's bare `<h2>`
(`board-view.tsx:44-49`):

```
<h2 id="board-column-{id}">          ← keeps the section's aria-labelledby target
  <button type="button">             ← the drag handle (U-02); contains dot + caption
    <span aria-hidden="true" />      ← the id-keyed dot (decorative, U-03)
    {NAME} ({N})                     ← toColumnCaption(), `uppercase`, name truncates
  </button>
</h2>
<IconButton                          ← kebab; sibling of the h2, not inside the button
  variant="ghost" size="md"
  icon={<EllipsisVertical />}
  label="Column actions for {NAME}" />
```

A `<button>` nested inside an `<h2>` is valid and keeps the heading available as the section's
accessible name. The header keeps its shipped `sticky top-0 bg-bg-app pb-6` treatment so rows scroll
under it.

**Remove the section's `tabIndex={0}`** (`board-view.tsx:41`). It exists solely to satisfy axe's
`scrollable-region-focusable` on a scroll region with no focusable content — a condition this phase
ends by putting a real button in the header. Leaving it would add a redundant tab stop in front of
every column.

**The kebab must not initiate a drag.** It sits inside the draggable header row, so the drag sensor
needs an activation constraint (a small pointer-distance or press-delay threshold) *and* the kebab
must stop pointer-event propagation. A plain click on the kebab opening a drag instead of the menu
is the single most likely regression here and should be an explicit acceptance criterion.

### Reorder (U-02)

- **Pointer:** press and drag anywhere on the header button. `cursor-grab` at rest,
  `cursor-grabbing` while held.
- **Keyboard:** focus the header button → `Space` lifts → `←`/`→` move one position → `Space` drops
  → `Esc` cancels and returns the column to its original index. While lifted, the handle carries
  `aria-roledescription="draggable column"` and `aria-pressed="true"`; every transition is announced
  through a polite `aria-live` region using the Copywriting Contract's announcement strings.
- **Wire mapping:** one `PATCH /boards/{boardId}/columns/{columnId}/reorder` per *completed* move
  carrying `{ version, targetPosition }` (0-based). Intermediate arrow-key steps are local only —
  a request per keystroke would burn versions and 409 against itself. The PATCH fires on drop, once.
- **Optimism:** the reordered array renders immediately; on failure the whole board's order rolls
  back (see UI Considerations → error/reorder).

### The `+ New Column` ghost column

Measured from PDF p3 (light) and p13 (dark) at a 1440pt page width:

- **280px wide** (identical to a real column, `w-70`), spanning the full height of the tallest
  column, as the **last** flex child of the existing horizontal scroll row.
- **Vertical gradient**, `--color-bg-column-add-from` → `--color-bg-column-add-to`, 180deg.
- **`rounded-md` (8px).** ~~`rounded-lg` (28px), a known deliberate deviation from the PDF's ~6px
  corner, kept so the placeholder would not be the only surface on the board with its own radius.~~
  **Superseded 2026-08-29.** The deviation's premise was that the shipped 28px was right and the
  PDF's ~6px was the outlier. It was the reverse: every radius token had been converted with
  `600/96 = 6.25` when the mock is a 1440px-wide design needing `12000/1440 = 8.3333`, so the whole
  scale read 1.333x too large, and two of its three slots were spent on *pills* (the mock's buttons
  are `height/2` by construction, which CSS clamping made look correct). The scale was re-derived
  during plan 04-12 — `sm: 4px` controls, `md: 8px` surfaces, buttons on `rounded-full` — so the
  placeholder now matches both the PDF and every other surface at once, which is what this note
  wanted and could not have at 28px.
- **Label** `+ New Column`, `heading-xl` (24px/700), `text-text-muted`, centered on both axes.
- **It is a real `<button>`**, full-bleed inside the placeholder, opening `AddColumnModal`. It is
  **not** a drop target for column reorder — dropping a column "on" the add-column affordance has no
  meaningful semantics, so the drop indicator never appears to its left or right beyond the final
  inter-column gutter.
- Hover/focus-visible swaps the label to `--color-bg-primary` (accent reserved-for item 7) and the
  focus ring is the global `--color-ring-focus`, as on every other primitive.

### Divergence from the PDF's `Board Columns` section (U-01)

PDF p9's `Edit Board` modal manages columns as a batch — rows with `×` remove, `+ Add New Column`,
one `Save Changes`. **This phase does not build that.** Per U-01 the shipped `EditBoardModal` stays
board-rename-only and gains no `Board Columns` section. The PDF's *visual anatomy* for that section
is still honoured where it maps onto per-column equivalents: the `Column Name` field is the same
`TextField` treatment, and `+ Add New Column` keeps its exact PDF wording in the empty state. What
is not carried over is the batching mechanic and its single `Save Changes` across N columns.

Consequence for `AddBoardModal`: it is untouched by this phase. It already collects initial column
names at board-create time (BOARD-02, D-02) through a different, already-shipped path, and the two
must not be merged.

### Toast reuse

No new toast anatomy. Column-mutation failures reuse the `Toast` established in Phase 2
(`bg-bg-surface`/`shadow-lg`/`rounded-lg` with a `--color-bg-danger` accent), and Base UI's
`Toast.Viewport` already renders its own `aria-live="polite"` region. **The reorder live-region
announcements are a separate region from the toast viewport** — they are frequent, transient
position reports, and routing them through the toast stack would bury real errors.
