<objective>
Replace two repeated ad-hoc primitives with one shared construct each: the result/status discriminant
retyped as a bare literal across 18 files becomes a single `RESULT_STATUS` enum-like constant, and
the hand-rolled boolean `useState` pair becomes `usehooks-ts`'s `useBoolean`.

Purpose: both are the same defect in two shapes — a value or a pattern with no single declaration, so
a change means N independent edit sites and a typo in any one of them is a silent unmatched branch
rather than a type error. CONVENTIONS.md already states both rules (commit `dc63dc5` for the status
one); neither has a shared construct behind it yet. This lands before the remaining feature plans
(02-11 board detail, 02-12 rename, 02-13 delete) so those three are written against the replacement
pattern rather than adding three more instances of the one being replaced.
Output: `src/lib/core/api-contract/result-status.ts`, 18 migrated call sites, `usehooks-ts` as a
pinned dependency, four migrated boolean-state call sites, and a CONVENTIONS.md rule for the latter.
</objective>

  <name>Task 1: Settle the shared status constant's public shape before 18 files depend on it</name>
  <decision>
    The public shape of the shared status constant — its member set, its runtime values, and its
    module. Once 18 files import it, changing any of the three means touching all 18 again, so it is
    settled before the migration rather than during it.
  </decision>
  <context>
    Six distinct discriminant spellings exist today, counted directly from the tree on 2026-08-25:

    | Spelling | Declared in |
    |----------|-------------|
    | `ok` | `fetch-boards.ts`, `app/(dashboard)/layout.tsx` |
    | `success` | `create-board.ts`, `create-board-columns.ts`, `update-theme.ts`, and their three stubs |
    | `error` | all 18 files |
    | `unauthenticated` | `fetch-boards.ts`, `create-board.ts`, `create-board-columns.ts`, two stubs |
    | `invalid` | `create-board.ts`, `create-board-columns.ts`, two stubs |
    | `idle` | `action-state.ts` and the three auth stubs |

    `ok` and `success` are the same concept spelled two ways; unifying them is part of the point of a
    shared constant, and is the change with the widest blast radius.

    Two in-repo precedents govern the casing question, both following ADR tech/0012: `THEME =
    { LIGHT: "LIGHT", DARK: "DARK" }` and `PROBLEM_CODE = { VALIDATION_FAILED: "VALIDATION_FAILED", ... }`.
    Both use SCREAMING_SNAKE keys AND values, which ADR tech/0012 requires ("Keys and values are both
    SCREAMING_SNAKE_CASE and identical"). `COOKIE` is the only lowercase-valued constant and only
    because its values are externally-dictated cookie names. Nothing serialises a status discriminant
    to storage, to the backend, or to any consumer outside this app — the values cross the RSC wire
    but both ends ship together — so changing their casing is safe.

    Recommendation: **option `asvs-aligned`**. It is the only option that satisfies ADR tech/0012 as
    written and matches both existing precedents, and the casing change costs nothing extra because
    every one of the 18 sites is being edited regardless.
  </context>
  <options>
    <option id="asvs-aligned">
      <name>One constant, SCREAMING_SNAKE values, `ok` folded into `SUCCESS`, at `src/lib/core/api-contract/result-status.ts`</name>
      <pros>
        Obeys ADR tech/0012 verbatim and reads identically to `THEME` and `PROBLEM_CODE` two
        directories away. `Object.values()` and the literal string stay interchangeable, which is the
        stated reason ADR tech/0012 wants matching keys and values. Placement matches CONVENTIONS.md's
        placement rule step 8 — a pure, framework-agnostic module in `lib/core/` under the
        `api-contract/` concern that already holds `problem-detail.ts` and `external-paths.ts`, and
        which the `eslint-plugin-boundaries` policy lets every ring import. One member set covers all
        five branches: `SUCCESS`, `ERROR`, `UNAUTHENTICATED`, `INVALID`, `IDLE`.
      </pros>
      <cons>
        Every runtime value changes case, so no call site can be migrated by adding an import alone —
        each has to be read and rewritten. `IDLE` is a client form-state value living beside four
        server-result values in one constant, which is a mild conflation.
      </cons>
    </option>
    <option id="preserve-values">
      <name>One constant, lowercase values preserved, `ok` folded into `success`</name>
      <pros>
        The runtime values on the wire and in every serialised `useActionState` payload are byte-for-byte
        unchanged except for the `ok`-to-`success` fold, so the diff is smaller and a mid-migration
        state is less likely to be observably broken.
      </pros>
      <cons>
        Contradicts ADR tech/0012's explicit key-equals-value rule and diverges from both existing
        precedents in the same `lib/core/` tree, which is exactly the drift a shared constant exists to
        prevent. Would need its own recorded carve-out to not read as an oversight.
      </cons>
    </option>
    <option id="split-consts">
      <name>Two constants — `RESULT_STATUS` for server-result branches, `FORM_STATUS` for the client `idle`/`error` pair</name>
      <pros>
        Keeps the auth forms' `useActionState` vocabulary separate from Server Action result branches,
        which are genuinely different axes. `AuthActionState` never has a success member (success
        redirects), so it never wants four of the five values.
      </pros>
      <cons>
        `error` then exists in two constants with the same value, which reintroduces the exact
        duplication this plan removes, one level up. `AuthActionState` is the only consumer of the
        second constant, so it buys separation for one type at the cost of a second source of truth.
      </cons>
    </option>
  </options>
  <resume-signal>Select: asvs-aligned, preserve-values, or split-consts. If you want a different member set, module path, or a value-casing rule other than the three above, say so instead and the migration will follow that.</resume-signal>
</task>
