<objective>
Deliver BOARD-05: delete a board, cascading to its columns, tasks and subtasks, behind a plain
confirm modal, with the redirect behaviour D-08 defines for the case where the deleted board was the
one being viewed.

Purpose: this is the phase's only irreversible operation. ADR domain/0002 makes the cascade hard —
no undo, no soft delete — so the confirm modal is the entire safety mechanism, and the deliberately
non-optimistic ordering D-09 specifies exists so a failed delete never makes a board look gone when
it is not. With this plan all six of BOARD-01 through BOARD-06 are delivered.
Output: the delete Server Action, two pure redirect helpers, the non-optimistic delete hook, the
confirm modal, the menu wiring, and an end-to-end proof of the cascade and the redirect.
</objective>

## Currency note (why this plan was regenerated)

The 2026-08-20 version of this plan built BOARD-05 on a `app/api/boards/[boardId]/route.ts` Route
Handler and a `useDeleteBoard` hook doing query-cache surgery on success — cancelling in-flight
queries, writing the shortened list back with `setQueryData`, and removing the deleted board's
full-board cache entry. Phase 02.1 banned Route Handlers and deleted that cache entirely
(docs/adr/tech/0019); board and full-board reads are server-rendered per request now. This plan
delivers the same D-06 through D-09 behaviour on that architecture: a Server Action plus `refresh()`
removes the row, and the client's only remaining job is moving the user if they were viewing the
board that went away.

## Review dispositions (02-REVIEWS.md)

| Finding | Severity | Disposition | Where it landed |
|---------|----------|-------------|-----------------|
| `useDeleteBoard` calls `removeQueries` without a preceding `cancelQueries`, so an in-flight full-board fetch can resolve afterwards and silently repopulate the deleted board's cache entry | HIGH | **moot on the current architecture, recorded not dropped** | The finding was correct against the query-cache design it reviewed. Phase 02.1 removed every client-side board read (docs/adr/tech/0019 Consequences: reads never go through a client query, so there is no cache entry to repopulate), so no in-flight client fetch of board or full-board data exists to lose the race to. This plan's hook performs no cache work at all, which Task 1's grep for the absence of an optimistic hook and this table together record deliberately — so a future reader does not mistake the missing cancellation for the gap this review found. The underlying property the finding protects — a deleted board can never reappear — is instead proved by Task 3's reload assertion against the real backend. Threat T-02-68 carries the same reasoning. |
