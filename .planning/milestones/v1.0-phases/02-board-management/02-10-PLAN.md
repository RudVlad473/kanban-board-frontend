<objective>
Deliver BOARD-02: a signed-in user creates a board, optionally naming its initial columns, and it
appears in the sidebar immediately.

Purpose: this is the phase's most intricate flow and its first write path. There is no bulk-create
endpoint — the board create request body accepts only a name — so creation spans one board create
plus one column create per named row, sequentially, with a defined partial-failure outcome
(ADR domain/0003, D-03/D-04/D-05). It is also the first place `refresh()` from `next/cache` has to
carry a mutation's result back into the persistent dashboard layout.
Output: two Server Actions, the domain's Zod schemas and one pure model helper, the orchestrating
client hook, the create-board modal, the sidebar entry point, and an end-to-end proof.
</objective>

(`app/api/boards/route.ts` and `app/api/boards/[boardId]/columns/route.ts`), a `boards-api.ts` fetch
wrapper, and a TanStack Query cache prepend into `useBoards()`'s `["boards"]` entry. Phase 02.1

RSC-fed (docs/adr/tech/0019). This plan delivers the same D-01 through D-05 behaviour on the
replacement architecture: Server Actions plus `refresh()` in place of Route Handlers plus a cache
prepend. Newest-first ordering needs no client-side cache write here — `load-boards.ts` already
reverses the backend's creation-order array, so a `refresh()` after a create puts the new board at the
top on its own.
