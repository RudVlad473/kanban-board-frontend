<objective>
Close the folded pending todo "Clear the theme cookie on sign-out" (FT-01) and finish the
prerequisite scope by writing the PC-04 and PC-05 rules into CONVENTIONS.md.

Purpose: the non-httpOnly `theme` cookie currently survives sign-out, so on a shared browser a
second account can briefly render the first account's theme (Phase 1 code review WR-02). Clearing
it alone is NOT a complete fix — `app/layout.tsx` resolves the pre-paint `dark` scope from that
cookie and nothing else, so a cleared cookie would make every fresh sign-in render light regardless
of the account's stored preference. The correct fix is symmetric: clear on sign-out, write from
`identity.theme` on sign-in and sign-up.
Output: symmetric theme-cookie lifecycle in the three auth actions, a strengthened THEME-01
end-to-end assertion that would actually catch the regression, and CONVENTIONS.md brought up to
date with PC-01 through PC-05.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| shared browser profile → Next.js server | Two different accounts may use the same browser profile in sequence; state left behind by the first is visible to the second |
| browser → Server Action endpoint | Sign-in/sign-up/sign-out are invokable over the wire with arbitrary bodies |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-18 | Information Disclosure | `theme` cookie surviving sign-out (Phase 1 WR-02) | low | mitigate | `signOutAction` calls `themeCookie.clear()` alongside `session.destroy()`, so no preference belonging to the previous account is readable by the next one on a shared profile. Asserted by Task 1's unit test and Task 2's end-to-end cookie-absence poll. Severity is low: the cookie carries a display preference, not a credential or any account-identifying value (T-01-35). |
| T-02-19 | Tampering | Theme value written at sign-in | medium | mitigate | The write takes `identity.theme` from the guarded upstream record (`isSessionPayload`), never a value from the submitted `FormData` — a caller cannot use sign-in to plant an arbitrary cookie value. Task 1's behavior block and unit assertions pin the source. |
| T-02-20 | Spoofing | Cookie write on a failed sign-in | medium | mitigate | The write sits after the failure branch has already returned, so a rejected attempt writes nothing and cannot signal to an observer that a given email exists (the same anti-enumeration property T-01-08 protects). Task 1's failure-branch tests assert the write did not happen. |
| T-02-21 | Denial of Service | Third concurrent session in the THEME-01 spec | medium | mitigate | The backend caps one account at two concurrent sessions and refuses a third with an indistinguishable 401. Task 2 explicitly forbids adding a second test block or a `createFixtureAccount` call, and its acceptance criteria assert the spec still holds exactly one `test(` invocation. |
</threat_model>
