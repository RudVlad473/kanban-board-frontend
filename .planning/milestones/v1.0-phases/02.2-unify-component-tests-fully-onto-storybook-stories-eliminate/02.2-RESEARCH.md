### Locked Decisions

**Rendering strategy — reversing ADR tech/0021**
- **D-01:** Full reversal of ADR tech/0021's `.run()` decision. Every component test (not just
  today's hand-rendered ones) stops calling composeStories' `.run()` and instead renders the
  composed story directly (e.g. `render(<Empty />)` via `vitest-browser-react`, the "pre-10.x
  pattern" tech/0021 explicitly rejected). Planning/execution must author a new ADR that
  **supersedes tech/0021**, not just amend it — tech/0021's existing text stays as history (matches
  this project's own `⊘ Superseded` convention already used for ADR tech/0004). — **Reversibility:**
  one-way — every existing `.test.tsx` file using `.run()` must be rewritten, and a new ADR
  formally reverses a previously Accepted decision; undoing this again would mean a second
  reversal.
- **D-02:** Rationale for the reversal (goes in the new ADR's Decision Drivers): `.run()` is an
  opaque helper — tests can't see or control the exact rendered React tree, which makes deep
  interaction assertions (e.g. the real-`FormData`-on-submit test, event-listener attachment)
  awkward or impossible. This is the stated reason, not "two render mechanisms colliding" (that
  symptom is real but secondary).
- **D-03:** Rendering a composed story directly pulls in that story's own decorators (`AuthCard`
  for `SignInForm`, the flex-height wrapper for `Sidebar`, the outline wrapper for `ThemeToggle`)
  plus the global `QueryProvider`/theme decorators from `.storybook/preview-annotations.tsx`.
  Decision: **render through the decorators** for interaction/deep tests too — this is closer to
  real production usage — rather than adding decorator-free story variants.
- **D-04:** Centralize the `afterEach(() => { document.body.innerHTML = ""; })` cleanup currently
  copy-pasted per test file into one global `afterEach` in `vitest.setup.ts`'s "browser" project,
  now that there's only one rendering mechanism.
- **D-05:** "No play functions in stories" (already true — 0 of 17 `*.stories.tsx` files use
  `play:`) becomes a **blocking, mechanically-enforced rule**, matching this project's established
  pattern (tech/0020's `no-restricted-properties` ESLint rule, tech/0023's comment-length check) —
  not just a documented convention.
- **D-06:** `.run()` itself also gets blocking ESLint enforcement (banned outside `*.stories.tsx`,
  matching the same mechanical-enforcement pattern), so a future contributor can't reintroduce it
  once the new ADR supersedes tech/0021.

**Action-stub reconciliation with the no-mock policy**
- **D-07:** Direction is to **replace the `*-action-storybook-stub.ts` no-op fakes with real Server
  Action calls** (against the real nonprod backend) rather than sanctioning the whole-module-alias
  as a documented D-19-style carve-out. — **Reversibility:** costly.
- **D-08 (research gate):** Because Server Actions normally require a real Next.js server runtime
  to execute at all, **this is the #1 open research question for `/gsd-plan-phase`'s research
  step**: confirm whether Server Actions can execute for real inside Storybook/Vitest Browser Mode
  before committing implementation to "replace stubs with real calls." **RESOLVED BELOW — see
  Summary and "Server Action execution feasibility" in Architecture Patterns: infeasible.**
- **D-09 (fallback, if D-08's research finds it infeasible):** Move the interaction coverage that
  needs the real action's effect (redirect, cookie write, backend rejection) out of Storybook-driven

- This applies to all four actions: `sign-in`, `sign-up`, `sign-out`, `update-theme`.

## Summary

This phase is a testing-architecture refactor, not new product code — every finding below is
grounded in this repository's own source files (read this session) plus two verified external
facts. The two external facts carry the plan's biggest risk if gotten wrong, so they were checked
against primary sources rather than assumed:

1. **`composeStories`' output is directly JSX-renderable, decorators included** — this is a
   currently-documented Storybook pattern (`render(<Primary />)`), not a "pre-10.x" relic that
   vanished from the framework. Storybook's own docs still ship this exact pattern for both Jest and
   Vitest portable-stories testing in the current major version. D-01's reversal is executing a
   still-supported, still-documented API path, not fighting the framework. [CITED:
   github.com/storybookjs/storybook/blob/next/docs/_snippets/portable-stories-jest-compose-stories.md]

2. **D-08's research gate resolves to infeasible — real Server Actions cannot execute inside
   Storybook's Vitest-driven rendering.** `@storybook/nextjs-vite` (the framework package this
   project's `.stories.tsx` files already import `Meta`/`StoryObj` from) has a known, currently-open
   gap in `"use server"` handling: its Vite bundling attempts to bundle server-only code (reaching
   `node:crypto`, database/HTTP clients, etc.) into the browser bundle, which fails outright — this
   is exactly the failure this project's own `serverActionStubAlias` in `vitest.config.ts` was built
   to route around in the first place. No plugin ships this support yet; the two documented
   workarounds are (a) mock/stub the action (what this project already does) or (b) refactor the
   action into a fetchable Route Handler (which CONVENTIONS.md's `docs/adr/tech/0019` explicitly
   bans project-wide). **D-09's fallback is therefore the only viable path**: keep the no-op action
   stubs for shallow/visual story rendering, and move every assertion that depends on the action's
   real effect (redirect, cookie write, backend-rejection message) into Playwright e2e, which runs
   against a real Next.js server. [CITED: github.com/storybookjs/storybook discussion #31127 —
   "Help with mocking server actions & database client instance"]

Beyond these two, this research corrects three scope estimates in CONTEXT.md against the actual
codebase (verified by reading files, not assumed): the `.run()`-elimination scope is **16 files /
~79 call sites**, not just the 5 hand-rendered ones; the `afterEach(() => { document.body.innerHTML
= ""; })` cleanup D-04 centralizes is already copy-pasted in **11 files**, not 5; and
`board-list.test.tsx` is an **undocumented tenth consumer** of the `next/headers`/`next/navigation`
D-19 shim family, missing from ADR tech/0020's Surviving Mock Register entirely (it postdates the
register's last generation) — this affects both D-12's "down to 1 file" prediction and D-16's
register-amendment task.

**Primary recommendation:** Sequence this phase in the order CONTEXT.md's own decision groups
suggest (D-01..D-06 rendering-mechanism unification first — it touches every file and de-risks
everything downstream; D-13..D-16 cookie-to-e2e migration next, since it determines D-12's real
scope; D-10..D-12 boilerplate consolidation last, sized against what's actually left; D-07/D-11's
action-stub barrel can land any time, independent of the others).

### Pattern 1: Direct composed-story rendering (replaces `.run()`)

**What:** Render a composed story's output as JSX through `vitest-browser-react`'s `render()`,
instead of calling the story's own `.run()` method.

**When to use:** Every `*.test.tsx` file in the "browser" Vitest project, for both shallow
(structural/copy) and deep (interaction) assertions — per D-03, decorators are inherited either way.

**Example (verified current pattern — Storybook's own docs, React Testing Library form; this
project substitutes `vitest-browser-react`'s `render` for RTL's, matching how `render-with-
providers.tsx` already does it today):**
```tsx
// Source: github.com/storybookjs/storybook/blob/next/docs/_snippets/portable-stories-jest-compose-stories.md
// (pattern confirmed current for Storybook 10.x's composeStories output; adapted to this
// project's vitest-browser-react render + Vitest test() import)
import { composeStories } from "@storybook/react";
import { screen } from "@testing-library/react";
import { expect, it } from "vitest";
import { render } from "vitest-browser-react";

import * as stories from "./sidebar.stories";

const { Expanded } = composeStories(stories);

it("renders the brand mark when expanded", async () => {
    // Act — decorators (QueryProvider, theme, flex-height wrapper) inherited automatically,
    // same as .run() provided (D-03).
    await render(<Expanded />);

    // Assert
    expect(screen.getByText("kanban")).toBeInTheDocument();
});
```

**Overriding args on a direct render** (needed for any test that today calls
`Story.run({ args: {...} })`):
```tsx
// Source: composeStories' composed story exports are React components whose default props ARE
// the story's args — passing JSX props merges over them (documented Jest-portable-stories pattern).
await render(<Filled password="overridden" />);
```

### Pattern 2: Server Action stub stays a real module, not a `vi.mock` (D-07/D-09)

**What:** The `*-action-storybook-stub.ts` files remain whole-module aliases
(`vitest.config.ts`'s `serverActionStubAlias`) rather than being replaced by real network calls,
because Storybook's Vitest-driven rendering cannot execute `"use server"` for real.

**When to use:** Any story/composed-story test whose component imports a Server Action.

**Rationale confirmed this session (not assumed):** `@storybook/nextjs-vite`'s Vite bundling has no
RSC-aware transform for `"use server"` exports — it tries to bundle the action's real dependency
graph (which reaches `node:crypto`, the external API client, etc.) into a page the browser has to
load, which fails. This is a currently open, named gap in Storybook's own issue tracker, not a
version-specific bug already fixed. [CITED: github.com/storybookjs/storybook discussion #31127]

**What changes under D-09 instead:** any assertion in today's hand-rendered tests that depends on
the stub's *effect* (e.g. `sign-out-button.test.tsx`'s `signOutActionCallCount()` poll) needs a new
home. A real counter on a stub module (not a `vi.fn()`) can still prove "the button's `formAction`
wired to the stub and the stub was invoked once" — that's a shallow/structural claim about the
component's own wiring, not a claim about the *real* action's effect, so it can stay in the
component test. What must move to e2e is anything claiming the *real* action's effect (a real
redirect happened, a real cookie was written, a real backend rejection produced this exact
message) — see Runtime State Inventory below for the file-by-file disposition.

### Pattern 3: Centralized `vi.mock` with a shared mutable handle (D-10b)

**What:** One shared module registers `vi.mock("next/headers", ...)` once; individual test files
that need a specific fake cookie value import a shared `vi.fn()` handle and call `vi.mocked(handle)
.mockReturnValueOnce(...)` rather than redeclaring the whole mock factory.

**When to use:** Only if ≥2 files still need the `next/headers`/`next/navigation` shim after D-13's
e2e migration lands — run the consumer-count check in Common Pitfalls §3 first.

**Mechanism (Vitest's own hoisting contract — `vi.mock` calls are hoisted to the top of the file
they're declared in, not shared automatically across files):**
```ts
// src/test-utils/next-headers-mock.ts — NOT auto-registered; each consuming file still calls
// vi.mock() itself (Vitest doesn't hoist across files), but delegates the factory body here.
import { vi } from "vitest";

export const cookiesMock = vi.fn();

// consuming-file.test.ts
import { vi } from "vitest";
```

### Pattern 4: Playwright cookie injection for edge-case coverage (D-15)

**What:** Use `browserContext.addCookies()` to place a malformed/expired/tampered cookie directly,
bypassing the UI, then navigate and assert the real server's real rejection.

**When to use:** Any edge case today covered by directly constructing a bad JWT/cookie value and
handing it to the mocked `cookies()` jar (`session.test.ts`'s verification-failure cases,
`cookie-client.unit.test.ts`'s tampered-value case).

**API surface (Node.js `BrowserContext.addCookies`):**
```ts
// Source: playwright.dev/docs/api/class-browsercontext (addCookies) — Node.js API reference
await context.addCookies([
    {
        name: "session",
        value: tamperedJwt, // e.g. a real JWT with the signature segment corrupted
        domain: "localhost", // or the deployed preview host
        path: "/",
        httpOnly: true,
        secure: true,
        sameSite: "Lax",
    },
]);
await page.goto(ROUTE.BOARDS);
// Assert the real server's real rejection — e.g. redirected to sign-in.
```
Either `url` or both `domain` and `path` are required per Playwright's own API contract. [CITED:
playwright.dev/docs/api/class-browsercontext]

### Anti-Patterns to Avoid
- **Writing a decorator-free story variant just to keep an interaction test "shallow":** D-03
  explicitly rejects this — render through the real decorators even for deep tests, since that's
  closer to production usage and avoids a second, decorator-free rendering surface diverging from
  the first.
- **Reaching for `no-restricted-properties` to ban `.run()`:** see Common Pitfalls §2 — the object
  name varies per file (`Empty.run()`, `Light.run()`, …), so the existing `vi.mock`/`vi.spyOn`
  enforcement mechanism (which matches on a fixed `{object, property}` pair) cannot express this
  ban; it needs a `no-restricted-syntax` selector on `property.name`, not `no-restricted-properties`.
- **Assuming the action-stub replacement (D-07) is still open for implementation:** it is not — the
  research gate (D-08) is closed by this document; the fallback (D-09) is the confirmed path.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Rendering a composed Storybook story with overridden props | A custom prop-merge wrapper around the composed story | JSX prop spreading directly on the composed component (`<Filled password="x" />`) — composeStories' output already merges JSX props over story args, this is a documented, current pattern | Reinventing this duplicates behavior Storybook's own portable-stories implementation already provides and keeps in sync with story authoring |
| Faking a Next.js request scope to execute a Server Action for real in a browser test | A custom Vite plugin stubbing `"use server"` transforms (the community workaround mentioned in the Storybook discussion) | Keep the existing whole-module alias stub (D-09) and prove the real effect via Playwright e2e instead | Building/maintaining a custom RSC-transform plugin is a much larger, fragile undertaking than this phase's scope — Storybook's own maintainers haven't shipped this yet either |
| Injecting a malformed/expired session cookie to test the real rejection path | Hand-rolling a fetch-based cookie injection script, or standing up a second fake server | Playwright's built-in `context.addCookies()` | Already the framework-native mechanism for exactly this use case; no maintenance burden beyond what e2e already carries |

**Key insight:** every "don't hand-roll" item above resolves to "use what the framework you're
already standardized on already documents" — this phase's biggest risk was building custom
machinery (a Vite plugin, a hand-rolled cookie injector) to route around a documented limitation
that has a documented, framework-native answer once traced back to the primary source.

## Common Pitfalls

### Pitfall 1: `.run()` elimination is a ~79-call-site change across 16 files, not just the 5 hand-rendered ones

**What goes wrong:** Scoping this task against CONTEXT.md's "5 files" framing (which refers only to
the `renderWithProviders` deletion) under-sizes the actual `.run()` rewrite.

**Why it happens:** `.run()` predates the hand-rendered/composed split — it's the *only* rendering
mechanism in every UI-primitive test (`button.test.tsx`, `checkbox.test.tsx`, `text-field.test.tsx`,
`switch.test.tsx`, `dropdown.test.tsx`, `modal.test.tsx`, `toast.test.tsx`, `menu.test.tsx`,
`icon-button.test.tsx`, `error-fallback.test.tsx`, `auth-card.test.tsx`, `board-list.test.tsx`)
in addition to the 5 files that also use `renderWithProviders` for their deep-interaction half.

**How to avoid:** Verified this session via `grep -rc "\.run(" src --include="*.test.tsx"` — 16
files call `.run()`, totaling roughly 79 call sites (`sign-up-form.test.tsx` alone has 10,
`sign-in-form.test.tsx` 8, most UI primitives 3-6 each). Size waves/tasks against this count, not
against the 5-file `renderWithProviders` list.

**Warning signs:** A plan that only lists the 5 `renderWithProviders` files as touched by the
`.run()` reversal is under-scoped — every other `*.test.tsx` file in `src/` also needs its `.run()`
calls converted.

### Pitfall 2: `no-restricted-properties` cannot express D-06's `.run()` ban — needs `no-restricted-syntax` instead

**What goes wrong:** Copying the existing `vi.mock`/`vi.spyOn` enforcement block (section 8d-2 of
`eslint.config.mjs`) verbatim and swapping in `.run` as the `property` doesn't work, because
`no-restricted-properties` matches on a **fixed `{object, property}` pair** — `vi.mock` always has
`vi` as the object. `.run()` is called on a different, dynamically-named object per test file
(`Empty.run()`, `Light.run()`, `Default.run()`, …), which `no-restricted-properties` cannot express.

**Why it happens:** The two existing enforcement mechanisms in this codebase target different AST
shapes: `no-restricted-properties` (fixed object+property) and `no-restricted-syntax` (arbitrary
selector, already used in this same file for `TSImportType` and the raw-`<a>` ban).

**How to avoid:** Use `no-restricted-syntax` with a `MemberExpression`/`CallExpression` selector on
`property.name`, ignoring the object:
```js
{
    selector: "CallExpression[callee.type='MemberExpression'][callee.property.name='run']",
    message: "composeStories' .run() is banned (docs/adr/tech/00XX, supersedes tech/0021) — render the composed story directly instead.",
}
```
scoped with `files`/`ignores` the same way section 8d-2 scopes the `vi.mock` ban (excluding
`*.stories.tsx`, though no story file calls `.run()` today anyway — the exclusion exists for parity
with the enforcement pattern, not because it's load-bearing).

**Warning signs:** An ESLint rule that "does nothing" (0 violations found even before the retrofit
sweep) when it should be flagging ~79 existing call sites is a sign the selector never matched the
right AST shape.

### Pitfall 4: Not every `next/headers`-mocking test file is actually testing cookie *writing/reading* — some are testing pure logic

**What goes wrong:** Treating D-13/D-14's "full e2e migration" as "delete the whole file" for every
one of the 9 `next/headers`-consuming files loses pure-logic coverage that has no natural e2e
equivalent test-per-assertion.

**Why it happens:** `cookie-client.unit.test.ts` (verified — read this session) tests
`createCookieClient`'s own behavior against an in-memory fake jar: option-merging (a per-call
`expires` override doesn't leak into the next call's options), and cross-client isolation (two
different cookie names never see each other's values). These are pure unit-level claims about one
module's internal correctness, not claims about what a real browser/server actually persists — an
e2e test *can* approximate them (toggle twice, inspect two different `Set-Cookie` headers) but at
much higher cost per assertion and with less precise failure localization. `session.test.ts`
(verified — read this session) similarly mixes pure JWT-shape assertions (payload doesn't leak the
raw user id, three dot-separated segments) with cookie-flag assertions (httpOnly/Secure/SameSite)
that do need a request scope.

**How to avoid:** The planner should decide, file by file, whether a "unit test of this module's own
logic, with the module's fake-jar parameter passed in directly rather than via a mocked
`next/headers` import" is a viable trimmed-down replacement (keeps the assertion fast and precise,
loses nothing D-13 actually objects to — no `vi.mock` of `next/headers` needed if the fake jar is
passed as a constructor/parameter instead of intercepted at the module boundary) versus deleting the
assertion outright in favor of an e2e-observable equivalent. This is a real design decision CONTEXT.md's
D-14 ("gutting/deleting most of the 8-file... register") anticipates but does not resolve
per-assertion — flag as a task-level decision, not a blocker.

**Warning signs:** A plan that deletes `cookie-client.unit.test.ts`'s isolation-by-name assertion
entirely with no e2e or refactored-unit-test replacement is a silent coverage loss the user did not
sign off on (D-14 confirmed "full scope" migration, not "delete without replacement").

### Pitfall 5: `@storybook/nextjs-vite` vs `@storybook/react` import source still matters after this phase

**What goes wrong:** Importing `composeStories`/`render` helpers from `@storybook/nextjs-vite` in a
rewritten `*.test.tsx` file, now that direct rendering makes the distinction feel less load-bearing.

**Why it happens:** The reason for the split is unchanged by this phase — `@storybook/nextjs-vite`'s
main entry still eagerly imports real Next.js internals that only resolve under the Vite plugin the
separate "storybook" Vitest project loads (`storybookTest()` in `vitest.config.ts`), which the
"browser" project (where every `.test.tsx` lives) does not load. This phase changes *what you do*
with the composed story (render directly vs. `.run()`), not *which package* composes it.

**How to avoid:** Every rewritten `.test.tsx` keeps `import { composeStories } from
"@storybook/react"` unchanged — the new ADR superseding tech/0021 must carry this exact import-
source guidance forward, not drop it as no-longer-relevant.

**Warning signs:** A `ReferenceError: process is not defined` or an unresolvable
`sb-original/image-context` error appearing in the "browser" project's test run after this phase's
rewrite is the exact symptom tech/0021 already documented for this mistake.
