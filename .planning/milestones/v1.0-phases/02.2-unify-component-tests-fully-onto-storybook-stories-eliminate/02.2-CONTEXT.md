# Phase 02.2: Unify component tests fully onto Storybook stories - Context

**Gathered:** 2026-08-22
**Status:** Ready for planning

<domain>
## Phase Boundary

This phase unifies every component test onto Storybook stories as the single rendering
mechanism, and resolves the four pending testing-pattern todos surfaced during Phase 2 that
Phase 02.2 was pulled forward to close before 02-10..13 add more instances of the patterns
under review:

- Eliminate `renderWithProviders` (`src/test-utils/render-with-providers.tsx`) and every
  hand-rendered test — 5 files (`sidebar.test.tsx`, `sign-in-form.test.tsx`,
  `sign-out-button.test.tsx`, `sign-up-form.test.tsx`, `theme-toggle.test.tsx`).
- Stop using composeStories' `.run()` — render composed-story output directly instead — for
  **every** component test, not just the ones currently hand-rendered. This is a deliberate
  reversal of ADR tech/0021's explicit `.run()`-over-direct-JSX decision (see D-01).
- Reconcile the `*-action-storybook-stub.ts` whole-module-alias exception with ADR tech/0020's
  no-mock policy.
- Decide the scope of test-boilerplate consolidation (action-stub barrel export, `next/headers`/
  `next/navigation` `vi.mock` centralization).
- Decide whether cookie-writing (and, as the discussion extended, cookie-reading) coverage moves
  from the `next/headers` D-19 shim to real e2e.

**Not in scope:** any new product capability (BOARD-\*/COLUMN-\*/TASK-\*/SUBTASK-\* requirements);
those remain Phase 2's.

</domain>

<decisions>
## Implementation Decisions

### Rendering strategy — reversing ADR tech/0021

- **D-01:** Full reversal of ADR tech/0021's `.run()` decision. Every component test (not just
  today's hand-rendered ones) stops calling composeStories' `.run()` and instead renders the
  composed story directly (e.g. `render(<Empty />)` via `vitest-browser-react`, the "pre-10.x
  pattern" tech/0021 explicitly rejected). Planning/execution must author a new ADR that
  **supersedes tech/0021**, not just amend it — tech/0021's existing text stays as history (matches
  this project's own `⊘ Superseded` convention already used for ADR tech/0004). — **Reversibility:**
  one-way — every existing `.test.tsx` file using `.run()` must be rewritten, and a new ADR
  formally reverses a previously Accepted decision; undoing this again would mean a second
  reversal.
- **D-02:** Rationale for the reversal (goes in the new ADR's Decision Drivers): `.run()` is an
  opaque helper — tests can't see or control the exact rendered React tree, which makes deep
  interaction assertions (e.g. the real-`FormData`-on-submit test, event-listener attachment)
  awkward or impossible. This is the stated reason, not "two render mechanisms colliding" (that
  symptom is real but secondary).
- **D-03:** Rendering a composed story directly pulls in that story's own decorators
  (`AuthCard` for `SignInForm`, the flex-height wrapper for `Sidebar`, the outline wrapper for
  `ThemeToggle`) plus the global `QueryProvider`/theme decorators from
  `.storybook/preview-annotations.tsx`. Decision: **render through the decorators** for
  interaction/deep tests too — this is closer to real production usage (`SignInForm` always
  renders inside `AuthCard`) — rather than adding decorator-free story variants.
- **D-04:** Centralize the `afterEach(() => { document.body.innerHTML = ""; })` cleanup
  currently copy-pasted in 5 test files into one global `afterEach` in `vitest.setup.ts`'s
  "browser" project, now that there's only one rendering mechanism (no more two-mechanisms-collide
  justification needed per file).
- **D-05:** "No play functions in stories" (already true — 0 of 17 `*.stories.tsx` files use
  `play:`) becomes a **blocking, mechanically-enforced rule**, matching this project's established
  pattern (tech/0020's `no-restricted-properties` ESLint rule, tech/0023's comment-length check) —
  not just a documented convention.
- **D-06:** `.run()` itself also gets blocking ESLint enforcement (banned outside
  `*.stories.tsx`, matching the same mechanical-enforcement pattern), so a future contributor
  can't reintroduce it once the new ADR supersedes tech/0021.

### Action-stub reconciliation with the no-mock policy

- **D-07:** Direction is to **replace the `*-action-storybook-stub.ts` no-op fakes with real
  Server Action calls** (against the real nonprod backend) rather than sanctioning the
  whole-module-alias as a documented D-19-style carve-out. This holds even though the real
  action/backend behavior is *already* proven elsewhere (`sign-in.integration.test.ts` etc.) —
  the user was presented that counter-argument explicitly and held the original position (the
  no-mock philosophy should apply to this test layer too, not just be satisfied by coverage
  existing somewhere else). — **Reversibility:** costly — reverting to a stub after building
  real-call-based stories/tests means re-introducing the alias and re-documenting the carve-out.
- **D-08 (research gate):** Because Server Actions normally require a real Next.js server
  runtime to execute at all (they compile to a POST to a framework-internal endpoint — the exact
  reason the stub exists today, "no story ever submits a form", and Storybook's Vitest-driven
  rendering has no server/client build split per `vitest.config.ts`'s own comment), **this is the
  #1 open research question for `/gsd-plan-phase`'s research step**: confirm whether Server
  Actions can execute for real inside Storybook/Vitest Browser Mode before committing
  implementation to "replace stubs with real calls."
- **D-09 (fallback, if D-08's research finds it infeasible):** Move the interaction coverage that
  needs the real action's effect (redirect, cookie write, backend rejection) out of Storybook-driven
  component tests entirely and into Playwright e2e (which has a real server). The no-op stub then
  stays, but scoped to **shallow/visual rendering only** — no assertions about post-submit
  behavior through the stub. This is the fallback order the user chose explicitly over "keep the
  stub for everything, formally documented" as a first-class option.
- This applies to all four actions: `sign-in`, `sign-up`, `sign-out`, `update-theme`.

### Test-boilerplate consolidation scope

- **D-10:** Both consolidation todos are in scope, fully: (a) a thin barrel re-export for the
  action stubs, and (b) centralizing the `next/headers`/`next/navigation` `vi.mock` declarations
  redeclared across 8 files into a shared module with a mutable handle (`vi.fn()` other files
  reconfigure via `vi.mocked()`).
- **D-11:** The action-stub barrel is a **thin re-export only** — keep
  `sign-in-action-storybook-stub.ts` etc. as separate files (matches CONVENTIONS.md's
  one-file-per-Server-Action rule and tech/0020's per-action register); add
  `src/test-utils/index.ts` so call sites do `import { signInStub, updateThemeStub } from
  '@/test-utils'` instead of one import line per stub file. Not a deeper merge into one shared
  stub/registry module.
- **D-12 (interaction/dependency note for the planner — important):** D-10(b)'s `vi.mock`
  centralization for `next/headers` may become **moot** given D-13/D-14 below: if the cookie
  read+write migration to e2e fully lands, `next/headers` may have zero remaining test consumers,
  and `next/navigation`'s only remaining consumer would be `sidebar.test.tsx` alone (a single
  file — nothing left to centralize). The planner should check actual remaining consumer count
  after scoping D-13/D-14's migration and skip/close D-10(b) as resolved-by-obsolescence if the
  count drops to 0-1 files per shim.
- **D-11's barrel also interacts with D-07/D-08:** if the research in D-08 leads to fully
  replacing stubs with real calls, there may be no stub files left to barrel-export at all — the
  barrel is worth doing regardless as a quick win, but treat it as provisional pending D-08's
  outcome.

### Cookie coverage — full migration to e2e

- **D-13:** **Full e2e — drop the `next/headers` shim entirely**, not a hybrid split. This
  applies to **both reading and writing** — the user explicitly extended scope beyond the
  originating todo's "cookie-writing" framing to include the cookie-*reading* files too
  (`load-boards.integration.test.ts`, `server-client.integration.test.ts`, which attach the
  session cookie to an outgoing authenticated request) after being asked to confirm the narrower
  scope. — **Reversibility:** one-way — this is confirmed as a large rewrite (see D-14), not a
  narrow tweak; reverting means re-introducing the shim and rebuilding the unit/integration test
  files from scratch.
- **D-14 (scope confirmation — asked explicitly given the size):** This cascades into
  gutting/deleting most of the 8-file Surviving Mock Register (`sign-in.integration.test.ts`,
  `sign-out.integration.test.ts`, `sign-up.integration.test.ts`,
  `update-theme.integration.test.ts`, `load-boards.integration.test.ts`,
  `server-client.integration.test.ts`, `cookie-client.unit.test.ts`,
  `theme-cookie.unit.test.ts`, `session.test.ts`) and building equivalent e2e coverage. The user
  was told this explicitly and confirmed **full scope, in this phase** — not split into a
  follow-up phase.
- **D-15:** Edge cases that are cheap to trigger with the fake cookie jar (expired session,
  malformed/tampered JWT, verification failure) move to e2e via **Playwright's browser-context
  cookie API** (`context.addCookies` / reading `page.context().cookies()`) to inject a bad cookie
  directly before navigating — exercising the real server's real rejection path, no shim needed.
- **D-16:** Amend ADR tech/0020's D-19 carve-out and Surviving Mock Register once this lands:
  remove the `next/headers` carve-out example (leaving only `next/link`), and remove the
  `next/navigation`/`redirect()` register rows for the 4 action-integration files that move to
  e2e (`sidebar.test.tsx`'s own `next/navigation` row, for router reasons, stays — it's
  unaffected and the only remaining example).
- Existing e2e infra to extend, not replace: `e2e/auth.e2e.spec.ts` (sign-up/sign-in/sign-out
  happy paths already assert the httpOnly session cookie), `e2e/theme.e2e.spec.ts` (theme cookie
  persistence across reload/sign-out/sign-in), `e2e/seed.sh` (curl-based seeding, ADR tech/0022).

## Existing Code Insights

### Reusable Assets
- `.storybook/preview-annotations.tsx` — already provides the global `QueryProvider` +
  dark-mode-class decorators every story gets; direct-rendering a composed story (D-01) inherits
  these automatically via `setProjectAnnotations` in `vitest.setup.ts`, closing the
  `QueryProvider` duplication with `render-with-providers.tsx` the roadmap goal names.
- `e2e/auth.e2e.spec.ts`, `e2e/theme.e2e.spec.ts` — already assert the httpOnly session cookie
  and theme cookie via real sign-up/sign-in/sign-out/toggle flows; the base to extend with
  edge-case coverage (D-15) rather than a new e2e file from scratch.
- `e2e/seed.sh` — curl-based account/board seeding CLI (ADR tech/0022); reuse for any new e2e
  test's account setup instead of hand-rolling sign-up calls.
- `src/test-utils/factories/` — `Partial<T>`-override entity factories (D-11 of tech/0020);
  pattern to follow if new fixture data is needed for e2e or surviving unit tests.

### Established Patterns
- Shallow-vs-deep test split (visual/staged-state assertions vs. real-interaction assertions) —
  currently expressed via `.run()` vs. `renderWithProviders`; after D-01, both become "render the
  composed story directly," so the shallow/deep *distinction* likely stays (still useful test
  organization) even though the *mechanism* unifies. Planner should decide whether to keep the
  comment markers (`// Shallow: ...`, `// Deep: ...`) seen in `sign-in-form.test.tsx`.
- `describeForEachDevice` (`src/test-utils/describe-for-each-device.ts`, ADR tech/0014) — every
  component's behavioral suite runs at both viewports by default; unaffected by this phase's
  changes but every migrated test file uses it.
- Mechanical ESLint enforcement of testing-policy rules (`no-restricted-properties` for
  `vi.mock`/`vi.spyOn`, per-file `eslint-disable-next-line` with a stated reason) — the pattern
  D-05/D-06's new rules should extend, per `eslint.config.mjs` section 8d-2.

### Integration Points
- `vitest.config.ts`'s `serverActionStubAlias` — the whole-module alias mechanism D-07/D-08 may
  remove entirely (if real calls prove feasible) or narrow (if the fallback in D-09 applies).
- `vitest.setup.ts` — owns `setProjectAnnotations` (must not be duplicated elsewhere, per
  tech/0021) and is where D-04's centralized cleanup and D-10(b)'s centralized `vi.mock` handle
  (if not moot per D-12) would live.
- ADR tech/0020's "Surviving mock register" table — the exact rows D-16 removes/keeps.
