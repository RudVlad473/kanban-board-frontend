## Decisions Made

- Kept the file's existing `SESSION_COOKIE_NAME`-style local reference but replaced every usage
  with `COOKIE.SESSION` imported directly from `cookie-registry.ts` (rather than adding a redundant
  runtime equality check) — TypeScript narrows both to the same literal type, so a runtime
  `if (SESSION_COOKIE_NAME !== COOKIE.SESSION)` check is statically always-false and ESLint's
  `no-unnecessary-condition` correctly rejected it.
- Used `page.getByText(...)` rather than `page.getByRole("alert")` for server-error-banner
  assertions — Next.js's own route-announcer (`#__next-route-announcer__`) also carries
  `role="alert"`, causing a Playwright strict-mode collision with the app's own `<p role="alert">`.
- For the duplicate-sign-up test, signed out via the UI between the two sign-up attempts —
  `proxy.ts` redirects a signed-in visitor away from `/register` entirely, so the second attempt
  would otherwise be unreachable; this app's own sign-out never calls the backend, so it doesn't
  touch the account's two-concurrent-session budget.

### Investigated, Not Fixed (architectural, out of scope)

**4. [Rule 4 - Architectural, deferred] `proxy.ts` breaks a Server Action's own POST when the session cookie is already gone**
- **Found during:** Task 3, while implementing the plan's second new sign-out test ("with a
  session cookie removed from the browser context while the signed-in page is still open,
  activating Sign Out still lands on the sign-in route and renders no error page").
- **Investigation:** Signed in normally, cleared every cookie via `context.clearCookies()` while
  the `/boards` page stayed open, then clicked "Sign Out". Instrumented the page with response/
  console/pageerror listeners for one debug run (not committed) and observed: `307 POST
  http://localhost:4173/boards` → `200 POST http://localhost:4173/login` → client console error
  `"An unexpected response was received from the server."`, with the URL remaining at `/boards`
  and the app's own error boundary (`heading: "Something went wrong"`, `button: "Try again"`)
  rendered instead.
- **Root cause:** `proxy.ts`'s guard (`isProtectedPath(pathname) && !identity → redirect`) applies
  to every request method, including a Server Action's own POST — which targets the *current*
  page's pathname (`/boards`, a protected path). When the session cookie is absent, the guard
  redirects that POST to `/login` before `signOutAction` itself ever runs. Next.js's client-side
  action-invocation machinery expects the response to be a flight/action-stream payload; receiving
  an ordinary HTTP redirect (which the browser's `fetch` then follows, re-POSTing to `/login`)
  breaks that parsing, surfacing as a generic client-side crash — unrelated to whether the action's
  own logic handles a missing session gracefully (it does: the deleted unit-level
  `sign-out.integration.test.ts` already proved `signOutAction` completes cleanly with no session,
  bypassing `proxy.ts` entirely by calling the function directly).
- **Why not fixed here:** the correct fix (skip `proxy.ts`'s guard for requests carrying Next.js's
  `next-action` header, letting the action's own `redirect()` — which the client machinery *can*
  parse — handle the outcome) touches the application's auth-guard middleware, which is explicitly
  called out as Rule 4 (architectural/auth-approach change) territory in the executor's deviation
  rules, and `proxy.ts` is outside this plan's `files_modified` list and outside every other 02.2
  plan's list too. This is a genuine, real-world-reachable gap (a session expiring naturally while
  a user is on a protected page, then activating ANY Server Action, would hit the identical
  failure) worth fixing, but the fix and its security implications (does any other, not-yet-built
  Server Action rely on `proxy.ts` as its sole protection?) need deliberate review, not an
  executor's unilateral middleware change.
- **Disposition:** coverage ledger row 11 marked NOT REACHABLE with this reason; the test for this
  scenario was written, confirmed to fail for this documented cause, then removed rather than left
  permanently red — a short in-file comment records the disposition and points here. Restate in
  plan 02.2-09's ADR amendment per the plan's own instructions.
- **Files modified:** none (investigation only; the test that surfaced this was removed, not kept red)
