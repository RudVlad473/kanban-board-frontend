<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user input → browser form state | Passwords are held in React state on the client for the duration of the form's life |
| browser → same-origin BFF endpoints | The only network boundary the client code knows about |
| server error message → rendered copy | Text originating server-side is rendered into the page |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-07 | Information Disclosure | Password held in form state and in the revealed-visibility state | high | mitigate | The form writes nothing to `localStorage`, `sessionStorage` or `document.cookie`; the password field is cleared on a failed sign-in; the visibility toggle is user-initiated and its accessible name always reports the current state, so the field is never silently revealed |
| T-01-08 | Information Disclosure | Account enumeration through sign-in or sign-up copy | medium | mitigate | Both forms render the server's message unmodified, and the endpoint returns identical responses for both failure causes (plan 01-11); the sign-in test compares the two rendered messages directly. The sign-up copy deliberately covers duplicate-email and unknown failure with one wording |
| T-01-31 | Tampering | Client-side validation treated as the security boundary | medium | mitigate | The same Zod schemas run server-side in plan 01-11 before any upstream call; the client validation is a usability affordance, and the shared schema module means the two cannot drift apart |
| T-01-32 | Information Disclosure | External API base URL reaching the browser bundle | high | mitigate | The auth feature imports only same-origin paths; `server-client.ts` carries the `server-only` marker so an accidental import fails the build, and the verify gate scans the feature folder for both the import and any absolute URL |
</threat_model>
