<objective>
Move sign-up and sign-in off the Route Handler and client fetch chain and onto server functions the
forms submit to directly, carrying the backend's own named failure reason back to the interface.

Purpose: one button press currently traverses a form, a mutation hook, a fetch wrapper, a Route
Handler and the data access layer — five files for one action, with hand-written request and
response shapes at every hop. GC-24 carves auth out of ADR tech/0002's rejection of server
functions, because the reason that rejection rested on — optimistic rollback — never applied to
authentication. GC-20 adds the requirement that a failure carries a reason a caller can branch on.

Output: two server functions with their own tests, two rewritten forms, and four deleted files.
Sign-out is deliberately left alone until plan 01-34, so this plan leaves a working application.
</objective>

<decisions>
**Pending state comes from `useActionState`, not `useFormStatus`.** The research addendum sketches
the two-component split the Next.js docs use, where a child reads the form's pending status because
the parent cannot. That split exists for React versions where `useActionState` returns only a state
and an action. This project is on React 19.2, where `useActionState` returns a pending flag as its
third element directly — so the parent already has what the split was invented to obtain, and
introducing a child component solely to re-derive it would add a file and a layer for nothing.
Recorded here so the deviation from the research's sketch is visible rather than silent.

**React Hook Form stays, for display-time validation only.** The forms keep `mode: "onTouched"`
field validation, which is what makes an error appear as a field is left rather than only after a
submission — behaviour the current component tests assert and users notice. Submission itself goes
through the form element's action, so it works before hydration; the server function re-validates
with the same schema and returns field errors for anything that reaches it. The two error sources
are merged at render time with a precedence rule that ALSO clears a stale server error once the user
edits the field (Task 2's `<action>`, resolving 01-REVIEWS.md MEDIUM #4) — a naive `clientError ??
serverError` would re-show the previous submit's server error the moment the client error resolves to
`undefined` after the user fixes the input, so the server error is gated on the field being unmodified
since the submission that produced it, not merely on the absence of a client error.
</decisions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → server function | Credentials now cross on a framework-managed action request rather than a hand-written route |
| backend failure reason → rendered copy | A named reason now reaches the client, where previously only a message did |
| form data → validation | Values arrive as untyped form entries rather than a parsed JSON body |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-54 | Information Disclosure | Account enumeration through a message that distinguishes a wrong password from an unknown address or a refused session | high | mitigate | Sign-in returns one fixed message for every rejection arm, carried across verbatim from the Route Handler with its comment; a test asserts the wrong-password and session-ceiling cases produce an identical message |
| T-01-55 | Information Disclosure | The backend's named reason being rendered to the user and leaking the distinction the message hides | high | mitigate | The reason is carried in the state's code field only; the rendered message is a project-owned constant chosen by the branch, never derived from the backend's own text. The checkpoint has a human confirm no code reaches the screen |
| T-01-56 | Tampering | Untyped form entries reaching the backend unvalidated because a parsed body no longer arrives | medium | mitigate | Each server function re-parses the form values with the same schema the client uses and returns per-field errors without calling the backend; a test asserts the client is never called on a validation failure |
