Close GC-06: add gitleaks secret scanning to the existing Husky and lint-staged pre-commit chain,
installed through npm rather than as a hand-placed binary.

Purpose: this repository already handles real credential material — `SESSION_SECRET`, a generated
per-run CI secret, and `.env.local` values — and its only current protection is `.gitignore`. The
user's requirement was explicit: an npm-wrapper package that brings the binary along with a normal
install, so there is no per-contributor setup step and CI needs no extra tooling.

existing lint-staged step, a named script for scanning on demand, and a CI job so a commit made
with the hook bypassed is still caught.

arbitrary-variant lint rule and the ignore-file unification, both recorded as deferred with reasons

<decisions>
**Neither candidate wrapper appears in this phase's Package Legitimacy Audit, so both are
`[ASSUMED]` and the install is gated on a blocking human checkpoint.** The audit in 01-RESEARCH.md
predates this gap-closure round and covers no gitleaks wrapper. Under the fallback rule an
unaudited package is treated as assumed-unverified, and an assumed package may not be installed
without a human looking at it — that checkpoint is Task 1, and it is never auto-approvable
regardless of any auto-advance setting.

**Both candidates are genuinely thin, and that is the honest state of this ecosystem.** Upstream
gitleaks is a 28,000-star, actively maintained Go project; what does not exist is a first-party npm
distribution of it. Every npm wrapper is a third party repackaging someone else's binary, which is
exactly the shape of a supply-chain risk. The evidence for both is laid out in Task 1 so the
decision rests on facts rather than on a name.

**The scan blocks the commit; there is no warn-only mode.** D-26g already settled this for the lint
and format checks, and the same reasoning is stronger here — a secret that reaches a commit object
is effectively public even if the next commit removes it.

**CI runs the scan too.** D-26h states plainly that hooks are a convenience and CI is the
authoritative gate, and that nothing should rely on a hook as its only enforcement. A hook alone
would make the bypass flag a complete defeat of this control.
</decisions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| working tree → git history | Once a secret is in a commit object it is effectively published, even if a later commit removes it |
| npm registry → every contributor machine and CI runner | Installing a wrapper runs or places third-party code wherever the project is installed |
| scan output → terminal, shell history and CI logs | A scanner that echoes what it caught republishes the secret in a second place |
