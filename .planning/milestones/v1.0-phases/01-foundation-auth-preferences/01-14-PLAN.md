<decisions>
**Theme cookie module placement: `src/lib/server/theme.ts`, in the server ring (resolves
01-REVIEWS.md LOW #5).** This plan was originally drafted before round-4's three-ring `lib/` reorg and
created `src/lib/theme.ts` — a flat path that matches no boundaries element once the three rings land
(01-36/01-37) and would be an orphan. Because HIGH #2's fix re-sequenced this plan to `wave: 22`,
`depends_on: ["01-38"]`, it now runs *after* the entire reorg, so `theme.ts` must be created in the
new structure. `THEME_COOKIE`/`readThemeCookie`/`writeThemeCookie` are server-only (they call Next's
`cookies()` and run in the root-layout server render and the persistence handler), and they are
consumed by `app/layout.tsx` — outside `features/theme/` — so they are shared server-only
infrastructure, not feature-local pure logic. Under the three-ring rule (server-only module ->
`lib/server/`) and GC-26 (feature-local only when a single domain consumes it) the correct home is
`src/lib/server/theme.ts`, NOT `src/lib/theme.ts` and NOT `src/features/theme/`. This placement is
independent of 01-35 Task 3's persistence-shape decision: whichever option is chosen (Route Handler,
server function + client query, or full server function), the pre-hydration cookie helpers are
server-only and used by the root layout, so they belong in the server ring either way. **The
persistence *mechanism* — a Route Handler at `app/api/users/me/theme/route.ts` (option A) versus a
theme server function at `src/features/theme/actions.ts` following the auth `actions.ts` convention
(options B/C) — is still governed by 01-35 Task 3's decision as applied by 01-35 Task 4; this decision
resolves only the cookie module's home.**

**All cross-plan `lib/` references in this plan name their post-reorg paths.** Because this plan now
runs at wave 22 (after 01-36/01-37/01-38), every module it reads that the reorg moved is cited at its
new location: `src/lib/server/dal.ts` and `src/lib/server/server-client.ts` (server ring, moved by
01-37), `src/lib/core/api-contract/problem-detail.ts` (core ring, moved by 01-36), and
`src/features/auth/actions.ts` (renamed by 01-37). These files do not exist at those paths until the
reorg lands; 01-35 Task 4 (which runs at wave 18, before the reorg) repoints these references and its
read-first-existence gate excludes them for exactly that reason.

**Failure feedback is an inline live-region message, not a toast.** UI-SPEC records the
theme-persistence failure UI as unresolved and recommends reverting the Switch plus a transient
toast, explicitly flagged as unconfirmed. Reverting is implemented as recommended. The toast is
not: no toast primitive exists in D-13's seven-primitive set, and pulling in a toast library here
would introduce a runtime dependency that never passed this phase's package legitimacy audit. An
inline, polite live-region message rendered beside the toggle satisfies the same requirement — the
user learns the save failed — using only what the design system already provides. Recorded here so
the deviation from UI-SPEC's recommendation is visible rather than silent.
</decisions>

<flagged_assumptions>
- **The theme-persistence failure UI is unconfirmed.** UI-SPEC marks this row unresolved; the
  revert-plus-inline-message behaviour above is a planner-level decision, not a sourced design.
- **A theme preference is a durable row in a shared, real database.** A preference saved while
  developing or under test persists and is visible to every other run against the same environment;
  nothing resets between runs except the reset step plan 01-31 wired into CI.
- **A single account is capped at two concurrent sessions, and this application's sign-out cannot
  release one** — the backend's own sign-out route is verified broken and recorded in
  `.planning/phases/01-foundation-auth-preferences/deferred-items.md`. A persistence check that signs
  in a third time inside the server-side session
  lifetime is refused with the same message a wrong password produces. That is the recorded
  limitation, not a theme defect; use a freshly created account instead of reading it as one.
- **THEME-01 edge-probe resolution (spec-less probe fallback, both items already covered — no new
  requirement bolted on).** The deterministic edge probe surfaced two THEME-01 items — *idempotency*
  ("what happens if this runs twice on the same input?") and *concurrency* ("if interrupted or run in
  parallel, what is guaranteed?"). Idempotency is already an explicit `must_haves.truth` and a Task 1
  behaviour + acceptance case (a repeated identical `PUT` leaves the stored record and UI state
  unchanged, both calls succeed). Concurrency: the theme `PUT` is a single-field, last-writer-wins
  update with no multi-step transaction, so a parallel or interrupted call has no partial-write hazard;
  the optimistic-update path reverts and reports on failure (Task 2), and the two-concurrent-session
  cap is the recorded limitation above, handled by giving every e2e leg its own account. Neither probe
  item warrants a new requirement on this already-designed work; both are surfaced here rather than
  dropped silently.
</flagged_assumptions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → theme server function | Server Actions aren't covered by the page-level route guard either, so this function is the only place its own access decision is made |
| caller-supplied user id → upstream contract | The contract takes the target user as a query parameter and declares no auth scheme |
| theme cookie → browser | Deliberately readable, unlike the session cookie |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-06 | Elevation of Privilege | Caller-supplied `userId` letting one signed-in user rewrite another's preference | high | mitigate | `updateThemeAction`'s signature carries no caller-suppliable identifier at all — the user id comes exclusively from `verifySession()`, so there is no argument position through which a different user's id could be supplied; a test asserts only the calling session's own record changes |
| T-01-05 | Elevation of Privilege | A mutation relying on a guard that never runs for its call path | high | mitigate | `updateThemeAction` calls `verifySession()` itself and returns a failure state when it yields nothing, asserted directly |
| T-01-03 | Tampering | Cross-site request forgery against the state-changing theme update | medium | mitigate | Server Actions carry their own built-in Origin-header CSRF protection, independent of the session cookie's `SameSite` attribute; the call also requires an authenticated session (T-01-05), so an unauthenticated cross-site call is refused before it could act |
| T-01-35 | Information Disclosure | Theme cookie readable from JavaScript | low | accept | It carries a display preference, not a credential; readability is required for the pre-hydration scope resolution, and it is a separate cookie so the session's httpOnly protection is untouched |
| T-01-36 | Repudiation | A save reported as successful when it failed, leaving the user's belief and the stored state divergent | medium | mitigate | The control reverts to the stored value on failure and a live-region message states the save did not happen; the test asserts both, since either alone still misinforms |
