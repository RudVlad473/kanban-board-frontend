<decisions>
**`isLoading` is a separate prop from `isDisabled`, not a variant of it.** Disabled is a static
statement about whether a control is available at all; loading is a transient statement that a
request is in flight. They compose: either one makes the control non-activatable, but only
`isLoading` sets `aria-busy` and only `isLoading` shows a spinner. Folding loading into
`isDisabled` would make it impossible for a caller to express "temporarily busy" distinctly from
"not available", which is exactly the distinction assistive technology reads off `aria-busy`.

**A loading TextField becomes read-only, not disabled.** A disabled input drops out of the tab
order and takes its value with it visually — the browser also blurs it, so a user mid-typing has
focus yanked to the document body the instant they press submit. `readOnly` freezes the value
(which is the actual requirement: the submitted text must not change under the request) while
keeping the field focusable, selectable and legible. `aria-busy` carries the "working" signal.

**Loading copy is a glyph, not text.** UI-SPEC's loading row specifies "disabled + loading-spinner
variant" with "no dedicated copy". The button keeps its own label visible beside the spinner so
its width does not jump mid-submit.

**`aria-busy` is always rendered, as "true" or "false", never omitted.** Plan 01-12's existing
tests already assert the attribute is present and reads false once a request settles; an
implementation that removed the attribute instead of setting it to false would regress those.
</decisions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user input → in-flight request body | The values already sent upstream must not diverge from what the user believes they sent |
| repeated activation → BFF auth endpoints | An unguarded submit control can be pressed many times before the first response lands |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-37 | Tampering | Editable TextField during an in-flight submit (`sign-in-form.tsx`, `sign-up-form.tsx`) | medium | mitigate | Every field goes read-only from the mutation's pending flag; the test types into a pending field and asserts the value did not change |
| T-01-38 | Denial of Service | Repeated submit against `/api/auth/signin` and `/api/auth/signup` before the first response lands | medium | mitigate | The submit Button is non-activatable whenever `isLoading` is set, and `retry: false` already bounds each accepted submit to one upstream call |
| T-01-39 | Repudiation | A form that stays frozen after a failed request, leaving the user unable to correct and resubmit | medium | mitigate | Task 3's recovery-after-failure test asserts every control is editable again once the rejection lands |
| T-01-40 | Information Disclosure | A busy icon-only control losing its accessible name when its glyph is swapped for a spinner | low | mitigate | `label` continues to supply `aria-label` independently of the rendered glyph; the test finds the busy control by its accessible name |
</threat_model>
