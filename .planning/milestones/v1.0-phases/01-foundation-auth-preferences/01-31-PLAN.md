<objective>
Make every CI run that touches the real backend clean up after itself, using the reset endpoint the
backend already proved end to end.

Purpose: since plan 01-30, every unit, component and end-to-end run writes real rows into a shared
nonprod database, and the backend caps an account at two concurrent sessions with a server-side
lifetime far longer than a suite. Without a reset, one run's leftovers become the next run's
mysterious failure. GC-23 makes this CI's responsibility rather than each developer's.

Output: an authenticated post-suite reset step, a repository secret only a human can supply, and a
green pipeline run proving both.
</objective>

  <what-built>
    Nothing yet — this checkpoint precedes the workflow change, because the step it adds cannot be
    verified without a real credential and no agent can obtain one.

    Plan 01-30 pointed every test target at the deployed nonprod backend. Every CI run now creates
    real accounts and real sessions in a database shared with every other run. The backend already
    exposes a reset endpoint for exactly this, proven end to end in its own phase 8, guarded by a
    single shared-secret header compared in constant time.
  </what-built>
  <how-to-verify>
    1. On the backend's nonprod host, read the `APP_RESET_TOKEN` value from its `.env.nonprod`
       file. It is deliberately never committed anywhere, in either repository — do not look for it
       in git.
    2. In this repository on GitHub, go to Settings, then Secrets and variables, then Actions, and
       add a new repository secret named exactly `NONPROD_RESET_TOKEN` with that value.
    3. Confirm the endpoint accepts it, from your own machine:

       ```bash
       curl -sS -o /dev/null -w '%{http_code}\n' -X POST \
         -H "X-Reset-Token: <the value>" \
         https://kanban-board-rud-vlad-473-nonprod.duckdns.org/api/admin/reset
       ```

       A correct token prints `204`. A wrong or absent token prints `403` — the two are
       deliberately indistinguishable from the endpoint's own responses, so a `403` here means the
       value is wrong, not that the endpoint is broken.
    4. Note that this call truncates every table in nonprod, including the probe accounts left
       behind during planning. That is the intended effect.
  </how-to-verify>
  <resume-signal>Type "approved" once the secret exists and the manual call printed 204, or describe what the call returned instead.</resume-signal>

    `https://kanban-board-rud-vlad-473-nonprod.duckdns.org/api/admin/reset`, as a `POST` carrying a

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions → backend nonprod admin route | A destructive, internet-reachable endpoint is called with a shared secret |
| repository secret → workflow step | The only place the reset credential exists in this repository |
| one CI run → another CI run's data | Concurrent runs share a single database and a single reset button |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-43 | Information Disclosure | The reset token leaking into a workflow log through an echoed command or a verbose client | high | mitigate | The token is read only as a header value from a repository secret, never echoed and never placed in the file; the verify gate asserts the literal value is absent from the workflow, and the existing secret-scanning job gates every push |
| T-01-44 | Repudiation | A rotated or wrong token turning cleanup into a silent no-op that nobody notices until a later run fails oddly | high | mitigate | The step compares the response status to the documented success status and fails the job on anything else, printing what it received; a broken credential surfaces as a red job immediately |
| T-01-45 | Denial of Service | One run truncating the database while a concurrent run's suite is mid-flight | medium | accept | Accepted per GC-23 for a single-developer non-production environment; the workflow's existing concurrency group already cancels superseded runs on the same ref, and the step is deliberately not added to jobs that make no real request |
| T-01-46 | Elevation of Privilege | A fork pull request obtaining the reset secret through the workflow | medium | mitigate | GitHub does not expose repository secrets to workflows triggered from forks, so the step is a no-op credential-wise there; the status check then fails that job loudly rather than deleting anything |
</threat_model>
