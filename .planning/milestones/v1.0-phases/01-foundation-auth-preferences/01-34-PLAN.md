<verified_backend_facts>
Observed directly against live nonprod on 2026-08-18 during planning:

- `POST /api/logout` returns **500** with `code: INTERNAL_ERROR` and the detail
  `No static resource logout.`
- A request to the same route with the context path repeated returns **200**. Without the context
  path at all it returns 404.
- After the failed call, the same session credential still authenticated a subsequent read, so the
  upstream session was **not** invalidated.
- The cause is visible in the backend's own source: `SecurityConfiguration` builds its logout URL by
  prefixing the context path onto the route, while the framework matches that setting against the
  path with the context path already stripped — so the filter listens one segment deeper than
  anyone can reach on purpose.

Consequence for this application: signing out cannot release the upstream session. The backend caps
an account at two live sessions and holds each one server-side for three hours, so a user who signs
in from a third context inside that window is refused with the same message a wrong password
produces. That is a backend defect this frontend cannot fix, and Task 1 records it rather than
working around it.
</verified_backend_facts>
