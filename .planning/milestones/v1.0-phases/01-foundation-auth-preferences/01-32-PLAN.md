<objective>
Bridge this app's own session to the backend's, so that a signed-in user's calls actually
authenticate — and so that when the backend's session quietly expires, the user is signed out
rather than stranded.

Purpose: the backend authenticates by session cookie and this app forwards none, which means
pointing at a real backend does not "just work" — every call on behalf of a signed-in user is
refused. GC-18 makes this the round's load-bearing prerequisite: the mechanism is general, not an
auth special case, because plan 01-14's theme calls and Phase 2's board calls go through the same
client.

Output: an extended session record, a request middleware that authenticates every outbound call, a
forced sign-out path for upstream expiry, and an integration test that proves the whole chain
against the live backend.
</objective>

<verified_backend_facts>
Observed directly against live nonprod on 2026-08-18 during planning, with `curl`:

- Both `POST /api/signup` (201) and `POST /api/signin` (200) return
  `Set-Cookie: JSESSIONID=<value>; Max-Age=600; Expires=<...>; Path=/; HttpOnly; SameSite=Strict`,
  and a body carrying `id`, `email`, `displayName`, `theme`.
- `GET /api/users/me/theme?userId=<id>` with **no** cookie returns `401` with `code: UNAUTHENTICATED`.
- The **identical** call carrying `Cookie: JSESSIONID=<value>` returns `200` and the four-field body.
- A wrong-credential `POST /api/signin` returns `401` with `code: BAD_CREDENTIALS` — a different
  code from the unauthenticated one, which is what makes the two distinguishable in the response
  middleware.

The `SameSite=Strict` attribute and the backend's CORS allow-list are properties of a *browser*
sending that cookie. This app forwards it server to server as a request header, so neither applies
here — do not design around them.
</verified_backend_facts>

<assumption_delta_decision>
**Disposition: `add-alongside`.**

`SessionPayload` today is documented as the identity the backend returns, and its guard
`isSessionPayload` has two callers with different inputs: a decoded session token, and a raw
upstream response body which will never carry a credential. Folding the backend's session id into
`SessionPayload` — as the pattern map suggested — would break the second caller the moment the
guard checked for it.

So the identity type stays exactly as it is, and a second type is introduced beside it:
`SessionRecord`, being the identity plus the backend's session id, is what the cookie carries and
what `verify` returns. The session is not becoming a plural or compound identity — there is still
exactly one user and exactly one upstream session per cookie — so this is neither a promotion nor a
no-change; it is one new type sitting alongside an unchanged one, with a clear rule about which
callers use which.
</assumption_delta_decision>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| this app's session cookie → the backend's credential | A second credential now lives inside a cookie that previously carried only identity |
| every outbound client call → the backend | One middleware now authenticates all of them, including calls no one has written yet |
| upstream refusal → this app's session lifecycle | A response from another service can now sign a user out |
