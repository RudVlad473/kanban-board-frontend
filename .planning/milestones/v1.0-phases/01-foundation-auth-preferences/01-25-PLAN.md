<objective>
Close GC-16: establish and prove Modal's loading convention — a consumer driving an async action from
inside a Modal must be able to prevent the modal from being dismissed mid-request, using Modal's
existing public surface, with no new prop.

Purpose: Modal was not in GC-01/01-16's scope and drives no async mutation directly (D-18: Modal is
content-driven, no size axis). Rather than inventing a new `isLoading` prop for a component that has
no loading state of its own, this closes the gap by documenting and proving the pattern a consumer
already has available: `isDismissableOnBackdropClick={!isLoading}` blocks backdrop dismissal, and a
controlled `onOpenChange` handler that ignores a close request while `isLoading` blocks Escape (which
Base UI's Dialog fires the same `onOpenChange(false)` callback for, per the existing Escape test in
`modal.test.tsx`). Output: a documented convention plus a real story and a real behavioral test
proving both dismissal paths are actually blocked while loading and restored once it ends.
</objective>

<decisions>
**No new prop on Modal.** `isOpen`/`onOpenChange` (controlled mode) and `isDismissableOnBackdropClick`
already exist on `Modal.Root`'s public surface. Adding an `isLoading` prop to Modal itself would give
the component a loading state it does not actually have — the loading state belongs to the action
inside it (e.g. a submit `Button` in `Modal.Footer`), which already gets `isLoading` from GC-01's
established pattern. This item documents composition, not a new mechanism.

**Escape is blocked by the consumer's own `onOpenChange` guard, not by a new Modal-level prop.** The
existing `modal.test.tsx` Escape test proves Base UI's Dialog always calls `onOpenChange(false)` on
Escape, regardless of `isDismissableOnBackdropClick` (which only governs backdrop clicks). A consumer
in controlled mode (`isOpen` + `onOpenChange`) can already ignore that callback while `isLoading` is
true — this is existing, provable behavior, not a gap in Modal's implementation.
</decisions>
