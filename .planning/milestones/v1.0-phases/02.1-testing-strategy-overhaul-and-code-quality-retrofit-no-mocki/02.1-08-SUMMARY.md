# Phase 02.1 Plan 08: Dropdown/Menu/Modal/Toast/ErrorFallback Storybook-Driven Tests Summary

**Routed the shallow rendered-state assertions in Dropdown, Menu, Modal, Toast and ErrorFallback
through composed Storybook stories, discovered and fixed a real cross-file test-pollution bug in
the shared `vitest.setup.ts` composeStories wiring along the way, and annotated both route error
boundaries with their ADR tech/0021 carve-out.**

## Performance

- **Duration:** ~130 min
- **Tasks:** 3
- **Files modified:** 13 (12 declared in the plan + `vitest.setup.ts`, an undeclared Rule 3 fix)

## Accomplishments

- `dropdown.test.tsx`/`menu.test.tsx` drive their closed/open/loading/selected rendered states
  through `composeStories` (`Closed`, `Loading`, `OpenWithSelection` for Dropdown; `Open`,
  `WithDisabledItem` for Menu), keeping every keyboard-nav, focus, click-interaction, and
  `getComputedStyle()` assertion as a direct render with a one-line Deep reason. `dropdown.tsx`/
  `menu.tsx` themselves are untouched (plan 02.1-11's sweep scope).
- `modal.test.tsx` drives closed/open/with-description rendered states through composed stories
  (`Closed`, `Open`, `WithDescription`); focus trap, Escape/backdrop dismissal, the loading-guards-
  dismissal composite, and both computed-style/device-dependent layout tests stay direct renders.
- `toast.test.tsx` drives seeded-copy, `aria-live` region, dismiss-control accessible name, and
  `data-type` variant assertions through composed stories (`Default`, `Danger`); auto-dismiss
  timing, action-click, close, stacking and upsert behaviour stay direct renders per the plan's own
  Toast-specific Deep/Shallow split.
- `error-fallback.test.tsx` drives title/description copy, digest reference line, and
  homeHref link/no-link states through composed stories (`Default`, `WithReference`, new
  `WithoutHomeLink`); `onRetry` click/keyboard activation stay direct renders (real interaction).
- `app/(dashboard)/error.test.tsx` and `app/global-error.test.tsx` each carry a one-line pointer to
  `docs/adr/tech/0021`'s route-file carve-out — explicit rather than silently overlooked. Neither
  file mocks anything; existing coverage is unchanged.
- **Rule 3 fix:** `vitest.setup.ts` gained `testingLibraryRender: render` in its
  `setProjectAnnotations` call — without it, `composeStories().run()` in the "browser" Vitest
  project rendered through an untracked fallback whose DOM (including any open Base UI portal)
  survived into later tests and collided once two tests shared an accessible name. Combined with a
  local `afterEach(cleanup)` in every rewritten test file.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] composeStories' `.run()` never registered with RTL's `cleanup()`,
causing cross-test DOM pollution and accessible-name collisions**
- **Found during:** Task 1, first `pnpm exec vitest run --project browser` pass on the rewritten
  `dropdown.test.tsx`/`menu.test.tsx` — 33/48 tests failed with Playwright strict-mode violations
  ("resolved to 2 elements") on roles/names every story in the file shares (Dropdown's trigger
  placeholder, Menu's "Board actions" label).
- **Issue:** `@storybook/react`'s `composeStories().run()` only participates in React Testing
  Library's `cleanup()` registry when a `testingLibraryRender` project annotation is supplied;
  without it, `.run()` falls back to an internal `renderToCanvas` path (a raw `ReactDOM.createRoot`
  call) whose mounted DOM — including any Base UI portal a story opens (e.g. `Menu`'s `Open` story,
  `Dropdown`'s `OpenWithSelection`) — is never unmounted between tests. `vitest.setup.ts`'s
  `setProjectAnnotations` call (added in plan 02.1-01) didn't supply this annotation, so it had been
  silently leaking since that plan; `sidebar.test.tsx`'s 3 composed-story tests never collided only
  because each asserted unique text, not a shared role/name.
- **Fix:** Added `testingLibraryRender: render` (from `@testing-library/react`) as a third
  `setProjectAnnotations` entry in `vitest.setup.ts`, plus `afterEach(cleanup)` in every rewritten
  test file. Confirmed this is the correct general fix, not a narrow one, by re-running the FULL
  `pnpm exec vitest run --project browser` (315/315 passing, including `sidebar.test.tsx`
  unaffected) and the full `pnpm exec vitest run --project storybook` (91/91) after the change.
- **Files modified:** `vitest.setup.ts` (not declared in this plan's `files_modified` — a shared
  setup file with no owning plan); `dropdown.test.tsx`, `menu.test.tsx`, `modal.test.tsx`,
  `toast.test.tsx`, `error-fallback.test.tsx` (added `afterEach(cleanup)`).
- **Verification:** All four task-scoped `vitest run` commands and the full `browser`/`storybook`
  project runs pass; `git diff --name-only` confirms no other file changed as a side effect.
- **Committed in:** `732c274` (Task 1 commit — the fix landed with the first files that needed it).

**2. [Rule 1 - Bug] `@testing-library/user-event`'s `.hover()` throws `Illegal invocation` in
Vitest Browser Mode**
- **Found during:** Task 2, writing Toast's new "exposes the viewport as an aria-live region and
  the close control by its accessible name" composed-story test — `Toast.Close` is `aria-hidden`
  until hovered/focused, so revealing it requires a hover.
- **Issue:** `@testing-library/user-event`'s `hover()` isn't designed for Vitest Browser Mode's real
  browser environment; calling it on a plain DOM element threw `TypeError: Illegal invocation`
  inside its internal `patchFocus` step.
- **Fix:** Used `vitest/browser`'s own `userEvent.hover(page.elementLocator(element))` instead —
  the same `page.elementLocator(...)` pattern `modal.test.tsx`'s `getBackdropElement()` helper
  already establishes for wrapping a plain DOM element as a Locator.
- **Files modified:** `toast.test.tsx`.
- **Verification:** The test passes in both MOBILE and DESKTOP `describeForEachDevice` runs.
- **Committed in:** `768f965` (Task 2 commit).
