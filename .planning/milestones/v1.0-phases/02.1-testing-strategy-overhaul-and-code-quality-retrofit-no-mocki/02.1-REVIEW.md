zod boundary validation, consolidated cookie handling (`createCookieClient`/`themeCookie`/
`upstreamCookie`), curl-based E2E seeding, a full Storybook-`composeStories` rewrite of every
component test, and a comment-length compression sweep enforced by a new script. The security-
sensitive surface (session JWT signing/verification, cookie flags, auth Server Actions, the
`externalApi` session-bridging middleware, CVE-2025-29927-class route-guard defense-in-depth) was

## Warnings

### WR-01: Theme cookie name and max-age duplicated instead of imported from the single declaration

**File:** `src/features/theme/hooks/use-theme-preference.ts:14-15`
**Issue:** `COOKIE.THEME` is declared once in `src/lib/core/cookies/cookie-registry.ts` specifically
so "every cookie name this app sets or reads" (PC-02, per that file's own doc comment) has one
source of truth. `use-theme-preference.ts`'s unauthenticated write path re-declares both the name
and the max-age as fresh local literals instead of importing the existing constants:
```ts
const THEME_COOKIE_NAME = "theme";
const THEME_COOKIE_MAX_AGE_SECONDS = 60 * 60 * 24 * 365;
```
This is a `feature -> lib-core` import, already permitted by `eslint.config.mjs`'s boundaries
policy — there is no architectural reason for the duplication. `src/lib/server/cookies/
theme-cookie.ts` independently declares an identically-valued `THEME_COOKIE_MAX_AGE_SECONDS`
constant of its own. If the theme cookie's name or lifetime is ever changed, only one of the two
call sites has to be found and edited for the app to silently regress (client-set cookie in one
lifetime, server-set cookie in another).
**Fix:**
```ts
import { COOKIE } from "@/lib/core/cookies/cookie-registry";
// re-export or import the max-age from theme-cookie.ts, or promote it to cookie-registry.ts
const writeThemeCookieClientSide = (theme: Theme): void => {
    document.cookie = `${COOKIE.THEME}=${theme}; path=/; max-age=${String(THEME_COOKIE_MAX_AGE_SECONDS)}; samesite=lax`;
};
```

### WR-02: Client-written theme cookie never sets `Secure`

**File:** `src/features/theme/hooks/use-theme-preference.ts:23-25`
**Issue:** The unauthenticated toggle path writes the theme cookie directly via `document.cookie`
with `path=/; max-age=...; samesite=lax` but no `Secure` attribute at all:
```ts
document.cookie = `${THEME_COOKIE_NAME}=${theme}; path=/; max-age=${String(THEME_COOKIE_MAX_AGE_SECONDS)}; samesite=lax`;
```
Every server-side cookie write in this codebase goes through `createBaseCookieOptions()`
(`src/lib/core/cookies/cookie-registry.ts`), which sets `secure: process.env.NODE_ENV !==
"development"` — i.e. `Secure` outside local dev. This client-side write bypasses that convention
entirely and is missing `Secure` unconditionally, including in production. The theme value itself
is non-sensitive, so this is not exploitable for account takeover, but it is an inconsistent,
unhardened cookie write against the project's own stated cookie-attribute conventions, and would
be flagged by any cookie-security scanner.
**Fix:** Gate `Secure` the same way the server does, e.g. via `location.protocol === "https:"`:
```ts
const secureAttr = location.protocol === "https:" ? "; secure" : "";
document.cookie = `${COOKIE.THEME}=${theme}; path=/; max-age=${String(THEME_COOKIE_MAX_AGE_SECONDS)}; samesite=lax${secureAttr}`;
```

### IN-03: Duplicate `no-restricted-syntax` `TSImportType` selector across two config blocks

**File:** `eslint.config.mjs:104-120` and `eslint.config.mjs:340-388`
**Issue:** Two separate flat-config objects both set the `no-restricted-syntax` rule for the same
file scope (no `files:` filter on either): the first (section "4c") configures only the
`TSImportType` selector; the second (section "8d") repeats that identical selector alongside five
more. Because ESLint flat config *replaces* (never merges) a rule's config per matching object,
section 4c's array is entirely superseded by section 8d's later one in the array — the duplication
is harmless today only because section 8d happens to re-list the same selector, but section 4c is
otherwise dead configuration that could mislead a future editor who edits its message text
expecting it to take effect. Pre-existing structure (not introduced by this phase — only comments
in this region were touched — but the file is in this phase's reviewed set).
**Fix:** Delete the standalone "4c" block and fold its selector into "8d"'s single array (already
done in substance — remove the now-redundant duplicate block).
