<objective>
Replace three near-duplicate `next/headers` cookie implementations with one typed, reusable client,
and bring the three cookie/session test files into no-mocking compliance.

Purpose: D-10 calls for a single generic, typed abstraction for reading/writing/clearing named
cookies, with `session.ts`'s own bespoke handling refactored to consume it. 02.1-RESEARCH.md
verified three independent `await cookies()` + `cookieStore.set/get/delete` implementations already
exist (`theme-cookie.ts`, `session.ts` twice). D-20 confirmed `upstream-cookie.ts` is in scope for
the decision but structurally different — it parses a raw `fetch` `Response`, never touching
`cookies()` — so this plan resolves that by keeping it separate and writing down why.

Output: `cookie-client.ts` with a typed codec-driven API, `themeCookie` and the session service both
rebuilt on it, `upstream-cookie.ts` documented and given its first test, and the three test files'
surviving mocks narrowed to the documented `next/headers` shim.
</objective>

    <behavior>
        - `read()` returns the decoded value when the cookie holds something the decoder accepts.
        - `read()` returns `null` when the cookie is absent.
        - `read()` returns `null` when the cookie holds a value the decoder rejects (tampered).
        - `write(value)` sets the cookie under its registered name with the client's own configured options merged over `baseCookieOptions()`.
        - `write(value, { expires })` merges a per-call option override on top of the configured options without mutating the client's own configuration for the next call.
        - `clear()` deletes the cookie by its registered name.
        - Two clients built for two different names never see each other's values.
    </behavior>
    <action>
Create `src/lib/server/cookies/cookie-client.ts`, opening with `import "server-only";`. Export a
factory (a `const` arrow function per ADR tech/0015, taking one destructured object parameter per
ADR tech/0016):

```
export const createCookieClient = <TValue>({ name, decode, encode, options }: CookieClientConfig<TValue>): CookieClient<TValue>
```

where `name: CookieName` (from `@/lib/core/cookies/cookie-registry` — no string literal),
`decode: (raw: string | undefined) => TValue | null`, `encode: (value: TValue) => string`, and
`options: Omit<Parameters<Awaited<ReturnType<typeof cookies>>["set"]>[2], never>` narrowed to the
per-client cookie attributes (`httpOnly`, plus `maxAge` or `expires`). The returned
`CookieClient<TValue>` is a factory-namespaced object literal (this project's established
abstraction shape) with:
- `read: () => Promise<TValue | null>` — `const store = await cookies(); return decode(store.get(name)?.value);`
- `write: (value: TValue, overrides?: CookieWriteOverrides) => Promise<void>` — sets
  `{ ...baseCookieOptions(), ...options, ...overrides }`. Compute the merged object fresh on every
  call so no caller can mutate another's configuration, matching `baseCookieOptions()`'s own
  documented reason for being a function rather than a frozen constant.
- `clear: () => Promise<void>` — `const store = await cookies(); store.delete(name);`

Do NOT weaken any flag by default: `baseCookieOptions()` supplies `secure`/`sameSite`/`path` and the
per-client `options` supplies `httpOnly`. There is no default value for `httpOnly` — every caller
states it explicitly, so a future client cannot silently inherit a permissive default. This is the
ASVS V3 Session Management control 02.1-RESEARCH.md's Security Domain names.

Rewrite `src/lib/server/cookies/theme-cookie.ts` to consume it:
```

    name: COOKIE.THEME,

    encode: (theme) => theme,
    options: { httpOnly: false, maxAge: THEME_COOKIE_MAX_AGE_SECONDS },
});
```
Keep `THEME_COOKIE_MAX_AGE_SECONDS` and its trailing one-line comment. Compress the existing file
header comment to at most three prose lines, keeping the WHY (client-writable by design, T-01-35/

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → Next.js server | The session cookie crosses this boundary on every request and is the sole bearer of identity |
| Next.js server → external API | The bridged `JSESSIONID` extracted from an upstream `Set-Cookie` header is replayed on subsequent calls |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02.1-09 | Information Disclosure | session cookie flags after the refactor | high | mitigate | The generic client supplies no default for `httpOnly`; the session client states `httpOnly: true` explicitly and `baseCookieOptions()` still supplies `secure`/`sameSite`/`path`. `session.test.ts`'s existing option assertions are kept unchanged as the regression net, and the acceptance criteria grep for the literal flag. |
| T-02.1-10 | Tampering | theme cookie value | medium | mitigate | `decode` runs `isTheme` and returns `null` for anything else — the theme cookie is client-writable by design (T-01-35/T-02-10), so decoding is the boundary. Preserved verbatim by `theme-cookie.unit.test.ts`'s tampered-value cases. |
| T-02.1-11 | Spoofing | upstream `Set-Cookie` parsing | medium | mitigate | `upstreamCookie.extract` keeps using `getSetCookie()` (array form) rather than the comma-joined header, so an `Expires` comma cannot split one entry into two and let an attacker-shaped value be read as the session cookie. Now covered by a real test. |
| T-02.1-12 | Elevation of Privilege | per-call option override | medium | mitigate | `write`'s `overrides` merge is computed fresh per call over `baseCookieOptions()` + the client's own options; a caller cannot mutate the client's configuration for a later call. Covered by a `<behavior>` bullet and its test. |
| T-02.1-SC | Tampering | npm/pip/cargo installs | high | mitigate | No packages installed by this plan. |
</threat_model>
