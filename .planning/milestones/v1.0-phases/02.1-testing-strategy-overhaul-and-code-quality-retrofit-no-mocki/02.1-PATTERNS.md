## Pattern Assignments

### `src/features/boards/hooks/use-board-list.ts` (hook, request-response + optimistic)

**Analog:** `src/features/theme/hooks/use-theme-preference.ts` (whole file, 95 lines — small enough
for one read, excerpted in full below since every part of it is load-bearing for the new hook)

**Core pattern** (lines 50-93):
```typescript
export const useThemePreference = ({ initialTheme, isAuthenticated }: UseThemePreferenceArgs) => {
    const [theme, setTheme] = useState<Theme>(initialTheme);
    const [errorMessage, setErrorMessage] = useState<string | null>(null);

    const mutation = useMutation({
        mutationFn: updateThemeAction,
        retry: false,
    });

    const toggleTheme = (): void => {
        const previousTheme = theme;
        const nextTheme: Theme = previousTheme === THEME.DARK ? THEME.LIGHT : THEME.DARK;

        // Optimistic: apply first, persist second
        setErrorMessage(null);
        setTheme(nextTheme);
        applyDocumentThemeClass(nextTheme);

        mutation.mutate(nextTheme, {
            onSuccess: (result) => {
                if (result.status === "error") {
                    setTheme(previousTheme);
                    setErrorMessage(FAILURE_MESSAGE);
                }
            },
            onError: () => {
                setTheme(previousTheme);
                setErrorMessage(FAILURE_MESSAGE);
            },
        });
    };

    return { theme, toggleTheme, errorMessage };
};
```

**What to change for `useBoardList`:** `initialTheme` → `initialBoards: Board[]`; `toggleTheme` →
`addBoard`/`renameBoard`/`deleteBoard` (three mutations instead of one, each wrapping the matching
Server Action from `create-board.ts`/`rename-board.ts`/`delete-board.ts`); the unauthenticated
cookie-write branch (lines 72-75 of the analog) has no board-domain equivalent and should be dropped,
not ported. `retry: false` and the optimistic-apply-then-mutate-then-rollback-on-error/failure
skeleton carry over exactly.

**Auth + validation + core pattern** (lines 26-63):
```typescript
export const updateThemeAction = async (theme: Theme): Promise<UpdateThemeResult> => {
    const record = await verifySession();
    if (!record) {
        return { status: "error" };
    }

    const parsed = themeSchema.safeParse(theme);
    if (!parsed.success) {
        return { status: "error" };
    }

    const { error } = await externalApi.PUT("/users/me/theme", {
        params: { query: { userId: record.id } },
        body: { theme: parsed.data },
    });

    if (upstreamError !== undefined) {
        return { status: "error" };
    }

    return { status: "success", theme: parsed.data };
};
```

**What to change for `createBoardAction`:** replace `externalApi.PUT("/users/me/theme", ...)` with
`externalApi.POST(EXTERNAL_PATH.BOARDS, { params: { query: { userId: record.id } }, body: { name: parsed.data.name } })`
(use the `EXTERNAL_PATH` constant per D-14, not a literal); replace `themeSchema` with a new
`createBoardSchema = z.object({ name: z.string() })`; validate the response body with
`BoardSchema.safeParse(data)` before returning (per D-12) instead of trusting `data` directly; add
`refresh()` from `next/cache` after a confirmed success (new for this phase — no existing action
calls `refresh()` yet, see RESEARCH.md Architecture Patterns §1 for the exact call). Session-check
ordering (session first, then schema validation, before any upstream call) is the one rule to copy
verbatim — it is this repo's documented security control (RESEARCH.md's "Known Threat Patterns"

### `src/features/boards/schemas.ts` (model, transform/validation)

**Analog:** `src/features/theme/actions/update-theme.ts` lines 18, 37 (only zod precedent in the
repo) + the type/guard file it replaces, `src/features/boards/types.ts` (whole file, 27 lines, being
deleted):

**Existing hand-written guard being replaced** (`types.ts` lines 7-26):
```typescript
export type Board = { id: string; name: string; version: number };
export const isBoard = (value: unknown): value is Board => {
    if (typeof value !== "object" || value === null) return false;
    const candidate = value as Record<string, unknown>;
    return typeof candidate.id === "string" && typeof candidate.name === "string" && typeof candidate.version === "number";
};
export const isBoardArray = (value: unknown): value is Board[] => Array.isArray(value) && value.every(isBoard);
```

**zod precedent to extend** (`update-theme.ts` lines 18, 37):
```typescript
const themeSchema = z.enum([THEME.LIGHT, THEME.DARK]);
// ...
const parsed = themeSchema.safeParse(theme);
if (!parsed.success) { return { status: "error" }; }
```

**New shape** (per RESEARCH.md's already-resolved placement + schema, `src/features/boards/schemas.ts`):
```typescript
import { z } from "zod";

export const BoardSchema = z.object({
    id: z.string(),
    name: z.string(),
    version: z.number(),
});
export type Board = z.infer<typeof BoardSchema>;
// call site: BoardSchema.array().safeParse(data)
```

`{status:"error"}` convention exactly, and RESEARCH.md's Don't-Hand-Roll table names `ColumnResponseDTO`
(`generated-types.ts:294-301`) as the next DTO needing the identical treatment.

### `src/lib/server/cookies/cookie-client.ts` (utility, D-10 generic cookie client)

**Analog 1 — the `next/headers`-based shape to generalize:** `src/lib/server/cookies/theme-cookie.ts`
(whole file, 35 lines):
```typescript
import "server-only";
import { cookies } from "next/headers";
import { baseCookieOptions, COOKIE } from "@/lib/core/cookies/cookie-registry";
import { isTheme, type Theme } from "@/lib/core/theme/theme";

export const themeCookie = {
    read: async (): Promise<Theme | null> => {
        const cookieStore = await cookies();
        const value = cookieStore.get(COOKIE.THEME)?.value;
        return isTheme(value) ? value : null;
    },
    write: async (theme: Theme): Promise<void> => {
        const cookieStore = await cookies();
        cookieStore.set(COOKIE.THEME, theme, {
            ...baseCookieOptions(),
            httpOnly: false,
            maxAge: THEME_COOKIE_MAX_AGE_SECONDS,
        });
    },
    clear: async (): Promise<void> => {
        const cookieStore = await cookies();
        cookieStore.delete(COOKIE.THEME);
    },
};
```

**Analog 2 — the second near-duplicate call site to fold in:** `src/lib/server/session.ts` lines
103-108 (write) and 145-153 (verify/destroy) — same `await cookies()` + `cookieStore.set/get/delete`
+ `baseCookieOptions()` shape, but `httpOnly: true`, an `expires` timestamp instead of `maxAge`, and
a JWT-encoded value instead of a raw enum string:
```typescript
const cookieStore = await cookies();
cookieStore.set(COOKIE.SESSION, value, {
    ...baseCookieOptions(),
    httpOnly: true,
    expires: expiresAt,
});
// ...
const verify = async (): Promise<SessionRecord | null> => {
    const cookieStore = await cookies();
    return verifyToken(cookieStore.get(COOKIE.SESSION)?.value);
};
const destroy = async (): Promise<void> => {
    const cookieStore = await cookies();
    cookieStore.delete(COOKIE.SESSION);
};
```

**Design implication for the generic client:** `createCookieClient<T>(name: CookieName, codec: {
encode, decode })` needs a per-call `options` override (since `theme-cookie.ts` uses `httpOnly: false`
+ `maxAge` and `session.ts` uses `httpOnly: true` + `expires`) — the V3 Session Management security
requirement (RESEARCH.md Security Domain) is that a generic client must NOT weaken the session
cookie's `httpOnly: true` while keeping the theme cookie's `httpOnly: false` intentional. Do not fold
`upstream-cookie.ts` into this same generic — RESEARCH.md's Open Question 1 flags it as structurally
different (parses a raw `fetch` `Response`, no `cookies()` call at all) and recommends treating it as
a deliberately separate, smaller module unless the user confirms otherwise.

**Source registry to reuse unchanged:** `src/lib/core/cookies/cookie-registry.ts` (`COOKIE`,
`baseCookieOptions()`) — no change needed here, both analogs already import from it.

## Shared Patterns

### Session-first, then-validate ordering (security control, applies to every new Server Action)
**Source:** `src/features/theme/actions/update-theme.ts` lines 27-40 (`verifySession()` called and
checked before `themeSchema.safeParse()`, itself called before any `externalApi` call)
**Apply to:** `create-board.ts`, `rename-board.ts`, `delete-board.ts`, and any future Column/Task/
Subtask Server Action. This is RESEARCH.md's documented Tampering mitigation — a Server Action is
invokable over the wire with an arbitrary payload regardless of what TypeScript claims about its
caller, so this ordering is real runtime defense, not formality.

### `userId` always session-derived, never client-supplied (security control)
**Source:** `app/api/boards/route.ts` lines 11-14 comment + `app/(dashboard)/layout.tsx` lines 12-15
comment (both already document this exact control for the code being replaced/extended)
**Apply to:** every board/column/task RSC read and Server Action write — the OpenAPI contract
declares `userId` a client-suppliable query parameter, but every call site must read it from
`verifySession()`'s own record instead. This must be preserved, not regressed, when porting
`route.ts`'s logic into the RSC.

### `.safeParse()` never `.parse()` (validation convention)
**Source:** `src/features/theme/actions/update-theme.ts` line 37, `src/lib/server/session.ts`'s
`isSessionPayload` treats a bad shape as a recoverable `null`/`{status:"error"}`, never an uncaught
exception
**Apply to:** every new zod schema (`schemas.ts` for boards, and Column/Task/Subtask as they're
built) — a bad upstream shape must resolve to a handled error branch, matching every existing
guard's behavior in this codebase.

### `as const` object, never `enum` (ADR tech/0012, applies to D-13/D-14)
**Source:** `src/lib/core/routing/routes.ts` (`ROUTE`), `src/lib/core/cookies/cookie-registry.ts`
(`COOKIE`), `src/lib/core/api-contract/external-paths.ts` (`EXTERNAL_PATH`) — three existing
identical instances of the pattern
**Apply to:** the E2E test-config constants grouping (D-13, e.g. a new `E2E_CONFIG` object in
`e2e/test-env.ts` wrapping `E2E_SESSION_SECRET`/`E2E_EXTERNAL_API_BASE_URL`/`E2E_PORT`/
`E2E_BASE_URL`) and any new route constants added to `EXTERNAL_PATH` for Column/Task/Subtask (D-14).

### Arrange-Act-Assert comment convention (D-06)
**Source:** `src/components/layout/sidebar/sidebar.test.tsx` — every `it()` block already uses this
exact `// Arrange` / `// Act` / `// Assert` structure (see lines 87-101 excerpted above)
**Apply to:** every rewritten/new E2E test body and, per D-06's text, worth carrying into the
retrofitted unit/component tests too for consistency even though D-06 is technically scoped to E2E.

### Environment-shim mock exception, documented inline (D-19)
**Source:** `src/components/layout/sidebar/sidebar.test.tsx` lines 27-45 (`next/link`/
`next/navigation` mocks, each with an inline comment citing the specific Vitest Browser Mode
limitation being worked around)
**Apply to:** any of the 14 `vi.mock` files where a mock survives the retrofit because it targets a
framework/environment gap rather than this project's own business logic — every such surviving mock
needs the same inline-comment justification, not a bare `vi.mock(...)` call.
