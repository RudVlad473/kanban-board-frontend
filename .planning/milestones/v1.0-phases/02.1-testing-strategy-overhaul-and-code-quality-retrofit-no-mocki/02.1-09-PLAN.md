<objective>
Bring the auth and theme feature components' tests into no-mocking compliance by replacing their
Server Action module mocks with the config-level stub aliasing the Storybook project already uses,
and give every component in those folders a stories/test pair.

Purpose: these four test files mock this project's own Server Action modules — the most clearly
banned category under D-04. They cannot call a real Server Action: they run in Vitest Browser Mode
(real Chromium, no Next.js server), and the action's import chain reaches `node:crypto`. The
repository already solved this exact problem for its `storybook` Vitest project with exact-specifier
aliases to real stub modules in `src/test-utils/`. Extending those aliases to the `browser` project
removes the mocks without inventing a new mechanism, and lets every assertion run through composed
stories per D-08.

Output: the `browser` project aliased like the `storybook` project, four rewritten test files, three
new stories files, one new test file, and one new stub module.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user input → auth form → Server Action | The forms are where credentials are entered and where the backend's error codes become user-visible copy |
| test config → module resolution | An alias silently substitutes a different module for a production import specifier |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02.1-29 | Information Disclosure | auth form error copy | high | mitigate | Task 2 asserts the exact copy for each mapped backend error code, including that a bad-credentials failure does not disclose whether the email exists. If the current tests do not assert that distinction, add it — this is the coverage D-05 removes from e2e and it must not simply vanish. |
| T-02.1-30 | Tampering | the stub alias reaching a production build | high | mitigate | The alias lives only inside `vitest.config.ts`'s test-project `resolve` blocks — `next.config.ts` and the production build never read it. The entries are exact specifiers, and the shared `serverActionStubAlias` constant is declared once so the `browser` and `storybook` lists cannot drift into covering different modules. `pnpm build` in the plan's verification confirms the production bundle is unaffected. |
| T-02.1-31 | Spoofing | a stub whose signature drifts from the real action | medium | mitigate | Each stub exports the same symbol name and signature as the real module; `pnpm exec tsc --noEmit` type-checks the real modules, and a drifted stub surfaces as a runtime failure in the composed-story run rather than silently passing. |
| T-02.1-32 | Tampering | accessibility regressions from three new stories files | medium | mitigate | All three are collected by the `storybook` project's axe-core gate, a verify command on every task. |
| T-02.1-SC | Tampering | npm/pip/cargo installs | high | mitigate | No packages installed by this plan. |
</threat_model>
