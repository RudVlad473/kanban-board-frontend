<objective>
Creating a task with subtasks leaves the new card captionless for the length of two server round
trips. Measured on the running app 2026-09-05: the card appears at t=74ms, the create response
lands at t=339ms, and `0 of 2 subtasks` only appears at t=499ms when the subtask fan-out lands.
The cause is in code, not timing — `useCreateTask.onMutate` stages the placeholder task with
`subtasks: []`, and subtasks reach the cache only when `createTaskSubtasksAction` succeeds.

Purpose: stage the typed subtask titles as placeholder rows in the SAME optimistic write that
stages the card, so the caption is there from the first frame — and close the new hazard that
creates, which is a client-generated subtask id becoming reachable by a toggle.
Output: one changed hook, one widened guard read, and two tests falsified against the unfixed code.
</objective>

1. **The current mechanism, read in `use-create-task.ts`.** `createTaskMutation.onMutate` inserts
   the placeholder task with `subtasks: []`. `onSuccess` calls `withTaskReplace`, which merges, so
   whatever `subtasks` array the placeholder holds survives the swap to the server's id. `onError`
   calls `withTaskRemove`, which takes the whole task and therefore its subtasks with it — the
   failure path needs no new work. `createSubtasks` appends `result.created` with `withSubtaskInsert`
   on success and writes nothing at all on a wholesale failure.
2. **`CreateTaskVariables` does not carry the titles today.** `subtaskTitles` lives only on
   `CreateTaskArgs`, which `createTask` destructures. `mutateAsync` is called with
   `{ boardId, columnId, title, description, clientId }`. The titles have to be added to the
   variables for `onMutate` to see them.
3. **The reducers already exist and are exported from `src/features/tasks/model.ts`:**
   `withSubtaskInsert` (appends one subtask to a task) and `withSubtaskRemove` (drops one subtask by
   id, and is already reused by `useCreateSubtask.onSuccess` for exactly this placeholder-retirement
   purpose). Neither needs changing. `toSubtaskSummary` renders `${completed} of ${length} subtasks`
   with no pluralisation, so one subtask reads `0 of 1 subtasks`.
4. **The shipped placeholder→real-id swap to copy is `use-create-subtask.ts`.** Its `onMutate`
   stages `{ id: clientId, title, isCompleted: false, version: 0 }`; its `onSuccess` removes that id
   and inserts the server's row. That is the shape this plan generalises to N rows at once.
5. **The guard already exists and is already wired at the call site.**
   `task-detail-modal.tsx:41` reads `useUnconfirmedIds({ mutationKey: MUTATION_KEY.CREATE_SUBTASK })`
   and passes `unconfirmedSubtaskIds.has(subtask.id)` into each `SubtaskChecklistRow`'s `isPending`.
   `edit-task-modal.tsx:58` does the same for its editor rows. Neither component needs editing.
   `SubtaskChecklistRow` renders `isPending` as `Field.Root disabled` plus `aria-busy` on the
   checkbox.
6. **`useUnconfirmedIds` reads ONE id per mutation.** Its `select` returns
   `(mutation.state.variables as { clientId?: string })?.clientId`, then filters out nils. A fan-out
   staging N rows needs it to read a plural array too. Its `fingerprint` memo (`[...present].sort().join("|")`)
   keeps working unchanged once `present` is a flat `string[]`.
7. **`createTaskSubtasksAction` returns `{ status, failedTitles, created }`.** `created` is in title
   order and holds only the rows that actually landed (`createChildrenSerially` pushes a value to
   `failedValues` and `continue`s on any refusal or unparsable body), so `created` and the typed
   titles are NOT index-aligned when anything fails. Retiring every placeholder id and then
   inserting `created` is correct for both the all-succeeded and the partial case; pairing by index
   is not.
8. **`MUTATION_KEY.CREATE_SUBTASK` is `["create-subtask"]`**, declared in
   `src/lib/core/query-keys/mutation-keys.ts`. `useCreateSubtask` already tags itself with it. Its
   only readers are the two modals in fact 5.
9. **The test file's stub controls, read in `src/test-utils/action-stub-registry.ts`:**
   `actionStub(action)` gives `.queue(outcome)`, `.hold()` (leaves the NEXT call unresolved),
   `.settle()`, and `.calls`. There is no implicit success default — an unqueued call is reported by
   the global `afterEach` and fails the run.
10. **The story that renders the board is `WithBoardBelow`**, and it is the only one on which an
    optimistic card is visible at all. It seeds `createBoardFull({ columns: createColumnsFull({ count: 3 }) })`,
    so each column already holds 2 fixture tasks with 3 subtasks each. The modal's Status control
    defaults to the FIRST column, which is where a new card is appended.
11. **The existing in-flight test to copy is
    `"renders the new card in its column, the modal already gone, before the create resolves"`**
    (~line 183). It shows the whole `queue` → `hold` → submit → `waitFor(calls)` → assert → `settle`
    shape, and `getFirstColumnTaskTitles()` (~line 75) reads each `li`'s first `button span`. The
    caption is the SECOND span inside that same button.
12. **The checklist query pattern is `screen.getByRole("checkbox", { name: TITLE })`**, and the
    busy/disabled assertions used by `task-detail-modal.test.tsx:220-221` are
    `expect.poll(() => checkbox.getAttribute("aria-busy")).toBe("true")` and
    `expect(checkbox).toHaveAttribute("aria-disabled", "true")`.
13. **The scoped test command is grounded.** `pnpm vitest run --project browser src/features/tasks/components/add-task-button/add-task-button.test.tsx`

    every test runs twice; both variants must pass.
14. **The e2e already asserts the end state.** `e2e/tasks-create.e2e.spec.ts:65,77` polls for
    `0 of 2 subtasks` after a two-subtask create and again after a reload, and line 80's test
    asserts a subtask-less task's card name is the title ALONE. Both must still pass — the second is
    the guard against staging a caption when there are no titles.
15. **`security_enforcement` is `false` in `.planning/config.json`.** No threat-model section is
    required, and this change crosses no trust boundary — it adds no request, and the one new
    request path it could have created is the thing task 3 disables.
16. **Known interaction, not in scope to fix.** `createTaskAction` calls `refresh()` before it
    returns. Per docs/adr/tech/0030 rule 1, the resulting RSC render overwrites the board entry
    through `HydrationBoundary` — and that refreshed board holds the task with `subtasks: []`,
